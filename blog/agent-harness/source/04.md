为什么 strict 输出比“请遵守 JSON”更有约束力？关键区别是干预位置。提示词影响模型更愿意生成什么；约束解码在每一步生成时，直接限制什么 token 还能被选择。

假设当前前缀是 `{"status":`，schema 要求值只能是字符串枚举 `"ok"` 或 `"failed"`。解码器根据当前前缀和语法状态，计算下一步允许的 token 集合，把不合法候选的概率屏蔽，再在剩余候选中选择。生成推进之后，解析状态也随之改变。原本分配给非法 token 的概率被移除，剩余分布再归一化。这种机制减少了后验“生成完再修 JSON”的需要。

这里有一个容易误导的动画：把所有答案画成一棵有限前缀树，然后沿树走到叶子。对于只有几个固定枚举值的玩具任务，这个图很直观；对于任意深度的嵌套 JSON，却不够。完整结构可能需要上下文无关文法、解析栈以及随生成维护的状态。OpenAI 的公开技术说明描述了将 schema 转换为 CFG 的做法，并讨论递归结构；不同 provider 不必使用完全相同的实现。[来源：Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)

还要记住，模型输出的基本单位是 token，通常不是单个字符。一个 token 可能覆盖引号、字母甚至相邻标点，因此“这个字符现在合法吗”的检查不能直接照搬成“这个 token 现在合法吗”。实现需要考虑 tokenizer 与语法前缀的配合。词表 trie 可以帮助组织 token 匹配，但它只是可能使用的数据结构之一，并不独立承担全部语法表达能力。

XGrammar 的研究重点之一，是把能够预先计算的检查与依赖当前解析状态的检查分开，降低逐 token 检查成本；后续 XGrammar 2 继续处理动态结构和工具调用相关问题。这些工作说明，约束解码除了正确性，还涉及预处理成本、缓存、动态分支与推理吞吐。入门时不必先实现解析器，但要避免把实际系统理解成一个静态字符串白名单。[来源：XGrammar](https://arxiv.org/abs/2411.15100)、[XGrammar 2](https://arxiv.org/abs/2601.04426)

约束越强是否越好？仍需看任务。schema 可以要求输出 `price` 数字，却无法凭结构知道这个数字是否来自正确报价；可以要求 `citations` 数组，却无法凭数组形状知道引用是否支持结论。过度限制还有可能逼模型在信息不足时选择某个合法但错误的值。为“无法判断”设计一个显式表示，比只留下几个必须硬选的选项更好。

你还需要处理输出未完成的情况。生成到一半触达 token 上限，用户取消，接口返回错误，都可能导致没有完整对象。所谓结构保证通常有适用条件和支持范围，应用必须读取终止状态。对工具执行而言，唯一安全的时机是完整调用已组装、参数已验证、权限已通过之后。
