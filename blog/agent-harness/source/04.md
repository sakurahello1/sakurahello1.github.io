## 干预的位置不同：劝说，还是把门锁上

在网页上填出生日期，常见两种做法。一种是一个文本框，旁边写着“请按 YYYY-MM-DD 格式填写”；另一种是日期选择器，你只能在滚轮上选年、月、日。前一种是**劝说**：大多数人会照做，但总有人写成“2026/2/3”或者“去年春天”。后一种在你输入的那一刻，就把不合法的写法排除了。

让模型输出 JSON，也有这两种做法。要看清区别，先得知道模型是怎样一段一段写出文字的。模型每次只生成一个 **token**（词元，模型读写文字的基本单位，可能是一个字、半个词，或者几个标点连在一起）。每一步，模型给词表里的每个候选 token 打一个分，换算成概率；**解码器**（decoder，负责从这些候选里选出一个的那部分程序）选定一个，接到已经写出的文字，也就是**前缀**后面，然后进入下一步。

为什么 strict 输出比“请遵守 JSON”更有约束力？关键区别是**干预位置**。提示词影响模型更愿意生成什么；**约束解码**（constrained decoding）在每一步生成时，直接限制什么 token 还能被选择。

提示词再怎么写，也只是让不合法的候选“不太可能”被选中；约束解码让它们“不可能”被选中。这就是日期选择器和文本框的区别。

这张图还说明了一件容易被忽略的事：约束解码要插在“打分”和“选出一个”之间，所以**通常只有运行模型的那一方才能做**。你通过 API 调用一个托管模型时，拿到的是已经选好的 token，没法从外面按语法状态给每一步加掩码；你能做的是在请求里交上 schema、打开 strict 这类选项，由 provider 在它那一侧完成约束。自己部署开源模型时，这一步就落到了你所用的推理引擎上。

还要分清层次。约束解码作用在[第 4 讲](#lesson-4)五层里的第 2 层“符合结构”：字段、类型、枚举。在它支持的范围之内，形状出错的机会被拿掉了；可第 3 层以下的事，比如报价是不是真的、用户有没有授权，它基本管不到。例外是某条业务规则恰好能直接写进语法，比如下面实验里的“只能买 1 到 3 台”。

## 一步一步收窄：屏蔽，再重新归一化

来看一步具体的。假设当前前缀是 `{"status":`，schema 要求这个值只能是字符串枚举 `"ok"` 或 `"failed"`。

解码器根据当前前缀和语法状态，计算下一步允许的 token 集合，把不合法候选的概率屏蔽，再在剩余候选中选择。原本分配给非法 token 的概率被移除，剩余分布再**归一化**：每个剩下的概率除以它们的总和，让它们重新加起来等于 100%。生成推进之后，解析状态也随之改变，下一步的允许集合又会不同。

```

这种机制减少了后验“生成完再修 JSON”的需要。没有它时，常见的做法是等模型写完，解析失败了再让它重写，或者用一段代码去“修补”括号和引号。重写要多花一次调用；修补则是在猜模型本来想写什么，猜错了比报错更糟。有了约束，每一步都只能从合法的候选里选，写到结尾自然就是合法的结构。

“选”的方式有两种。一种是每一步都挑概率最大的那个，叫**贪心解码**，下面的实验就是这样做的；另一种是按概率随机抽取，叫**采样**，概率 71% 的 `"ok"` 大多数时候会被抽中，偶尔也会抽到 `"failed"`。无论哪一种，屏蔽都发生在挑选之前，所以被屏蔽的候选在两种方式下都没有机会。

下面的实验把同样的机制放到一个小目标上：输出 `{"quantity": 1、2 或 3}`。先保持“语法约束”勾选，点“下一步”一步一步看。第一步里“好的，”、`DROP` 这些候选都被划掉，只剩 `{`，它的概率变成 100%；第四步最关键：模型最想写的是 `999`（45%），其次是 `1`（30%），再其次是带引号的 `"1"`（20%）；`999` 和 `"1"` 都被屏蔽，剩下的 `1`（30%）和 `2`（5%）重新归一化成大约 86% 和 14%。然后取消勾选“语法约束”，点“自动解码”：每一步都挑模型最想要的，最后得到 `{"quantity":999}`，格式完全正确，数量却不允许。还要留意一点：这个实验把“只能买 1 到 3 台”直接写进了语法，所以连业务规则也挡住了；很多业务规则没法这样写，最后一节会讲。

## 前缀树为什么不够：语法状态与解析栈

讲约束解码时，有一个很流行、也容易误导的动画：把所有合法答案画成一棵有限的**前缀树**（从根出发，每条边是一个字符，每条从根到叶子的路径就是一个合法答案），然后沿着树往下走，走到叶子就结束。对于只有几个固定枚举值的玩具任务，比如 `"ok"` 和 `"failed"`，这个图很直观。

对于任意深度的嵌套 JSON，它却不够。对象里可以有数组，数组里可以有对象，对象里又可以有数组，合法的输出有无穷多种，根本画不成一棵有限的树。这张图还会让人以为系统事先列好了所有答案，再逐个比对；实际上系统从来不列举答案，它只回答一个问题：**在当前这一刻，下一步可以写什么。**

想回答这个问题，光记住“已经写了哪些字符”不够，还得知道“现在身处哪一层结构里”。同样是刚写完一个值，在对象里，下一步可以是 `,` 或 `}`；在数组里，下一步却是 `,` 或 `]`。完整的结构可能需要：

- **上下文无关文法**（context-free grammar，CFG）：一组可以引用自己的规则，比如“一个值可以是对象，一个对象里包含若干个值”；
- **解析栈**：记下当前有哪些结构已经打开、还没有关上，像一摞叠起来的盒子，必须先关最里面那个；
- 随生成维护的状态：每写一个 token，都要更新这些记录。

OpenAI 的公开技术说明描述了将 schema 转换为 CFG 的做法，并讨论了递归结构；不同 provider 不必使用完全相同的实现。[来源：Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)

## token 不是字符

上面的讨论一直在说“字符”，可模型输出的基本单位是 token，通常不是单个字符。一个 token 可能覆盖引号、字母，甚至相邻的标点，比如 `"},` 这三个字符在某个词表里可能就是一个 token。因此，“这个字符现在合法吗”的检查，不能直接照搬成“这个 token 现在合法吗”。

反过来的情况也存在：token 的边界和语法的边界对不齐。语法眼里，`"ok"` 是一个完整的值；分词器却可能把它切成 `"o` 和 `k"` 两个 token，或者连着前面的空格切成 ` "ok`。于是解码器必须允许“写到一半”的 token：`"o` 本身不是一个完整的值，但它是一个合法值的开头，所以这一步应该放行。

判断一个 token 能不能选，要把它的字符一个一个喂给解析器，从当前状态出发，每一个字符都被接受，这个 token 才合法；中途有一个不行，整个 token 就要屏蔽。

这就引出了实现上的麻烦：真实的词表有几万到几十万个 token，每生成一步，理论上都要对每一个候选做这样的检查。实现需要考虑 **tokenizer**（分词器，把文字切成 token 的那部分程序）与语法前缀的配合。一种常见的组织办法是**词表 trie**：把所有 token 按共同前缀排成一棵树，这样开头相同的 token 可以一起检查，比如一旦发现在 `"}` 后面接 `}` 走不通，所有以 `"}}` 开头的 token 都可以一并排除。但 trie 只是可能使用的数据结构之一，它帮忙组织 token 的匹配，并不独立承担全部语法表达能力；语法本身仍要靠文法和解析栈来表示。

## 工程成本：预计算、缓存与动态结构

约束解码不是免费的。每生成一个 token 都要算出一个掩码，而模型推理本身已经很吃算力，这一步如果慢，整个服务都会慢下来。

XGrammar 的研究重点之一，是把能够预先计算的检查与依赖当前解析状态的检查分开，降低逐 token 检查的成本。用它自己的说法，是把词表分成两类：一类是**上下文无关的 token**，它能不能选只取决于当前处在语法的哪个位置，可以事先检查好；另一类是**上下文相关的 token**，比如上面的 `"}}`，能不能选还要看栈里更深处是什么，只能在运行时判断。论文还为后一类设计了专门的栈结构来加速检查。后续的 XGrammar 2 继续处理动态结构和工具调用相关的问题：agent 的输出格式不仅每个请求不同，在同一次回复里也会变化，比如先写一段自由文字，再切换到某个工具的参数格式。[来源：XGrammar](https://arxiv.org/abs/2411.15100)、[XGrammar 2](https://arxiv.org/abs/2601.04426)

| 成本 | 从哪里来 |
| --- | --- |
| 预处理 | schema 要先转换成语法，词表要按语法位置预先分类 |
| 逐 token 检查 | 每一步都要为整个词表算出一个掩码，上下文相关的 token 只能现场判断 |
| 缓存 | 不同请求带着不同的 schema，预处理的结果能不能复用，直接影响速度 |
| 动态分支 | 同一次输出里，结构可能在自由文字和某个工具的参数格式之间切换 |

这些工作说明，约束解码除了正确性，还涉及预处理成本、缓存、动态分支与推理吞吐。入门时不必先实现解析器，但要避免把实际系统理解成一个**静态的字符串白名单**：它不是拿输出去和一张“合法答案表”比对，而是在生成过程中，按不断变化的状态，一步一步地算出下一步能写什么。

## 约束越强越好吗？没写完又怎么办？

约束越强是否越好？仍需看任务。约束解码管的是**形状**。schema 可以要求输出 `price` 是数字，却无法凭结构知道这个数字是否来自正确的报价；可以要求 `citations` 是数组，却无法凭数组的形状知道这些引用是否支持结论。换到采购任务里：约束能保证 `total` 是整数，不能保证它等于 7480。

过度限制还有可能逼模型在信息不足时选择某个合法但错误的值。回想上一节的机制：屏蔽之后，剩下的概率会重新归一化。如果允许的选项里没有“不知道”，模型拿不准的那部分概率就只能被硬分给其他选项。

```

所以，为“无法判断”设计一个显式的表示，比只留下几个必须硬选的选项更好。[第 4 讲](#lesson-4)里 `total` 可以为 `null` 的写法，就是同一个道理。

最后，你还需要处理**输出没写完**的情况。生成到一半触达 token 上限，用户取消，接口返回错误，都可能导致没有完整的对象。约束解码保证的是每一步都接在一个合法的前缀后面，可是**合法的前缀不等于合法的输出**：`{"quantity":` 每一个字符都合法，它仍然不是一个完整的 JSON。所谓结构保证，通常有适用条件和支持范围，应用必须读取终止状态，而不是看到“开了 strict”就直接解析。

:::example 每一步都合法，结果却不能用
给采购答案开了 strict，却把输出上限设得太小。模型写到 `{"vendor":"clay","total":7480,"source":"quote-cl` 时，额度用完了。回头检查，每一个 token 都是从允许的候选里选出来的，没有一步违反语法；可这段文字缺了后半个引号，缺了 `delivery` 字段，也缺了收尾的 `}`。

响应的终止状态会说明它是因为长度上限停下的。正确的处理是把这次记为不完整，调大上限再试，而不是替它“补全”以后交给验收器：补出来的 `quote-clay-v2` 也许碰巧是对的，但那是你猜的，不是模型写的，更不是工具查到的。
:::

:::pitfall 看到 strict 就直接执行
“开了 strict，输出一定合法，所以可以直接执行”，这句话错了两处。第一，输出可能根本没写完，strict 保证不了完整；第二，就算完整，它也只证明了形状，数量是否合理、有没有授权，都还没人检查。对工具执行而言，唯一安全的时机是：完整调用已组装、参数已验证、权限已通过之后。
:::

:::recap 小结
- 提示词改变模型更愿意写什么；约束解码在每一步生成时直接限制哪些 token 还能被选，所以约束力更强。
- 每一步，解码器按当前前缀和语法状态算出允许的 token 集合，屏蔽其余候选，再把剩下的概率重新归一化后选择。
- 前缀树只适合几个固定枚举的玩具例子；任意深度的嵌套 JSON 需要上下文无关文法、解析栈和随生成维护的状态。
- token 不是字符，一个 token 要逐字符过一遍语法；约束解码还涉及预处理、缓存、动态分支和推理吞吐，不是一张静态的字符串白名单。
- 约束只管形状，管不了数值是否来自正确的证据；要给“无法判断”留出显式的出口，并读取终止状态，只在调用完整、参数已验证、权限已通过之后执行。
:::
