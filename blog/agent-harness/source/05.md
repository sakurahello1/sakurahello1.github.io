## “多想一会儿”其实是三件事

同事交来一份采购建议，你回一句“再想想”。他可能拿出草稿纸，把计算一步步写出来；可能转给一位更有经验的采购员重做；也可能什么都不改，只是在签字之前停下来，把合同对象和条款再核一遍。三种做法都叫“再想想”，花的成本不同，改善的环节也不同。

“让模型多想一会儿”至少也指三件不同的事：

1. **提示层面**：在提示里要求模型先写出中间步骤，再给结论。模型还是那个模型，只是输出的文字变长了。
2. **模型层面**：模型本身经过训练，具有特定的推理能力，并在推理阶段使用额外的计算。这类模型常被叫作推理模型；回答时（而不是训练时）多花的这部分计算，叫**测试时计算**（test-time compute）。
3. **harness 层面**：你的程序在关键的工具调用之间，专门安排一个检查或规划步骤。比如在给出推荐之前，先让系统列一张证据清单。

它们可能共同改善结果，但不是同一个机制。分清它们的好处很实际：效果变好或变坏时，你知道是哪个旋钮在起作用，下一次该拧哪一个。

## 思考该花在分叉处

开车时，没有人在直路上每一百米重新规划一次路线。需要停下来想的，是这几种时候：到了岔路口；导航说左转，路牌却写着此路不通；准备驶上一段开上去就掉不了头的高速。

agent 也一样。最有价值的思考机会，常出现在**决策分叉处**：

- **观察与原计划冲突**，需要重新定位问题。
- **两个工具都有用**，需要比较哪一个能带来更多信息，这叫比较**信息收益**：下一次调用最可能改变决定的，才值得先做。
- **准备执行不可逆操作**，需要核对对象和前置条件。

反过来，已知两个整数相加，让模型“认真思考”这道算术，既费 token 又可能算错，直接用确定性工具更划算。计算预算应该服务于**减少实际的决策错误**，而不是让每一轮都生成一大段文字。

把这三类分叉放到采购任务里，就能看出每一步该不该停：

这张图里值得“想”的三处，恰好是**错了代价最大**的三处：在冲突处想错，后面全部白做；在信息收益上想错，多花几次调用；在最终动作前想错，可能做出一件收不回来的事。而那道算术，想对了没有额外收益，想错了却会直接污染结论。

在自己的 harness 里，这些分叉往往有代码能识别的信号，不必每一圈都停：下一步要调用的工具带副作用（下单、写文件、发消息）；某个工具结果违反了任务里写明的硬约束（例如交期晚于截止日）；模型准备交出最终答案。只在这些时刻插入检查步，其余时候让循环照常运转。这样花掉的思考预算，大部分都落在了可能出错的地方。

:::pitfall 把“每一轮都长篇思考”当成稳妥
如果每一圈都让模型先写几百字的分析，成本会随圈数一起涨，而大多数圈里并没有需要权衡的分叉。更糟的是，冗长的文字会占据上下文，把真正的硬约束挤到不显眼的位置（[第 8 讲](#lesson-8)会讲窗口为什么会满）。与其处处加思考，不如找出那几个分叉，在那里加检查。
:::

## 研究说明了什么，没说明什么

“多想就更好”这个直觉，常被拿两项工作来支持。

第一项是 OpenAI 的 o1 研究。它在特定实验中展示了测试时计算与任务表现之间的关系：给模型更多推理阶段的计算，在那些任务上表现更好。第二项是 Anthropic 关于 think tool 的文章。文中的 think 是一个特殊的“工具”：调用它不会查询或改变任何东西，只是给模型一个在工具调用之间写下思考的位置。它和上面的第三个旋钮出现在同一个位置（工具调用之间），区别在于：是否停下来想，由模型自己决定，而不是由 harness 强制插入。文章报告了它在某些复杂的政策类工具任务上带来的改善。[来源：Learning to reason with LLMs](https://openai.com/index/learning-to-reason-with-llms/)、[The think tool](https://www.anthropic.com/engineering/claude-think-tool)

这两项结果都有明确的边界：具体的模型、具体的提示、具体的 benchmark 配置。它们**不构成**“输出的思考越长，所有任务就越好”这样的普遍定律。换一个模型、换一类任务，结论要重新测。

工程上值得做的，是把“增加思考”当成一个**可测试的变量**：固定其他条件，只改这一项，观察它是否真的减少了违规动作或错误结论。

| 这次实验里 | 具体做法 |
| --- | --- |
| 固定不变 | 模型版本、任务集、工具与其描述、其余提示、输出上限、调用次数上限、验收器 |
| 只改一项 | 例如 thinking 开或关；或者是否在推荐前插入证据清单步骤 |
| 记录结果 | 完成率、约束错误（违规动作、错误结论）、token、延迟、费用 |
| 判断依据 | 错误是否减少，以及为此多付了多少 token、时间和钱 |

最后一行很关键。一个旋钮让完成率变好，却让费用翻倍、延迟变长，值不值得，要看任务。只写“效果提升”不写代价，这个结论就是不完整的。

:::example 一个容易踩的不公平对照
你给“开启思考”的一组设了更大的输出上限，还允许多调用两次模型，结果它的完成率更高。这说明不了思考有用：多出来的可能只是预算。公平的比较要让两组花同样的预算，再看谁的错误更少。[第 25 讲](#lesson-25)会专门讨论怎样做等预算比较。
:::

下面这个实验原本是为多 agent 准备的（后面讲多 agent 时还会用到），但它演示的正是等预算的道理。总预算固定为 100 格，黑色是解题，橙色是协调，绿色是验证。把“agent 数”从 1 拖到 8，看黑色格子怎样被橙色挤掉，每个 agent 分到的解题预算怎样越来越少；再把任务切换成“必须一步接一步”，看墙钟时间的缩短幅度比“可以拆开并行”时小得多。注意这个实验里协调开销的算法只是示意，不是实测。把“多一个 agent”换成“多一段思考”，道理相同：多出来的开销要从同一份预算里扣，只有在等预算的对照里仍然减少了错误，才算真的有用。

::lab

## 把思考接到证据上

说了这么多“什么时候想”，还剩一个问题：想的结果放在哪里？如果它只是一段流畅的文字，别人没法核对，系统也没法据此行动。

一个有用的做法是：在推荐采购方案之前，让系统生成一张**简短的证据清单**，逐项回答四个问题：

1. 预算从哪里来？
2. 含税价格是怎么算出来的？
3. 交付日期对应哪一个报价版本？
4. 还有哪个字段是未知的？

这张清单不必复述模型的私有推理，它本身就是一个**可审核的外部产物**。随后由确定性验证器核对金额和日期。如果有字段缺失，就暂停推荐，先补查。这样，思考被接到了证据和行动上，而不是停留在文字里。

```json
{
  "budget": {"value": 7600, "from": "用户的原始任务"},
  "total": {"value": 7480, "from": "compute_total(clay, 1)", "source": "quote-clay-v2"},
  "delivery": {"value": "2026-10-03", "source": "quote-clay-v2"},
  "unknown": []
}
```

上面是一张填完整的清单（字段名是示意，不是某个 API 的格式）。每一个数字都指得出出处，`unknown` 是空的，验证器才有理由放行。下图演示清单在哪一栏卡住：


## 写得漂亮，不等于真实原因

很多人看到模型输出一段条理清楚的推理，会自然地认为：这就是它做决定的过程。这个推断不成立。

研究者做过这样的实验：在提示里放入会影响答案的线索，比如暗示某个选项才是正确答案，然后观察模型的回答和它写出的推理。结果发现，模型的可见推理可能**没有忠实披露**影响答案的那条提示线索：答案跟着线索变了，推理里却不一定提到它。读起来完整，不代表我们已经掌握了模型内部的因果过程。[来源：Language Models Don't Always Say What They Think](https://arxiv.org/abs/2305.04388)、[Reasoning Models Don't Always Say What They Think](https://arxiv.org/abs/2505.05410)

这对 harness 的影响很直接：日志应该帮助复盘**执行事实**，而不是用大量“我认真想过”的文字代替测试。复盘一次运行时，真正可靠的是这些东西：调用了哪个工具、通过校验的参数、工具返回了什么、读的是哪个版本、验证器查到了什么、最后为什么停止。

:::pitfall 用推理文字给结论背书
“模型解释得头头是道，所以推荐应该没问题”，这是把说服力当成了证据。上一节的证据清单之所以有用，恰恰因为它的每一栏都能拿去和工具返回、报价版本对账；一段推理文字做不到这一点。
:::

## 调用 thinking API：展示和协议是两回事

真正写代码调用带思考能力的 API 时，还要分清两类需求：**展示需求**（给人看什么）和**协议需求**（接口要求你怎么做）。前者你可以自由选择，后者不遵守，调用链就可能出错。

以 DeepSeek 为例。依据当前 DeepSeek 文档：

- thinking **默认开启**。教程和程序都应该显式选择开启或关闭，否则预算行为就不清楚：你以为是一次普通调用，实际上模型先花了一段思考。
- 工具调用场景中，返回的 `reasoning_content` 需要**按协议保留并回传**，包括相应的历史 assistant 消息。这类内容可以放在当前运行的内部历史里维护，不必默认展示，也不必导出。
- thinking 模式下，温度参数不产生通常预期的影响。想靠调温度控制它的随机性，可能是白费力气。
[来源：DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

另外还要留意一点，这一条不出自上面的文档：输出上限过小，模型可能耗尽预算，却没有给出最终答案。

第二条最容易做错，因为它把“展示”和“协议”缠在了一起。下面按时间顺序走一遍：

:::key 一句话
“多想”是一项要花钱的投入：把它放在决策分叉处，把它的产物变成可核对的证据，再用等预算的对照去检验它是否真的减少了错误。
:::

:::recap 小结
- “让模型多想”至少指三件事：提示里要求写出步骤、推理模型在推理阶段多花计算、harness 在工具调用之间插入检查或规划步骤；它们可能叠加，但不是同一个机制。
- 思考最值钱的地方是决策分叉处：观察与计划冲突、需要比较信息收益、准备执行不可逆操作；确定性的算术交给工具更划算。
- o1 和 think tool 的结果都受限于各自的模型、提示与 benchmark，不是“越长越好”的定律；要把“增加思考”当成变量，在固定其他条件、同等预算下测它是否减少错误。
- 可见的推理不一定忠实反映影响答案的因素；日志应记录执行事实，结论要靠证据清单和确定性验证。
- 调用 thinking API 时，展示与协议要分开：思考内容可以不展示，但工具调用场景下要按协议回传；开关要显式写明，输出上限要为思考留出余量。
:::
