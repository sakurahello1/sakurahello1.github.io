“能力饱和”至少有三种含义。第一是基准饱和：题目已经太容易，分数接近上限，新增能力无法体现在指标上。第二是信息饱和：相关资料已经齐全，继续搜索只会重复已有证据。第三是系统饱和：协调和整合耗尽预算，使实际解题资源下降。这三者需要不同处理，不能统一归结为“模型已经到极限”。

可以把总预算想成一只固定容量的水箱。直接推理、工具使用、分支通信、结果整合和最终验证，都要从中取水。增加分支可能扩大搜索面，也会多出任务说明、消息重复、冲突处理和汇总。若总量固定，每个 worker 实际得到的深度可能下降。一个任务必须连续分析很长的状态链，分成四份之后，每个人都只看了一小段，却还要花精力解释上下文，最终可能比完整执行更差。

协调税不只有 token。它还包括时间：等待最慢 worker、解决互相依赖、重新跑过期测试；包括信息：压缩报告时遗漏前提；也包括状态：每个分支观察到的环境版本不一致。某些代价可通过更好的协议减少，但不能因为消息是自动生成的，就认为协作没有成本。机器不抱怨开会，会议依然占用计算和关键路径。

前述 v3 论文报告了约 45% 基线表现附近的能力饱和现象，也讨论了不同架构中的轨迹级错误传播。[来源：论文 v3，结果与局限部分](https://arxiv.org/html/2512.08296v3) 这里不把 45% 当作部署阈值。不同任务的成功定义、题目难度和工具条件会改变分数含义；相同的 45%，可能表示做对一半独立题，也可能表示完整长流程的成功比例。这不是一个脱离任务仍然成立的物理常数。

如何知道系统正在饱和？不要只观察最终分数，还要看新分支是否带来不同的有效证据、通信占比是否上升、重复操作是否增加、纠错是否真的改变结果。假如从两个分支扩到四个，搜索覆盖没有扩展，只是重复读取同样网页，那么下一步更可能需要改进查询分工或聚合器，而不是增加到八个。若候选中经常存在正确答案，但最终选错，则瓶颈在选择与验证，不在候选数量。

还有一种容易误读的情况：整体分数不变，但高难度任务改善、简单任务退化。平均值会掩盖架构的适用分布。可以按依赖深度、工具调用强度、输入长度与验收难度分层，查看收益是否集中在某一类任务。不过分层过多、样本太少也会制造偶然模式，所以探索性观察应在新的保留集上检验，而不是直接写入路由规则。

动态分配预算是一个候选方向：简单任务先走单体；出现明确的独立子问题、需要第二种证据或候选搜索不足时，再生成分支。但路由器自身也要评估。它会误判任务难度，也会增加额外调用。一个复杂的自适应系统若只比固定单体略好，却更难维护、更难复现，未必是最佳选择。架构的目标是用可解释的代价提高可验证结果，而不是让结构图显得复杂。
