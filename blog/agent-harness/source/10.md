:::goal 读完这一讲，你能回答
- 模型标称能读很多 token，这个数字保证了什么，又没保证什么？
- 为什么“大海捞针”测试全部通过，也不能说明你的任务在这个长度上可靠？
- 长上下文任务答错了，怎样分辨是没找到、没用对、版本冲突、摘要走样，还是证据变了？
- 比较“全量塞入”“过滤片段”“摘要”几种输入策略时，实验要控制什么、分开记录什么？
- 为什么除了知识题，还要测模型能不能从当前状态正确地继续？
:::

## 标称窗口只回答了“装不装得下”

一间仓库标明能放一万箱货。这个数字告诉你货物不会被挡在门外，却没告诉你：仓管员能不能在一万箱里找到你要的那一箱，能不能把散在三个货架上的零件配成一套，会不会把去年的旧货当成今年的新货发出去。

模型的“上下文窗口”也是这样一个数字。先说两个术语。**token** 是模型读写文本的计数单位，一段文字切成多少 token 取决于模型的分词方式，汉字和 token 不是一一对应的。**标称窗口**是接口允许一次输入的最大 token 数：没超过，请求就被接受；超过了，就报错或者被截断。所以“模型支持很长的窗口”，首先只意味着接口允许输入这么多 token。

你真正需要知道的却是另一件事：在这项任务里，放进这些材料之后，模型还能否稳定地找出事实、连接证据、遵守约束，并得出正确结论。这两者之间的差距，可以用**有效上下文**来讨论。

## 有效上下文随任务而变

有效上下文不是一个放之四海而皆准的新规格，不存在脱离任务和可接受错误率的、通用的有效上下文数字。它取决于两样东西：**任务**，以及你**可接受的错误率**。

先看任务。一个模型可能很擅长在长文里找到唯一的一串密钥，却不擅长把十处合同条款合成一个判断：哪条是例外，哪条覆盖了哪条，哪个日期更晚。它能准确复述文档末尾的结论，也未必能发现中间某一页的数据与这个结论矛盾。找一个值、连几处证据、发现一处矛盾，是三种难度不同的工作，同一个长度上的表现可以差很远。

再看错误率。同一个模型、同一个长度，如果产出只是给人参考的草稿，偶尔漏看一条也许能接受；如果是自动提交之前的最后一道核对，漏看一次交期就是一次事故。所以说“有效”，总要带上“对哪项任务、在什么错误率要求下”。

最常见的长上下文测试叫**大海捞针**（needle-in-a-haystack）：在一大段无关文字里藏一句特定的话，也就是“针”，然后问模型那句话说了什么。它简单、好做、结果一目了然，但它测的主要是“找得到”那一层。RULER 通过不同长度和不同的任务设计说明，长上下文评估不能只靠一个简单的大海捞针测试。[来源：RULER](https://arxiv.org/abs/2404.06654)

## 答错了，先找错在哪一层

发烧的原因可能是感冒，也可能是别的感染，退烧药只能压住症状。长上下文任务的错答也一样：最后都表现为“答案不对”，病因却可能完全不同。调试时，先判断错误发生在哪一环：

| 类型 | 发生了什么 | 采购任务里的样子 | 常见的修法方向 |
| --- | --- | --- | --- |
| 召回问题 | 事实压根没被检索到，没进入 prompt | 交期更正在外部存储里，检索没选中它 | 检索与选择逻辑 |
| 使用问题 | 事实已经进入 prompt，却没被正确使用 | 税率规则就在上下文里，模型仍拿不含税价和预算比 | 编排与提示；计算交给工具 |
| 版本问题 | 新旧信息同时出现，却没有标记有效期 | 新旧两份 ink 报价都在，谁也没写哪份有效 | 版本字段与失效标记 |
| 压缩漂移 | 摘要改变了原文的意思 | 原文“可能延迟”，摘要写成了“已经延迟” | 摘要规则；保留回到原文的索引 |
| 证据不稳定 | 引用的文件后来被覆盖了 | 结论引用的报价文件已被新版替换，引用对不上 | 证据按版本保存，不原地覆盖 |

这里的 **prompt** 就是这一次调用实际发给模型的全部输入。这五类问题可能产生相似的最终错答，但需要不同的修复手段。把召回问题当成使用问题去改提示词，改多少遍都没用，因为那条事实根本不在输入里。

看一个完整的例子。假设采购 agent 推荐了 ink，而 ink 的交期是 2026-10-12，晚于 10 月 5 日的期限。你打开完整的事件记录，发现它曾读过一份旧报价，但新的交付更正只存在于外部存储中，检索没有选中它。


:::pitfall 窗口不够，就换个更大的
“答错了，一定是上下文不够长”是最顺手的判断，也很容易判错。先查事件记录：那条关键事实到底进没进 prompt？没进，是召回问题，该修检索；进了却没用对，才轮到编排和提示。换大窗口只对“确实装不下”这一种情况对症，而且往往意味着更多的输入费用和更多的干扰材料。
:::

## 把输入策略当成实验变量

“全塞进去”和“只给相关片段”哪个好，不必争论，可以测。一个好的实验应该把**输入策略**当成变量，其余一切保持不变。至少可以比较四种策略：

1. **全量小文档**：材料不多时，原样全部放进去。
2. **过滤片段**：按项目与日期过滤，只放相关的片段。
3. **有损摘要**：先把材料压成一段摘要，只放摘要。这里的“有损”指摘要必然丢掉一部分原文信息。
4. **摘要加源引用**：摘要里的每条结论都附上来源编号，需要时能回到原文核对。

答案要用同一份 fixture 的权威数据核验。**fixture** 是测试里事先准备好的固定数据，在我们的采购任务里，就是那份记着 clay 价格 6800 元、税率 10%、10-03 交付的数据，验收时据此核对含税 7480 元。模型和输出预算保持一致，否则你分不清差别来自策略，还是来自模型或输出长度。

指标至少要分开记录，不要合成一个总分：

| 指标 | 问的是什么 | 怎么判 |
| --- | --- | --- |
| 约束遵守 | 预算、交期、“只建议不下单”有没有被违反 | 对照任务约束逐条检查 |

| 引用支持 | 答案引用的来源，是否真的支持这个结论 | 按 `source_id` 找回原文比对 |
| 调用量与时间 | 花了几次调用、多少 token、多少秒 | 如实记录，单独报告 |

token 更少只是成本上的结果。如果它是靠丢掉关键约束换来的，就不能算整体优化：一个便宜三倍、却推荐了晚到供应商的方案，并没有省钱。

## 给每个片段贴上来源和版本

回想[第 10 讲](#lesson-10) 里冰箱门上的便签：两张都写着预算，都没写日期，你只能猜。解决办法很朴素，就是给每张便签写上是谁贴的、什么时候贴的、以哪张为准。

实践中，可以为上下文中的每个片段附上轻量的**元数据**，也就是“描述这段内容本身的数据”：

```json
{
  "source_id": "quote-clay-v2",
  "version": 2,
  "observed_at": "2026-09-30T10:00:00Z",
  "valid_from": "2026-09-28",
  "trust_level": "authoritative",
  "text": "clay 价格 6800 元，税率 10%，交付 2026-10-03"
}
```

字段的取值是示意。`source_id` 说明它来自哪份材料，事后可以对账；`version` 区分同一来源的新旧版本；`observed_at` 是系统读到它的时间；`valid_from` 是它从什么时候开始生效；`trust_level` 说明这段内容有多可信。

并非每个应用都需要全部字段，但至少要能区分三类内容：用户的**当前指令**、**权威的系统数据**，以及**未经确认的网页内容**。它们在输入里都只是文字，模型不会自动知道哪段该听、哪段只能参考，这件事要由 harness 写明。


一句话：**检索到的内容可以作为证据，不能因为位置靠前就升级为规则。** 这也和上一讲的结论接上了：位置至多影响一段内容好不好找，不影响它该不该信。[第 28 讲](#lesson-28) 会专门讨论不可信内容里夹带指令的情况。

## 不只是知识题：能否从当前状态继续

还有一个经常被忽视的维度：**过程状态**，也就是“这项工作做到哪一步了”。它和知识不同：知识回答“clay 的报价是多少”，过程状态回答“哪些已经查过、哪些试过但失败了、哪些操作已经发出去还没回音”。

模型如果忘记某个方案已经失败，就会重复探索，同样的弯路再走一遍；如果忘记已经发出的写操作，就可能重复副作用。所谓**副作用**，是指一个操作改变了外部世界，比如提交了一个任务、发出了一封邮件。读操作重复一次只是浪费，写操作重复一次，外部世界就多了一份。

:::example 知识题全对，续作却出错
设想一个虚构的情形：采购任务进行到一半，ink 的交期已经查过，确认晚于期限，一个交期核验任务 `delivery-check-17` 已经提交，还在运行。这时问模型“clay 的含税总价是多少”，它答 7480 元，知识题全对。可如果让它“从这里继续”，它也可能又去查一遍 ink，还重新提交一个核验任务。前一个是浪费，后一个是重复的副作用。只测知识题，这两个错误都测不出来。
:::

所以，长上下文评估不仅要问“能否答对知识题”，还要问“能否从当前状态正确继续”。一种做法是：把一段进行到一半的任务记录交给模型，其中包含一次失败的尝试和一个运行中的任务，然后检查它的下一步是否避开了已失败的方案，是否去查询运行中的任务、而不是重新提交。

这也是为什么[第 9 讲](#lesson-9) 的检查点里需要失败尝试、pending job 和下一动作。**pending job** 指已经提交、结果还没回来的后台任务。把它们写成明确的字段，就是为了让压缩之后的新上下文不必从一堆聊天记录里猜出“做到哪了”。

:::recap 小结
- 标称窗口只说明接口允许输入多少 token；有效上下文问的是，放进这些材料之后，模型还能否稳定地找到事实、连接证据、遵守约束并得出正确结论。
- 有效上下文不是一个固定规格，它取决于任务和可接受的错误率；RULER 说明，长上下文评估不能只靠一个简单的大海捞针测试。
- 长上下文的错答要先分类：召回、使用、版本、压缩漂移、证据不稳定，它们需要不同的修法；新证据没进窗口时，加大窗口不解决问题。
- 比较输入策略时，固定模型、输出预算和 fixture，把约束遵守、事实正确、引用支持、调用量与时间分开记录；token 少只是成本结果，丢了约束就不算优化。
- 给片段附上来源、版本、时间和信任等级，至少分清当前指令、权威数据和未确认内容；检索到的内容是证据，不因位置靠前变成规则。
- 除了知识题，还要测能否从当前状态继续：忘掉失败的尝试会重复探索，忘掉已发出的写操作会重复副作用。
:::
