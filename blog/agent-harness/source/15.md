这里没有任何一步必然在撒谎：测试可能只检查函数返回值；按钮可能只更新前端内存；成功提示可能在请求返回之前出现。真正的问题是，系统把“执行过程看起来顺利”误当成了“用户要求的状态已经建立”。

注意 agent 用来判断“完成”的证据全部来自它自己的执行过程：它跑的测试、它看到的提示。这些证据和它的工作是同一条链上的，链上任何一环有问题，证据也跟着有问题。这一讲要回答两个问题：“完成”到底该怎么定义，以及谁、凭什么来判断它。

## 先说清“完成”是什么：验收合同

**验证**（verification）指判断一个结果是否满足要求的过程，做这件事的程序或模型叫**验证器**。Verification 要解决的首先不是模型是否足够聪明，而是“完成”这个词到底意味着什么。

用户说“保存”，通常包含一些没说出口的条件：关闭页面后还能找回，不同用户的数据不会串号，失败时不能假装成功。执行 agent 不应该独自把这些条件缩减为“点击后显示一条 toast（页面角落弹出的短提示）”，再根据自己缩减后的标准给自己颁奖。

我们需要在实施前把目标展开成可检查的**验收合同**。这里的“合同”是本教程采用的工程术语，不是某个已有标准协议。一份最小合同可以写成：

```text
对象：用户 A 新建的一条待办
1. 保存后关闭页面；在新的浏览器会话中重新登录 A，条目存在。  证据：浏览器重开、数据库查询
2. 切换到用户 B，不能看到该条目。                              证据：权限测试
3. 模拟网络错误时，界面明确告知保存失败。                      证据：错误注入
```

这些句子同时说明了操作、对象、环境和期望结果，每一项还标注了证据来自哪里：浏览器重开、数据库查询、权限测试、错误注入。**错误注入**指故意制造一个故障（比如让网络请求失败），看系统怎样反应。

| 用户说的 | 合同里写成 | 证据来自 |
| --- | --- | --- |
| 保存 | 关闭页面、新会话重新登录后，条目仍在 | 浏览器重开、数据库查询 |
| 别串号 | 切换到用户 B，看不到 A 的条目 | 权限测试 |
| 出错别装没事 | 网络出错时，界面明确提示保存失败 | 错误注入 |
| 体验很好、完全可靠 | 不能直接检查；要么改写成具体条件，要么明确交给人判断 | 暂无 |

没有证据来源的“体验很好”“完全可靠”只能算愿望，不能直接作为自动验收条件。合同要在动手**之前**写，因为事后写的合同很容易被已经做出来的东西塑形：做成了什么，就写什么。

## 合同也只是代理：误接受与误拒绝

驾照考试考的是一组有限的动作。考过的人不一定真会开车；车技很好的人，也可能因为一个考纲没想到的习惯被扣分。

合同也一样，依然只是用户意图的**代理**：用户要的是好用的产品，测试检查的是有限的条件。遗漏条件会导致**误接受**：产品有缺陷，评分却通过。错误条件则会导致**误拒绝**：一个符合真实需要的实现，因为采用了评分器没想到的合法方法而失败。

因此，验证器不是站在系统外面的绝对真理。它也是软件，有需求、版本、盲区和维护成本。Anthropic 的 agent 评估指南区分了运行记录、评分器与最终环境结果，正是为了避免只看 agent 的陈述来决定成功。[来源：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 放到待办应用里：运行记录是 agent 做了什么、说了什么，包括那句“任务完成”；评分器是判分的逻辑；最终环境结果是数据库里到底有没有那条待办。只看第一样，就回到了本讲开头的那次失败。

:::pitfall 测试全绿，就是完成
测试也是合同的一部分，同样只是代理。测试只检查了函数返回值，全绿说明的就只是“函数返回值对”。要问的是：用户在意的那几个条件，有没有哪一个在测试里根本没出现？
:::

## 独立性：到底要独立什么

学生自己批改自己的卷子，换一支红笔也还是同一个人，同一个误解会在答题和批改时各出现一次。反过来，请一位同学来批改，他如果照着同一份错误的答案批，也谈不上独立。

所以，“独立”也不能靠新开一个聊天窗口获得。可以把独立性拆成五个问题：

| 问题 | 不独立的样子 | 独立的样子 |
| --- | --- | --- |
| 证据独立吗 | 验证器转述执行者的话：“文件已保存” | 验证器自己重新读文件、查数据库 |
| 判断独立吗 | 先读执行者的解释，被漂亮的理由带着走 | 先看验收条件和作品，再看执行者的解释 |
| 机制互补吗 | 所有检查都交给同一种手段 | 编译器、类型检查、数据库约束、模型审阅各查各的 |
| 权限隔离吗 | 执行者能删除测试、修改评分脚本、覆盖证据 | 检查器和证据放在执行者写不到的地方 |
| 环境干净吗 | 依赖某次运行留下的缓存和后台服务 | 从可复现的安装与启动过程开始 |

逐条多说一句。第一条最常被忽略：验证器读的如果是执行者写的总结，那它验证的其实是总结，而不是产物。第二条关于**锚定**：先看到的信息会影响之后的判断，先读了一段头头是道的解释，再看代码，就容易顺着解释去理解代码。第三条说的是，不同的检查手段能发现不同的错误：编译器发现语法错，数据库约束拦住重复主键，模型审阅也许能指出命名混乱，谁也替代不了谁。第四条最硬：执行者只要能改评分脚本，其余四条都可能失效。第五条针对的是“在我机器上能跑”：一个后台服务恰好还开着，测试就可能通过，换一台干净的机器就失败。

这五个问题比“验证器用了另一个模型”更重要。不同模型可能共享同一份错误资料；同一个模型如果获得新的数据库状态，也可能提供很有价值的独立检查。独立性的目的不是仪式性地多一票，而是让错误不那么容易沿着同一条链路同时污染生成与验收。

:::key 独立的是信息来源和权限，不是模型的名字
判断一次验证是否独立，先问它的证据从哪里来、执行者能不能碰到它。用的是不是另一个模型，排在后面。
:::

## 把独立做进架构

实现上，可以让生成器只返回产物位置，让验证器自行收集证据，再把结果交给一个非模型控制的**完成门**，也就是最终判定“完成还是未完成”的那段代码。

下面是架构伪代码，重点是数据流与职责，并非复制即可上线的完整应用：

```python
from dataclasses import dataclass
from typing import Literal

@dataclass
class Check:
    criterion: str
    verdict: Literal["pass", "fail", "unknown"]
    evidence_refs: list[str]
    reason: str

async def finish_candidate(candidate, contract):
    # 受信验证进程读取产物；执行 agent 不能写入这些检查器。
    evidence = await collect_fresh_evidence(candidate, contract)
    deterministic = run_executable_checks(evidence, contract)
    qualitative = await review_qualitative_checks(evidence, contract)
    checks = deterministic + qualitative
    # “不知道”不等于“失败”，但也不能被计为“完成”。
    required = contract.required_criterion_ids
    ids = [c.criterion for c in checks]
    complete = (
        bool(required)
        and len(set(required)) == len(required)
        and len(set(ids)) == len(ids)
        and set(ids) == set(required)
        and all(c.verdict == "pass" and bool(c.evidence_refs) for c in checks)
    )
    return {"complete": complete, "checks": checks}
```

对照上图读这段代码。`Check` 是一条合同的检查结果：哪一条（`criterion`），结论是什么（`verdict`，只有 pass、fail、unknown 三种），证据在哪里（`evidence_refs`），理由是什么。`collect_fresh_evidence` 里的 fresh 是关键：证据要重新收集，而不是沿用执行过程中留下的。检查分成两类，能用程序判定的（`run_executable_checks`，比如查数据库里有没有这条记录）和需要判断的（`review_qualitative_checks`，比如提示文字是否说清了失败原因，可以交给模型审阅）。最后的 `complete` 由五行条件共同决定：合同非空、必需项不重复、报告项不重复、报告与合同一一对应、每一项都是 pass 且带证据引用。本讲最后一节会解释为什么缺一不可，并用一张五关的图换个切法再走一遍。

## 反过来测验证器

验证器也是软件，也该被测试。最好再反过来测试验证器：故意把存储替换成内存、让按钮失效、把用户 ID 写错，观察验收能否发现。

这是**变异测试**思想在 agent 系统中的应用。变异测试原本是测试“测试”的方法：往代码里故意埋进小缺陷（叫“变异”），看测试能不能发现；发现的比例，说明测试有多少辨别力。放到这里，不要只数你写了多少检查，要看它们能辨认多少真实失败。检查写得再多，如果都在看同一个页面上的文字，它们合起来也发现不了“只存在内存里”。

测试验证器时还会遇到一个相反的问题：执行者改了测试，算不算作弊？执行者提交了一次合法测试修复，也不自动意味着作弊；需要检查用户授权、修改目的和是否降低了原本应满足的要求。比如界面上的提示文字按需求改了，测试里写死的旧文字跟着更新，这是正常维护；而删掉“切换到 B 看不到”那条测试，就是把要求降低了；除非用户明确授权放弃这项要求，否则不能接受，理由写得再好听也一样。

下面的实验就是一次小型的变异测试，场景换成了一个笔记应用：agent 要把一条笔记从“周五交报价单”改成“周四交报价单”并保存，道理和待办应用相同。先在“埋下的缺陷”里选一种：没有缺陷、只存在内存里、保存按钮被弹窗挡住、写进了另一个用户的记录（界面读的是本地缓存）、请求超时而服务端没写入；再在“验证手段”里选一种：只看 agent 说“已保存”、看一张截图、点击后刷新页面再看、刷新 + 查数据库 + 查 trace。点“运行并验收”，看界面、数据库、trace 三格怎样变化，以及下方的结论。三格里只有**亮起边框**的，才是这种验证手段真正看过的证据。

建议先试“写进了另一个用户的记录”配“点击后刷新页面再看”：刷新之后界面上的内容还在，因为界面读的是本地缓存；trace 里请求也返回了 200。数据库那一格其实已经写着 user_b 的新记录，但它没有亮起，这种验证根本没去看。现实里只做到刷新这一步的验证器，此时多半会判通过；实验因为知道埋了什么，才能告诉你“证据不足”。换成“刷新 + 查数据库 + 查 trace”，数据库那一格亮起，问题才被识破。再试“没有缺陷”配“只看 agent 说已保存”：结论也不是 PASS，因为光凭一句声明，无法和有缺陷的情况区分开。实验里“哪种证据能看到哪种缺陷”是预设的故障模型，用来说明证据强弱，不是某个评估器的实测结果。

::lab

## 完成门必须 fail closed

门禁系统断电时，门应该自动打开还是自动锁上？金库会选择锁上。这种“出了说不清的情况，默认结果是不通过”的设计，叫 **fail closed**。

完成门应 fail closed：合同为空、必需项重复、报告项重复、遗漏、unknown、没有证据引用，都不完成。前面伪代码里 `complete` 的那几行条件，就是逐一堵住这些口子。其中最隐蔽的是空合同这一个：

```python
checks = []  # 验证器出了错，一条检查结果也没返回
print(all(c["verdict"] == "pass" for c in checks))  # 输出 True
```

Python 的 `all()` 对空集合返回 `True`：没有任何一条检查，“全部通过”在逻辑上成立。验证器崩溃、合同没加载、过滤条件写错，都可能得到一个空列表；如果完成门只写了 `all(...)`，这些情况都会被判成“完成”。所以伪代码先用 `bool(required)` 拦住空合同，再用集合相等要求报告的条款和合同一一对应。

```figure
  {"at":[1],"pass":[1],"say":"第二关：条款没有重复。同一条检查报告两次，会让“数量对上了”变成假象，把漏掉的那一条掩盖过去。"},
  {"at":[2],"pass":[2],"say":"第三关：报告的三条和合同的三条一一对应。漏掉一条，就等于那一条没查。"},
  {"at":[3],"fail":[3],"say":"第四关：第二条“切换到 B 看不到”的结论是 unknown，权限测试的环境没能启动。unknown 不等于失败，但也不能算完成。"},
  {"at":[4],"say":"第四关已经不通过，结论是 incomplete，并写明缺的是哪一条、为什么。第五关同样要查：即使三条都是 pass，没有证据引用的也照样不算完成。"}]}
```

本课自己的验证器也是这样写的。Python 和浏览器固定题验证器在每条失败路径返回非空失败检查，不能借 `all([])` 真值退出：回答不是可解析的 JSON 时，它们返回的是 `{"parse": false}` 这样一条失败检查，而不是一个空字典；判定完成时，还要求五个检查项一个不多、一个不少，并且全部为真。检验空结果是必要回归测试：参考实现的测试专门把空字符串、`{}`、`[]` 和 `null` 交给验证器，确认验证器对它们返回的检查结果都不是“全部为真”。

fail closed 也有代价：环境不稳、检查偶尔超时，任务就会停在“未完成”，需要人或重试来处理。但这个代价是看得见的；反过来，把说不清的情况默认算作完成，代价要等到用户发现数据丢了才会出现。

:::recap 小结
- 执行过程看起来顺利，不等于用户要求的状态已经建立；执行者从自己的过程里拿到的证据，和它的工作在同一条链上。
- 验证首先要回答“完成”是什么：在实施前把目标展开成验收合同，写清操作、对象、环境、期望结果和每一项的证据来源；没有证据来源的形容词只是愿望。
- 合同只是用户意图的代理：遗漏条件导致误接受，错误条件导致误拒绝；验证器也是有盲区、要维护的软件，成功要看最终环境结果，而不是 agent 的陈述。
- 独立性拆成五个问题：证据、判断、机制、权限、环境；它们比“换一个模型”更重要。架构上让验证器自己取证，由非模型的完成门判定。
- 用变异测试反过来检验验证器能识破多少真实缺陷；完成门必须 fail closed，空合同、重复、遗漏、unknown、无证据都不算完成，并且要有检验空结果的回归测试。
:::
