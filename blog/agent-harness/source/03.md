软件通常需要确定的字段，模型默认擅长生成自然语言。让两者协作，第一步往往是要求“只输出 JSON”。但这里有几道独立的门，跨过前一道并不等于跨过后一道。

`{"date":"2026-02-30"}` 是合法 JSON。如果 schema 只要求 `date` 是字符串，它也符合 schema；日期仍然不存在。`{"recipient_id":"u_18"}` 可以通过严格结构检查，却指向同名的另一位用户。即使对象和权限都正确，发送服务也可能拒绝请求。我们至少要区分可解析、符合结构、事实与业务正确、经过授权、真实执行成功这几层。

JSON mode 通常改善语法层面的可解析性；结构化输出在支持的 schema 范围内进一步约束字段、类型与枚举；function calling 则给应用一个动作请求。模型生成 `get_quote` 调用之后，真正读取报价的仍是你的 Python 程序。应用执行，再把带对应调用 ID 的结果送回模型，下一轮才有机会利用该事实。[来源：Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Function calling](https://developers.openai.com/api/docs/guides/function-calling)

用函数调用的好处，是把面向用户的语言与机器可执行请求分开。你不必从“我认为可以查一下 A 的报价”里正则提取供应商。模型可以明确请求：

```json
{
  "name": "get_quote",
  "arguments": "{\"vendor_id\":\"A\"}"
}
```

注意 `arguments` 在常见 Chat Completions 协议中本身是一个 JSON 字符串。需要先取得完整字符串，再解析一次。流式响应里的参数常被拆成多个片段，收到前半截 `{"vendor` 时不能执行任何操作。还要按每个调用的 index 分别拼接，不能把并行调用的片段混在一起。

接口兼容也有范围。本文的 DeepSeek 示例使用官方 `openai` Python SDK 作为客户端。依据当前文档，普通 Chat Completions 的 JSON 模式使用 `response_format={"type":"json_object"}`，这不等于任意 JSON Schema 保证；strict 函数模式位于 beta 接口，并有受支持的 schema 子集。当前规则要求对象的属性列入 required，并设置 `additionalProperties: false`；长度等部分约束仍需本地检查。Responses 接口又有自己的结构化输出字段，不能把一个端点的限制复制到另一个端点。[来源：DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[Responses](https://api-docs.deepseek.com/api/create-response/)

实际工程里建议把本地 validator 看作恒定存在的一道边界。你可以逐步改善模型输出，让它更少撞上校验错误，但不要因此删除校验。对于缺失信息，允许模型明确返回“未知”或请求澄清，比强迫它填一个看似完整的值更可靠。对于拒绝、截断、网络错误和空输出，则应走独立状态分支，不能假设每次响应都包含一个完整业务对象。
