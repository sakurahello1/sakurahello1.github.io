## “只输出 JSON”只是第一道门

寄快递时填一张快递单。字写得工整，别人认得出来，这是第一步；收件人、电话、地址每一栏都填了，这是第二步；地址是真实存在的门牌号，收件人也确实住在那里，这是第三步；寄件人是你本人，不是替别人冒名寄的，这是第四步；最后，快递公司那天确实收了件、送到了，这才是第五步。前一步做对，不代表后一步也对。

软件和模型之间也隔着这样几道门。软件通常需要确定的字段：`vendor` 是哪家，`total` 是多少。模型默认擅长的却是生成自然语言：“我建议选 clay，含税大约七千五左右。”让两者协作，第一步往往是要求模型“只输出 JSON”。**JSON**（一种用花括号、键和值表示数据的文本格式）解决的是第一道门：程序终于能把这段文字读成数据了。但这里有几道独立的门，跨过前一道并不等于跨过后一道。

:::example 格式合法，事情却不对
`{"date":"2026-02-30"}` 是合法 JSON。如果 schema 只要求 `date` 是字符串，它也符合 schema。可是日期仍然不存在：二月没有三十号。

`{"recipient_id":"u_18"}` 可以通过严格的结构检查，却指向同名的另一位用户。

即使对象和权限都正确，发送服务也可能拒绝请求。字段再对，事情也没有办成。
:::

所以我们至少要区分这几层：**可解析、符合结构、事实与业务正确、经过授权、真实执行成功**。

## 五层正确性，一层一层过

先把五层逐个说清楚，每一层都配一个采购任务里的反例：

| 层 | 这一层问什么 | 采购任务里的反例 | 由谁检查 |
| --- | --- | --- | --- |
| 1 可解析 | 这段文字能读成 JSON 吗 | 输出在 `{"vendor":"clay","total":74` 处断掉了 | JSON 解析器 |
| 2 符合结构 | 字段、类型、枚举都对吗 | `"total":"7480"` 是字符串，不是整数 | schema 校验 |
| 3 事实与业务正确 | 值指向对的对象、满足业务规则吗 | 推荐 ink：结构完美，但交期 10-12 晚于 10-05 | 业务代码、验收器 |
| 4 经过授权 | 这个动作被允许吗 | 用户没有确认，却要下单 | 权限系统 |
| 5 真实执行成功 | 外部系统确实做成了吗 | 请求发出去了，供应商系统却拒绝了 | 外部系统返回的结果 |

前两层只看**形状**，程序自己就能判定。第三层开始要看**外部事实**：ink 的交期是多少、预算是多少，JSON 本身不知道，要拿去和数据对照。第四层看**谁允许**，第五层看**世界是否真的变了**。越往下，检查越依赖 JSON 之外的信息。

分层还有一个很实际的用处：**坏在哪一层，决定了该交给谁处理。**

- 第 1、2 层的错误，交回模型最合适。说清楚“`quantity` 应该是整数”，它下一轮通常就能改对，代价只是多一次调用。
- 第 3 层要看情况。选错了供应商，模型拿到“ink 交期晚于期限”的反馈可以改选；可如果是数据本身过期了，模型再怎么重试也没用，要去修数据（[第 1 讲](#lesson-1)那个缓存旧报价的例子）。
- 第 4 层不该交给模型“想办法”。没有授权就是没有授权，正确的出口是停下来问用户，而不是让模型换个说法再试一次。
- 第 5 层要看外部系统到底返回了什么。执行失败要如实报告；像上一讲的超时那样结果不明的，要先查清，不能猜。

把五层混成一句“输出不对”，这些不同的处理方式就无从谈起。

## JSON mode、结构化输出、function calling：各管一段

模型服务商提供了几种帮你跨过前几道门的功能，名字相近，管的范围不一样：

- **JSON mode**（JSON 模式）通常改善语法层面的可解析性，主要作用在第 1 层。它保证不了字段是不是你要的那几个：你要 `vendor`，它可能给你 `supplier`；你要整数 7480，它可能给你字符串 `"7,480 元"`。这些都是合法的 JSON。
- **结构化输出**（structured outputs）在支持的 schema 范围内，进一步约束字段、类型与枚举，作用到第 2 层。它怎样做到这一点，是[第 5 讲](#lesson-5)的主题。
- **function calling**（函数调用）给应用一个**动作请求**：模型说“我要调用哪个工具、参数是什么”，但它自己不执行。模型生成 `lookup_vendor` 调用之后，真正读取报价的仍是你的 Python 程序。应用执行，再把带对应调用 ID 的结果送回模型，下一轮模型才有机会利用这个事实。[来源：Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Function calling](https://developers.openai.com/api/docs/guides/function-calling)

三者都停在第 2 层以内。第 3 到第 5 层，没有任何一种输出格式能替你检查。

结构化输出和函数调用常被混为一谈，其实用途不同。在采购任务里，模型最后交出的推荐 `{"vendor":"clay","total":7480,"source":"quote-clay-v2","delivery":"2026-10-03"}` 是一份**给程序读的答案**，适合用结构化输出约束它的形状，再交给验收器检查第 3 层；而“帮我查 clay 的报价”是一个**要程序去做的动作**，适合用函数调用表达。前者说的是“结论长什么样”，后者说的是“下一步做什么”。

用函数调用的好处，是把**面向用户的语言**与**机器可执行的请求**分开。没有它，你得从“我认为可以查一下 clay 的报价”这样一句话里，用正则表达式把供应商名字抠出来，而模型换一种说法就可能抠不到。有了它，模型可以明确地请求：

```json
{
  "name": "lookup_vendor",
  "arguments": "{\"id\":\"clay\"}"
}
```

一次完整的函数调用是一个来回。下面这张图里，注意那个调用编号是怎么一路跟着走的：

调用编号看起来只是记账的细节，配错了却很难察觉。模型一次同时查三家时，harness 要送回三条 `tool` 消息。假如把编号配错，把 ink 的结果标成了查 clay 的那次调用，模型就会以为 clay 报价 6400 元、交期 10-12，进而得出“clay 来不及交货”这种完全错误的结论。整个过程中没有任何一步报错，JSON 全都合法，错的是第 3 层的事实。

## arguments 是一段字符串：先拼完整，再解析，再执行

仔细看上面那段 JSON：`arguments` 的值两边有引号，里面的引号全都带着反斜杠。这说明在常见的 Chat Completions 协议里，`arguments` 本身是一个 **JSON 字符串**，而不是一个已经解析好的对象。

所以要**解析两次**。第一次解析整条响应，SDK 通常替你做了；第二次，你要自己把 `arguments` 这段字符串解析成对象。第二次解析可能失败，因为这段字符串是模型写出来的，它可以是任何文字。需要先取得完整字符串，再解析一次。

**流式响应**（streaming，模型边生成边往回发，而不是全部生成完再一次性返回）让这件事更微妙。用户喜欢流式，因为文字一个个冒出来，不必干等；可是对工具调用来说，“先到的一半”没有任何用处。参数常被拆成多个片段先后到达，收到前半截 `{"vendor` 时不能执行任何操作。

并行调用又多了一层麻烦。模型可以在一次回复里同时发起好几个调用，[第 1 讲](#lesson-1)实验里那段录像就是这样：第一轮同时请求查询三家供应商。这时每个片段都标着它属于第几个调用（index），要按 index 分别拼接，不能把并行调用的片段混在一起。

写成代码只有几行（示意，片段是手写的）：

```python
import json

# 流式到达的参数片段：(调用的 index, 这一块文字)
chunks = [(0, '{"id":"cl'), (1, '{"id":"pa'), (0, 'ay"}'), (1, 'per"}')]

buffers = {}
for index, piece in chunks:
    buffers[index] = buffers.get(index, "") + piece  # 按 index 分开拼接

# 流结束以后，才逐个解析
for index in sorted(buffers):
    args = json.loads(buffers[index])
    print(index, args)  # 0 {'id': 'clay'}，然后 1 {'id': 'paper'}
```

## 换一个端点，保证就换一套

同一个 SDK、同样的写法，连到另一家服务、另一个接口地址，背后的规则可能就不一样了。接口兼容也有范围。

本课的 DeepSeek 示例（见[第 7 讲](#lesson-7)）使用官方的 `openai` Python SDK 作为客户端。依据当前文档（本课核对于 2026-09-30），情况是这样的：

| 用法 | 它保证什么 | 仍要自己做的 |
| --- | --- | --- |
| 普通 Chat Completions 的 JSON 模式：`response_format={"type":"json_object"}` | 输出是 JSON；这不等于任意 JSON Schema 保证 | 字段、类型、枚举全部本地检查；文档还要求提示里出现 “json” 字样并给出样例 |
| strict 函数模式：位于 beta 接口（`base_url` 设为 `https://api.deepseek.com/beta`），在函数定义里设 `"strict": true` | 在受支持的 schema 子集内约束参数 | 每个对象的属性都要列入 `required`，并设置 `additionalProperties: false`；字符串长度、数组长度这类约束不在支持范围内，仍需本地检查 |
| Responses 接口 | 有自己的结构化输出字段 | 不能把一个端点的限制复制到另一个端点 |

这张表最容易踩的坑是**无声的降级**。假设你在 strict 函数模式下开发，参数一直很规矩，于是代码里默认 `quantity` 一定是整数。后来为了省事，把同一套提示换到了普通 JSON 模式上。程序照样拿到 JSON，不报任何错，只是字段和类型不再有人担保；直到某一天 `quantity` 变成了字符串 `"1"`，而你的代码拿它去做了乘法。换端点时，要把它的保证范围重新读一遍，而不是只看“还能不能跑通”。

JSON 模式的文档还提醒了两件事：`max_tokens` 要设得合理，免得 JSON 在半路被截断；这个功能偶尔可能返回空内容。这两条正好是下一节要处理的情况。[来源：DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[Responses](https://api-docs.deepseek.com/api/create-response/)

:::pitfall 用上 strict 就把校验删掉
strict 模式让参数更少出格，这是真的。但它只在受支持的 schema 子集里生效，管不到长度限制，更管不到第 3 到第 5 层。换了端点或 provider，这层保证还可能整个消失。本地校验是你自己的代码，不随任何一方的文档改变。
:::

## 校验器是一道常设的边界

实际工程里，建议把本地 **validator**（校验器，执行前检查参数和输出的那段代码）看作恒定存在的一道边界。你可以逐步改善模型输出：写更清楚的工具描述，开 strict 模式，给出样例，让它更少撞上校验错误。但不要因为错误变少了，就删除校验。

道理和汽车的安全带一样：刹车越好，撞车的次数越少，但没有人因此把安全带拆掉。校验器的价值恰恰在那些罕见的时刻：模型换了版本，provider 改了行为，某个参数第一次出现了你没想到的值。而且校验器拦下的错误不会白白浪费，它作为观察交回模型（上一讲讲过怎样把错误写清楚），模型下一轮就能照着改。

第二件事是给“不知道”留位置。对于缺失的信息，允许模型明确返回“未知”或请求澄清，比强迫它填一个看似完整的值更可靠。

```json
}
```

注意 `required` 的含义：它要求的是“这个键必须出现”，不是“这个键必须有一个真实的值”。`total` 一定要写出来，但可以写 `null`，表示“我不知道”；`missing` 说明缺的是什么，没有缺口时就是空数组。这样写也满足前面 strict 模式“所有属性都列入 required”的要求。需要提醒的是，本课核对的 DeepSeek 文档在列出 strict 支持的类型时没有单独提到 `null`；这个写法能否直接用于某个端点的 strict 模式，要先对照该端点的文档或实测。这里只说明 `required` 的含义。

第三件事是分清“没有答案”和“答案错了”。一次调用结束时，模型不一定交回了一个完整的业务对象：它可能拒绝回答，可能生成到一半触达 token 上限，可能遇上网络错误，也可能返回空内容。这些情况应该走各自独立的状态分支，不能假设每次响应都包含一个完整的业务对象。拿到了响应时，判断的依据是响应里的**终止状态**，在 Chat Completions 里就是 `finish_reason` 字段，比如 `length` 表示达到了 token 上限；网络错误则根本没有响应可读，只能按错误处理。

:::recap 小结
- “只输出 JSON”只解决可解析；之后还有符合结构、事实与业务正确、经过授权、真实执行成功四层，前一层通过不代表后一层通过。
- JSON mode 主要改善可解析性，结构化输出在支持的 schema 范围内约束字段、类型与枚举，function calling 给出动作请求；真正执行和把结果带着调用 ID 送回的，始终是你的程序。
- 在常见的 Chat Completions 协议里，`arguments` 是一段 JSON 字符串：流式时按 index 分别拼接，拼完整再解析，校验通过才执行。
- 各个端点和 provider 的保证范围不同，strict 模式也只覆盖受支持的 schema 子集；本地校验要一直保留。
- 给“未知”留出正式的表示；拒绝、截断、网络错误和空输出各走独立的状态分支（有响应时先读它的终止状态），不能假设每次响应都有完整的业务对象。
:::
