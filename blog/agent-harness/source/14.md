## 同一件事，做到第五遍

新同事第一次做 CSV 数据质检，你花半小时讲步骤。第二次他忘了最后核对行数，你又讲一遍。第三次换了个人，你再从头讲。到第五次，你终于把步骤写成一页清单，附上一个检查脚本，放进共享盘：以后谁做这件事，先读清单，再跑脚本。

agent 也会遇到同样的事。当你重复执行同一种任务，就会发现一些步骤每次都要重新解释。比如 CSV 数据质检：先确认编码与列名，检查字段类型，统计缺失、重复和越界，输出报告，最后核对行数是否对得上。每次都在提示里重写一遍，既费篇幅，又容易这次漏一步、下次漏另一步。

[第 12 讲](#lesson-12) 区分过几种记忆内容：**经历记忆**记录某一次发生过的事，**程序性记忆**提炼可以重复的做法。本讲标题里的“经验记忆”，关心的正是从前者走到后者的那一步：把在一次次经历里反复验证过的做法，整理成下次可以直接拿来用的方法。

把这些程序性知识整理成可发现、按需加载的资源，就是 **skill** 的一种典型用途。可以把 skill 想成一份“带工具箱的操作手册”：写明什么时候用、怎么做、做到什么程度算完成，还可以附上脚本和参考资料。

并不是每条经历都值得写成方法。值得写进 skill 的做法，通常有这样几个特征：同类任务反复出现；步骤相对稳定，不会每次都大改；有明确的完成标准；至少有一部分能用确定的检查来验证。反过来，一次性的偏好（“这次报告用蓝色标题”）、只出现过一回的巧合、还没验证过的猜测，都更适合留在经历记录里，或者干脆不记。把它们写进 skill，等于把一次的偶然变成了以后每一次的默认。

## 一个 skill 长什么样

Agent Skills 开放规范采用目录与 `SKILL.md` 组织，可附带脚本、参考资料和资源文件。它强调逐步加载：先让 agent 看到名称与描述，相关时再读正文，更深入时才加载脚本或参考。这种设计减少了把所有流程一次塞进上下文的必要性，也给知识维护提供了独立单位。[来源：Agent Skills Specification](https://agentskills.io/specification)

一个简化的 CSV 质检 skill 可以这样组织：

```text
csv-quality/
  SKILL.md
  scripts/
    validate.py
  references/
    domain-rules.md
  assets/
    report-template.md
```

每个文件各管一件事：

| 文件 | 负责什么 | 什么时候用到 |
| --- | --- | --- |
| `SKILL.md` 开头的 name 与 description | 让 agent 知道有这个 skill，以及什么任务该用它 | 一直在，相当于目录里的一行 |
| `SKILL.md` 正文 | 何时使用、需要什么输入、步骤与完成标准 | 任务和描述对上时才读 |
| `scripts/validate.py` | 实现确定性检查，每次以同样方式执行 | 执行到那一步时运行 |
| `references/domain-rules.md` | 解释某列的允许范围与例外 | 需要判断某个值是否合规时才读 |
| `assets/report-template.md` | 让结果保持稳定的结构 | 写报告时使用 |

把所有说明堆进一个巨大正文虽然也能工作，却会失去按需加载的好处。

正文可以从这样的内容开始：

```markdown
---
name: csv-quality
description: 检查 CSV 的字段、缺失、重复和范围，并生成可核验报告。用于需要审计结果的 CSV 质检。
---

# CSV 数据质检

适用于需要审计结果的数据检查。保留原始文件，不覆盖输入。

1. 确认输入文件、编码、分隔符与预期列。
2. 读取领域规则；缺少关键规则时先提出具体问题。
3. 在受控环境运行 scripts/validate.py，记录输入文件摘要。
4. 区分实际检测结果与规则缺失导致的未知项目。
5. 输出总行数、各类问题数、少量样例及可访问的完整结果。
6. 核对报告与本次输入版本一致后再交付。
```

逐段看它在做什么。开头两行 `---` 之间的部分是元数据，其中的 `description` 就是 agent 最先看到的那一句，它写得准不准，决定了该用的时候会不会被想起来。“保留原始文件，不覆盖输入”是一条边界，防止质检本身破坏数据。第 2 步和第 4 步处理的是“不知道”：规则缺失时先问，而不是自己编一条规则；报告里把检测结果和未知项分开，读报告的人才知道哪些结论有依据。第 6 步是交付前的自查，它让报告和这一次的输入对应起来，而不是和上一次的文件对应。

## 按需加载：目录常驻，正文和脚本用到才读

工具间的墙上挂着一排工具，每把都贴着标签；说明书收在抽屉里，用到哪把才拿出哪本。没有人每天早上把所有说明书从头读一遍。

skill 的加载也是这样分层的。下图跟着一次质检任务，看每一层内容在什么时候进入上下文。

分层买到了两样东西。一是篇幅：不相关的 skill 只占目录里的一行。二是可能干扰更少：[第 10 讲](#lesson-10) 讲过，上下文里放着不相关、又长得很像的材料，可能让模型更难用上真正需要的那一段；五本说明书同时摊开，比只摊开一本更容易看串行。

它也有代价。目录层每次调用都在，skill 越多，目录越长；描述写得含糊，该用的时候没被想起来，或者不该用的时候被读了进来，后面几层写得再好也白费。分层还多了一步决策：模型得先决定去读正文，这一步本身可能出错。

所以 `description` 那一句值得认真写。比较两种写法：“数据工具”几乎什么都没说，任何和数据沾边的任务都可能把它读进来，真正的质检任务反而未必想到它；“检查 CSV 的字段、缺失、重复和范围，并生成可核验报告。用于需要审计结果的 CSV 质检。”说清了对象（CSV）、动作（检查哪几类问题）、产出（可核验的报告）和适用场景，模型拿任务去对照时有据可依。一个实用的写法是：它处理什么输入、做哪几件事、交出什么结果，以及什么时候该用它。

“能保存”和“每次都加载”是两个问题。Claude Code 的 memory 文档区分了用户维护的指令与自动积累的记忆，并对自动加载的内容设定了预算。[来源：Claude Code Memory](https://code.claude.com/docs/en/memory) 保存下来的东西可以很多，每次调用都放进上下文的东西必须少而准。

下面的实验把刚才的过程简化成三层。点三次“下一步”：第一次，上下文里只有技能目录，五个 skill 各一行；第二次，任务“给 orders.csv 做质检”到来，目录里 csv-qa（相当于上面的 csv-quality）那一行变色，它的 SKILL.md 被读进来；第三次，脚本运行，第三格里只出现三行输出。每一步都看下方两根条：“按需加载”累计用了多少 token，“全部塞进去”（五个 skill 的说明和脚本一开始就全部放进上下文）又是多少。条上的数字是为了对比量级做的估计，实际大小取决于 skill 的内容和模型的分词方式。留意第三步：脚本的代码一行也没有进入上下文，进来的只有它的输出。

::lab

## 分清四个角色：tool、skill、harness、模型

skill 容易和 tool（工具）混为一谈，因为两者都在“扩展 agent 能做的事”。其实它们回答的是不同的问题：

| 角色 | 决定什么 | 在 CSV 质检里的样子 |
| --- | --- | --- |
| tool | **能够**做什么：读取文件、运行脚本、保存报告 | 注册好的读文件、运行脚本、保存报告等工具 |
| skill | **何时**使用这些能力，以及**如何组合** | csv-quality 的正文：先确认列，再跑脚本，再写报告 |
| harness | 如何装载、执行、授权和记录 | 把目录放进上下文，在沙箱里运行脚本，写 trace |
| 模型 | 理解任务、选择过程 | 判断这项任务该用 csv-quality，读懂输出，写出报告 |

用一次运行把四个角色串起来：模型读到任务，从目录里认出 csv-quality，这是模型在选择；它读进来的正文告诉它先确认列、再跑脚本，这是 skill 在指导；它提出“运行 validate.py”，harness 检查这个调用是否在授权范围内、在沙箱里执行、把输出和耗时记进 trace，这是 harness 在把关；真正读文件、跑检查的，是注册好的工具和脚本。四者缺一个，这次质检都做不成，而且缺的是哪一个，出错的样子各不相同。

从这张表还可以直接推出几件 skill **做不到**的事。增加一个 `SKILL.md` 不会改变模型权重，也不会凭空安装脚本依赖或创建不存在的工具。正文里写着“用 pandas 读取文件”，而运行环境里没有装 pandas，脚本照样会失败。正文里提到一个从未注册的工具，模型照着去调用，只会被 harness 按工具契约拒绝（[第 3 讲](#lesson-3) 讲过工具契约）。

:::pitfall 把“装了 skill”说成“模型学会了”
skill 是放在模型外面的文字和代码。把它拿走，这项“能力”就消失了，模型本身什么也没变。这不是缺点：正因为它在外面，人才能读它、审它、改它、回滚它。但描述效果时要准确，说“这个 agent 配置了 csv-quality，在某批任务上漏步更少”，而不是“模型学会了数据质检”。
:::

## skill 有没有用，要拆开来测

员工手册写得再厚，没人翻开就没用；翻开了但步骤含糊，照样出错；步骤清楚但要用的软件没装，还是做不成。

因此 skill 的效果需要拆开评估。触发是否准确？正文是否足够具体？脚本是否能在当前环境运行？遇到缺失的规则，能否停止猜测？输出是否经过验收？下图跟着一个 skill 走完这五关。

:::example 一次同任务对照怎么做
准备一批 CSV 样本，其中一部分埋了已知问题：错误编码、重复行、越界值、缺失的领域规则。同一个模型、同样的预算，先不配 skill 跑一遍，再配上 csv-quality 跑一遍。每次记录：skill 有没有被触发、漏掉了哪些检查、有没有把猜测当结论、用了多少 token 和时间。

再混进一些**不该**触发它的任务，比如“把这个 CSV 转成图表”，看它会不会被误读进来。只测“该用的时候好不好用”，会漏掉“不该用的时候添不添乱”。
:::

## 维护与供应链安全

skill 写好之后还要维护。长期维护时，给 skill 指明适用版本和依赖；当 API 改变或流程不再有效时更新它。比如订单导出的格式改了一列名字，validate.py 还按旧列名检查，就会把每一行都报成缺失。

实践中，可以在 skill 里写明几件事：它适用于哪个版本的输入格式或接口，脚本依赖哪些库，最后一次用对照任务验证是什么时候，由谁负责修改。某次运行因为 skill 的步骤出了错，要修的是 skill 本身，而不只是那一次的结果；否则同样的错误会在下一次任务里原样出现。

安全上，导入 skill 与导入代码、指令供应链类似。所谓**供应链**，是指你的系统依赖的、来自别处的东西：第三方库、别人写的脚本、别人写的说明。skill 正文中的命令可能有副作用，脚本可能连接外部服务，参考链接也可能不可信。

## 回头看：从一个动作到一套方法

到这里，我们得到一条完整的连接：模型依据上下文提出动作，harness 让动作受控执行，工具提供可核验的观察；日志保存过程，检查点恢复状态，检索找回证据，skill 复用可靠的方法。

后续再讨论验证、多代理或更复杂的自治时，这条基础链始终存在。任何新能力都应该回答同样几个问题：它增加了什么信息，改变了哪项决定，如何证明执行结果，以及出错后怎样继续。

:::recap 小结
- 反复执行的任务里，经过多次经历验证的做法可以提炼成程序性知识；skill 是把它整理成可发现、按需加载的资源的一种典型方式。
- 按 Agent Skills 规范，一个 skill 是一个带 `SKILL.md` 的目录，可附带脚本、参考资料和资源文件；在本讲的例子里，`SKILL.md` 写何时使用、输入、步骤与完成标准，脚本做确定性检查。
- 分层加载让目录常驻、正文和脚本用到才读，省篇幅，也可能减少干扰；代价是目录常驻的开销，以及“描述不准就不被想起”的风险。“能保存”和“每次都加载”是两个问题。
- tool 决定能做什么，skill 指导何时用、怎样组合，harness 负责装载、执行、授权和记录，模型理解任务并选择过程；加一个 `SKILL.md` 不改变权重，也不凭空安装依赖或创建工具。
- skill 的效果要拆成触发、正文、脚本、缺规则时的行为和验收五关来测，并用同任务对照证明；导入 skill 与引入代码、指令供应链类似，需要审查，而且它不能靠自己的正文给自己授予额外权限。
:::
