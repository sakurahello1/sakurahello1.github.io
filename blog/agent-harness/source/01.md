:::goal 读完这一讲，你能回答
- ReAct 里真正值钱的东西是什么：是那三个英文词，还是别的？
- 一圈循环里，**谁**决定、**谁**执行、**谁**把结果送回去？
- 为什么“多看一步”有时候能救命，有时候只是白花钱？
- 循环空转时，harness 靠什么发现，又不能怎么“治”？
:::

## 先破一个误会：ReAct 不是一种输出格式

很多教程一上来就画一张三行的图：Thought，Action，Observation，然后告诉你“模型就是这样一行一行输出的”。图没有错，但它容易让人把注意力放在**格式**上：似乎只要让模型按这三个词写字，就有了 agent。

真正起作用的是格式背后的**信息关系**：模型每做一次行动，就从外部世界拿回一点它此前不知道的事实；这些事实又会改变它下一步怎么走。行动带来新证据，新证据改变决策，这条反馈链才是重点。ReAct 原论文研究的就是推理与行动交错进行的做法，在问答、事实核查和交互环境里做了实验。需要注意，论文的数字属于当时的模型和任务，不能直接搬来推断现代 coding agent 一定有多少收益。[来源：ReAct](https://arxiv.org/abs/2210.03629)

打个比方。闭卷考试时，你只能凭脑子里已有的东西作答；开卷考试时，你可以先翻资料，翻到的内容会改变你接下来写什么。ReAct 就是让模型从“闭卷”变成“开卷”，而且**每翻一页都能根据看到的内容决定翻哪一页**。

```figure
{"kind":"flow","title":"一圈 ReAct 循环里发生了什么","dek":"四条箭头连成一圈：读上下文 → 模型决定 → harness 执行 → 结果写回。","nodes":{
```

## 用采购任务走一遍

回到我们贯穿全课的采购任务：含税预算 7600 元，10 月 5 日前必须交付，三家供应商 clay、ink、paper 各有各的报价和交期。系统一开始只知道预算和期限，**不知道任何一家的报价**。

```figure
{"kind":"sequence","title":"采购任务的前几步，谁在跟谁说话（示意，简化为一家一家地查）","actors":[["用户",""],["harness","你的程序"],["模型",""],["工具","供应商数据"]],
 "msgs":[

  ["harness","模型","目标 + 工具列表",{"say":"harness 把任务和“你可以用哪些工具”一起交给模型。模型此刻还不知道任何报价。"}],
  ["模型","harness","调用 lookup_vendor",{"say":"模型没有编报价，而是提出请求：“帮我查 clay。”"}],
  ["harness","工具","lookup_vendor(clay)",{"say":"harness 校验参数没问题，才去调用真正的工具。"}],
  ["工具","harness","6800 元 · 10-03",{"dashed":true,"say":"工具返回事实：含 quote-clay-v2 这个来源编号，方便以后核对。"}],

```

这里有三处值得记住：

1. **模型从头到尾没有执行任何东西。** 它每次只是提出请求，执行者始终是 harness。
2. **报价来自工具，不是模型的记忆。** 所以答案里可以带上来源编号，事后能对账。
3. **第二步的决定依赖第一步的结果。** 如果 clay 的报价已经超预算，模型就不会去算它的总价，而是改查下一家。这种“看完再决定”，就是循环带来的价值。

## 有循环，不等于有反馈

看到一个 while 循环里调用了工具，就说它是 ReAct，其实太早了。循环只是**结构**；反馈是结构上跑着的**信息**有没有真正改变决策。两者可以脱节。

举一个虚构的例子。假设 harness 缓存了一条 clay 的旧记录：交期 2026-10-09，是很久以前查到的。这一圈模型重新调用 `lookup_vendor`，拿到的是 quote-clay-v2：交期 2026-10-03。新记录明明把旧记录更正了。如果模型在后面的推理里仍然引用 10-09，那么循环转了、工具调了、结果也写回了上下文，**反馈机制却没有发挥作用**：新事实进了上下文，没有进入决策。

```figure
{"kind":"compare","title":"循环都在转，反馈接没接上","cols":[
  {"title":"反馈没接上","tone":"bad","items":["缓存里有一条旧记录：clay 交期 10-09（虚构）","重新查询，拿到 quote-clay-v2：交期 10-03","决策仍然引用 10-09，给出“交期偏晚，不推荐”","每一步都执行了，结论却建立在过期信息上"]},
  {"title":"反馈接上了","tone":"ok","items":["同样先看到旧记录 10-09","重新查询，拿到 quote-clay-v2：交期 10-03","决策以新记录为准，并标明替换了哪条旧信息","结论建立在最新、带来源的事实上"]}],
 "steps":[
  {"hl":[[0,0],[1,0]],"say":"两边起点相同：上下文里有一条较早的记录。"},
  {"hl":[[0,1],[1,1]],"say":"两边也都做了同样的动作：重新调用工具，拿到更正后的新记录。到这里，两个循环在形式上完全一样。"},
  {"hl":[[0,2],[1,2]],"say":"差别出现在决策：左边仍然沿用旧记录，右边让新记录取代旧记录。"},
  {"hl":[[0,3],[1,3]],"say":"结论的质量，取决于这最后一步有没有接上。只看“调用了几次工具”，分不出这两种运行。"}]}
```

这也是为什么验收不能只看过程有多“勤奋”。工具调用得再多，也要去核对：**最终答案里用到的每个事实，是不是来自最新的观察**。后面讲验证的几讲会回到这件事。

### 一条好的观察，应该带什么

要让新旧信息能被分辨，观察本身就得带足够的元数据。一个采购查询返回的结果，至少应该有这几样：

| 观察里的内容 | 为什么需要 |
| --- | --- |
| 返回的事实（价格、交期、税率） | 决策直接依据它 |
| 来源编号，比如 `quote-clay-v2` | 事后可以对账；也能看出这条和旧版本不是同一份 |
| 取得时间或资源版本 | 判断它会不会已经过期；空转检测也要用到版本（见下文） |
| 是否成功，以及错误信息 | 失败同样是观察：让模型看见“被拒绝”，它才可能换一条路 |

:::pitfall 把工具结果当成“事实”直接塞回去
工具返回的内容也可能过期、出错，甚至在后面的课里你会看到，它也可能被别人动过手脚。写回上下文时，带上来源和版本，比只写数值更值得。
:::

## Thought 到底要不要打印出来

上面的教学轨迹可以这样写出来：

```text
目标：修复启动失败
动作摘要：先定位真实报错
工具：run_tests(scope="startup")
观察：ModuleNotFoundError: settings
动作摘要：核对仓库中的模块位置
工具：read_file(path="app/main.py")
观察：文件使用 import settings，模块位于 app/settings.py
工具：apply_patch(受控补丁)
观察：补丁已应用
工具：run_tests(scope="startup")
观察：相关测试通过
结论：修改说明、测试结果、尚未覆盖的范围
```

这里的“动作摘要”，是给**人**看的简短理由，用来帮读者理解这条轨迹。它不代表我们观察到了模型真实的内部思考，ReAct 也没有要求把所有内部推理都显示在界面上。对执行系统来说，往往最有用、也便于事后核对的信息是：动作名称、通过校验的参数、工具结果、时间、资源版本，以及最后为什么停止。

:::pitfall 别把“写出来的理由”当成证据
模型写一段头头是道的理由，并不能证明那段理由就是它决定动作的真实原因。要判断一次运行对不对，看的是**工具返回了什么、验收器查到了什么**，而不是模型自己怎么解释。
:::

## 循环会空转，harness 要能发现

循环有一个天然的风险：模型反复做没有新信息的事。比如连续三次读同一个文件，每次得到一模一样的内容，却不肯换个思路。

```figure

  "ver":{"at":[3,0],"text":"资源版本","sub":"文件或状态变过吗","icon":"clock"},
  "go":{"at":[1.5,1.7],"text":"正常继续","icon":"check","w":150},
  "warn":{"at":[3,1.7],"text":"提醒或停止","sub":"无进展重复","icon":"warn"}},
 "edges":[["call","sig"],["sig","ver","相同"],["sig","go","不同",{"bend":-14}],["ver","go","有变化",{"bend":-14}],["ver","warn","没变"]],
 "steps":[
  {"on":["call","sig"],"edges":["call>sig"],"say":"每次调用前，harness 先把“工具名 + 参数”当成一个签名，和最近几次比较。"},
  {"on":["sig","go"],"edges":["sig>go"],"say":"签名不同，说明这是一个新动作，放行。"},
  {"on":["sig","ver"],"edges":["sig>ver"],"say":"签名相同，还不能马上判定空转：同一个文件，中间可能已经被别的操作改过。"},
  {"on":["ver","go"],"edges":["ver>go"],"say":"资源版本变了，重复读取是合理的，放行。"},
```

所以**不能简单地“禁止重复读文件”**：修改文件之后再读一次，是完全正常的验证。重复检测要结合资源版本和动作的副作用来看。重复也不一定是模型的问题，也可能是工具描述含糊，模型根本没读懂结果。

## 什么时候不用完整循环

循环不是免费的。每多一圈，就多一次模型调用、一次工具延迟，上下文也更长。

| 场景 | 要不要完整循环 | 原因 |
| --- | --- | --- |
| 把一小段已给出的文字改写 | 不用，一次调用就够 | 环境里没有新事实可拿，多转几圈只是浪费 |
| 查三家报价再比较 | 要 | 每一次查询的结果都会影响下一步查谁、算什么 |
| 修复一个测试失败 | 要 | 不看报错就动手是猜，改完不重跑无法确认 |
| 结果必须经过验证 | 要，且要有独立验证 | 见后面“验证”部分几讲 |

一句话：**下一次观察有机会改变决策，或者执行结果必须经过验证，循环才值得。**

## 动手：让一个真实模型跑一圈

下面的剧场里，你可以“播放录像”，看一次真实的运行：左边是同一个循环的另一种画法（多了目标、调用校验和验收器三个节点，“观察”画成了从工具执行回到上下文的那条边，后面几讲会解释），右边是消息流。也可以点右上角连接你自己的模型，现场再跑一次。**留意每次工具调用之前，模型手里到底有哪些信息。**

::lab

:::recap 小结
- ReAct 的价值不在 Thought / Action / Observation 三个词，而在**行动带来新证据、新证据改变决策**这条反馈链。
- 一圈循环里：模型只负责提出下一步，harness 负责校验与执行，结果再写回上下文。
- “动作摘要”是给人看的解释，不是模型内部思考的记录；更可靠的依据是工具结果和验收结果。
- 空转要靠“调用签名 + 资源版本”联合判断，不能简单禁止重复。
- 循环有成本：只有下一次观察可能改变决策，或结果必须验证时，才值得完整循环。
:::
