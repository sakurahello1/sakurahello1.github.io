## 验证不是免费的

如果验证无限便宜，最简单的建议就是多跑几遍、找更多模型、多检查一些。可现实里每一道检查都要花钱、花时间。餐馆可以让每道菜出锅前由三位厨师各尝一口，菜会更稳，但上菜更慢、人手更贵。真实的系统必须在成本、等待时间和质量之间做选择。

一个能完成任务却经常超预算的 agent，不是成熟的产品；一个价格很低却把错误留给用户发现的 agent，也可能只是把成本转移到了别人身上。用户花在核对和返工上的时间，账单上看不到，却是真实的成本。

前面各讲介绍每个机制时，都说过它的代价：多一圈循环多一次调用，多一个 worker 多一份协调，多一道审批多一次等待。这一讲把这些代价放到一起：怎样记账，怎样算成本，怎样看延迟，怎样重试，怎样退场，最后用一张验收清单把整个系统收拢。

## 总消耗和等待时间，是两本账

先分清两个经常被混为一谈的量。**墙钟时间**是真实世界里钟表走过的时间，比如从用户发出请求到拿到可用结果；**总消耗**是整个系统一共用掉的资源，包括所有模型调用的 token、所有工具和机器的运行时间。

四个 worker 并行运行，可能把用户等待从四分钟降到一分钟，却使用了更多的总 token；增加独立验证，可能提高成功率，也延长了**关键路径**（必须一步接一步完成的那串步骤中最长的一条，它决定了最快多久能完成）。

### 账本要分几栏

一本有用的预算账本，至少要把下面几栏分开记：

| 账目 | 为什么要单列 |
| --- | --- |
| 模型输入与输出 | 很多服务对两者分别计价，而且两者的增长原因不同：输入随上下文变长，输出随回答变长 |
| 缓存与非缓存 | 命中缓存的部分可能按不同价格计费，混在一起就看不出缓存省了多少 |
| 工具费用 | 搜索、数据库、第三方 API 各有各的账单 |
| 计算环境时间 | 沙箱、容器开着就在花钱，不管里面有没有在干活 |
| 重试 | 单列出来，才知道失败浪费了多少 |
| 验证 | 验收和审阅的消耗，它是固定开销，不该为了省钱被砍掉 |
| 人工等待 | 审批、修复花掉的人的时间，不在 API 账单上，但真实存在 |

费用计算要使用实际账单或当时适用的价格，不能把不同模型的一千 token 当成同价。对无法观察的内部推理计算，应说明可用的代理指标和盲区。即便 API 报告了推理 token，它与硬件时间或能源消耗之间，也不存在一个可以随意假设的固定换算。

引用别人的数字时尤其要小心。Anthropic 介绍其生产研究系统的文章给出过一个容易被误引的经验比较：普通 agent 约使用一般聊天四倍的 token，多 agent 约为一般聊天的十五倍。注意两个倍数的参照物都是“一般聊天”：这不是“多 agent 比单 agent 贵十五倍”，也不是适用于所有工作负载的常数。这类工程报告适合提醒你重视预算，不适合直接替代你自己的负载测试。[来源：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)


写成代码，就是分子把各项成本加起来，分母只数通过验收的运行：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class RunCost:
    model: float     # 按实际账单或当时价格算出的模型费用
    tools: float     # 搜索、数据库等工具费用
    compute: float   # 沙箱或容器运行时间折算的费用
    human: float     # 人工审批、修复的时间折算
    succeeded: bool  # 由验收合同判定，不由 agent 自报

def cost_per_success(runs: list[RunCost]) -> float | None:
    total = sum(r.model + r.tools + r.compute + r.human for r in runs)
    wins = sum(1 for r in runs if r.succeeded)
    return total / wins if wins else None  # 一次都没成功时没有这个数，而不是 0
```

这个算法有两个要守住的地方。

第一，**成功的定义必须由验收合同确定**，否则系统只需降低标准，就能表面上提高成本效率。比如一份只检查“含税不超过 7600 元、交期不晚于 10 月 5 日”的简化验收，把交期这一项拿掉，ink（含税 7040 元）也就“合格”了，而且它最便宜，每个合格结果的成本立刻下降；可用户拿到的，是一台 10 月 12 日才到的电脑（验收合同见[第 16 讲](#lesson-16)）。

第二，**失败损失要单独报告**，避免把重大事故藏进平均成本里。假设一千次运行里有一次重复下单，多付了 7480 元；摊到每次运行上只有 7.48 元，混在平均数里毫不起眼，可它是一次真实的事故，需要单独追查。

## 延迟看分布，不看平均

延迟也不能只看平均值。先认识两个常用的数：**p50** 是中位数，一半请求比它快；**p95** 表示 95% 的请求比它快，剩下 5% 更慢。p95 描述的是“倒霉的那部分用户”会等多久。

平均两秒的工具，如果少数请求卡住一分钟，就会支配复杂流程的尾部体验。设想一个工具，一百次调用里 94 次一秒左右返回，6 次卡了 60 秒（示意数字）：平均约 4.5 秒，p50 是 1 秒，p95 却是 60 秒。更麻烦的是，一个流程如果要**依次**调用它十次，至少碰上一次卡顿的概率约为 1 − 0.94¹⁰ ≈ 46%。单次调用的尾巴，到了多步流程里就变成了常态。

并行任务要等最慢的分支，这个问题在那里尤其明显：

## 省钱从哪里下手，重试怎样分类

优化应该从**重复与无效的工作**开始，而不是先砍验证：

- 减少重复读取相同的资料；
- 缓存版本明确的静态结果，比如 `quote-clay-v2` 这份报价，版本号不变，内容就不变；
- 给 worker 提供足够但不过量的上下文；
- 避免每一轮都重新传输整份历史；
- 把廉价的确定性检查放在昂贵的模型审阅之前。JSON 能不能解析、总价是不是 7480，一行代码就能查，没必要先请一个模型来读。

缓存必须考虑新鲜度、用户权限和数据范围。用过期的结果回答当前状态，或者把一位用户的数据缓存给另一位用户，会把性能优化变成正确性问题或隐私问题。

另一个大头是重试。重试策略需要按失败类型设计：

| 失败类型 | 该怎么做 | 无差别重试的后果 |
| --- | --- | --- |
| 短暂的网络故障 | 退避重试：等一会儿再试，每次间隔拉长 | 这是少数适合直接重试的情况 |
| 参数错误 | 先修正参数 | 同样的错参数，重试多少次都是错 |
| 权限被拒绝 | 申请授权，或者停止 | 反复撞门，甚至诱导 agent 去找别的通道 |
| 验收失败 | 先拿到新的诊断证据 | 不看原因地重做，很可能重复同一个错误 |
| 已执行但响应丢失 | 先查询状态，而不是立即重复 | 重复发送、重复下单、重复扣款 |

最后一行最危险。下单请求发出去以后超时了，你并不知道供应商那边有没有创建订单。立刻再发一次，如果第一次其实成功了，就有了两张订单。无差别重试看似提高了韧性，实际上可能产生重复发送、额外扣费与更多的状态混乱。

下面的实验就是[第 29 讲](#lesson-29)那次假保存的 trace，这次换一个问题来看：要不要重试，凭什么决定？把时间拖到 300 ms：网络轨道是 HTTP 500，数据库还是旧值。这两条放在一起，说明这一次写入没有生效，再保存一次风险较小（前提是保存这个动作本身可以重复执行）。再设想另一种情况：请求超时、没有响应，数据库却已经是新值，那就属于“已执行但响应丢失”，该做的是查状态，而不是再保存一次。如果只看 agent 那一行的“已保存”，这两种情况你一种也分不出来，甚至不会想到需要重试；成本账上，这次运行还会被错记成一次成功交付。

::lab

## 预算用完时，诚实地退场

预算总有用完的时候。系统需要一种诚实的退场方式：保存检查点，列出已完成且已验证的内容，指出尚未满足的条件，并说明继续下去需要哪些资源。

:::example 采购任务的预算在中途用完
预算在查完 clay 和 ink 之后用完了，paper 还没查。诚实的退场报告写的是：终态为未完成（incomplete）；已验证 clay 含税 7480 元、10 月 3 日到货，满足预算和期限，依据是 quote-clay-v2；ink 10 月 12 日到货，不满足期限；paper 尚未查询，所以还不能断定 clay 是三家里的最佳选择；继续需要再查询一次 paper 的报价。它不应该写成“推荐 clay，已完成”。
:::

:::pitfall 为了不超预算，先砍验证
预算不足，不会把“未知”变成“通过”。同样，给 agent 一个预算上限，也不能让它为了赶在上限前完成而偷偷跳过安全门和验证步骤。这些步骤应该属于**不可省略的固定开销**：分配预算时先扣掉，剩下的才是可以灵活使用的部分。
:::

## 把目标写成约束，把系统放进一张验收清单

最后，把优化目标写成一组可以检查的约束。例如：“在允许的资源内完成，关键验收全部通过，费用不超过上限，无法满足时返回具体的阻碍。”不要只告诉系统“尽可能快、尽可能好”，再让它自己决定可以牺牲什么，因为它往往最先牺牲的，恰恰是那些看不见的东西：验证、审批、证据。

可靠性、安全、成本与延迟，不是四份互不相关的报表，它们共同决定一个 agent 系统是否值得信任、能否真正投入使用。下图把一次采购运行放进这张验收清单，从上往下逐项核对：

| 可追溯 | 失败时能定位到哪一层，回放不会产生副作用吗？ | [第 29 讲](#lesson-29) |
| 成本 | 每个成功交付花多少，比较时预算对等吗？ | [第 25 讲](#lesson-25)、本讲 |
| 延迟与退场 | p95 可接受吗？预算不够时，终态如实吗？ | 本讲 |

到这里，harness 的轮廓已经完整：它组织信息、分配计算、控制权限、收集证据、管理状态，并在不确定性无法被合理消除时停止。模型提供推理和生成能力，harness 把这种能力放进一个能够交付、能够审查、能够恢复的流程。

回到[第 1 讲](#lesson-1)的那个问题：模型说做了，系统怎样知道真做了？答案不在模型的措辞里，而在这张清单里。工程成熟度不取决于你画了多少个 agent，而取决于系统能否说明自己做了什么、凭什么判断做对了、还剩什么风险，以及为什么现在应该继续或者停下。

:::recap 小结
- 验证不是免费的：真实系统要在成本、等待时间和质量之间取舍；把错误留给用户，只是把成本转移了出去。
- 墙钟时间和总消耗是两本账：并行可能缩短等待却增加总 token，独立验证可能提高成功率却拉长关键路径；账本要分开记模型输入输出、缓存、工具、计算环境、重试、验证和人工。
- 成本按成功交付归一化，成功由验收合同定义，失败损失单独报告；引用“四倍、十五倍”这类经验数字时，要守住它的参照物和适用范围。
- 延迟看 p50、p95、超时比例和关键路径；可以先交付已验证的部分，但不能提前宣布成功。重试按失败类型区分，已执行但响应丢失的动作要先查状态。
- 预算耗尽时如实退场，安全门和验证是不可省略的固定开销；目标要写成可检查的约束组合，答案正确只是验收清单的第一行。
:::
