如果验证无限便宜，最简单的建议是多跑几遍、找更多模型、多检查一些。但真实系统必须在成本、等待时间和质量之间做选择。一个能完成任务却经常超预算的 agent，不是成熟产品；一个价格很低却把错误留给用户发现的 agent，也可能只是把成本转移到了别人身上。

首先分清总消耗与等待时间。四个 worker 并行运行，可能把用户等待从四分钟降到一分钟，却使用了更多总 token；增加独立验证，可能提高成功率，也延长关键路径。用户体验关心从请求到可用结果的墙钟时间，运营关心每次运行和每个成功任务的成本，两者不能混成一个模糊的“效率”。

预算账本应至少区分模型输入与输出、缓存与非缓存、工具费用、计算环境时间、重试、验证以及人工等待。费用计算要使用实际账单或当时适用的价格，不能把不同模型的一千 token 当成同价。对无法观察的内部推理计算，应说明可用代理和盲区。即便 API 报告了推理 token，它与硬件时间或能源消耗之间也不存在一个可以随意假设的固定换算。

Anthropic 的生产研究系统文章给出过一个容易被误引的经验比较：普通 agent 约使用一般聊天四倍 token，多 agent 约为一般聊天十五倍。这不是“多 agent 比单 agent 贵十五倍”，也不是适用于所有工作负载的常数。该类工程报告适合提示你重视预算，不适合直接替代自己的负载测试。[来源：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

衡量成本时，最好同时看单次尝试和成功交付。一个方法每次便宜，但经常需要重试或人工修复，最终每个合格结果可能更贵。可以把模型、工具和人工处理成本相加，再按成功交付数量归一化；同时单独报告失败损失，避免把重大事故隐藏在平均成本里。成功的定义仍然必须由验收合同确定，否则系统只需降低标准，就能表面上提高成本效率。

延迟也要看分布。平均两秒的工具，如果少数请求卡住一分钟，会支配复杂流程的尾部体验。并行任务等待最慢分支时，这种问题尤其明显。记录 p50、p95、超时比例和关键路径，比只展示平均值更有帮助。但不能为了更好看的延迟，在慢任务尚未结束时提前宣布成功；可以先交付已经验证的部分，并明确剩余部分仍在处理。

优化应从重复与无效工作开始。减少重复读取相同资料，缓存版本明确的静态结果，为 worker 提供足够但不过量的上下文，避免每轮重新传输整份历史。把廉价确定性检查放在昂贵模型审阅之前，也常能减少浪费。缓存必须考虑新鲜度、用户权限和数据范围；用过期结果回答当前状态，或者把一位用户的数据缓存给另一位用户，会把性能优化变成正确性或隐私问题。

重试策略需要按失败类型设计。短暂网络故障可以退避重试；参数错误应先修正；权限拒绝需要授权或停止；验收失败需要新诊断证据；已执行但响应丢失的外部动作，应先查状态而不是立即重复。无差别重试看似提高韧性，实际上可能产生重复发送、额外扣费与更多状态混乱。

系统还需要预算耗尽时的诚实退场方式。它可以保存检查点、列出已完成且已验证的内容、指出尚未满足的条件，并说明继续需要的资源。预算不足不会把“未知”变成“通过”。同样，给 agent 一个预算上限，也不能让它为了赶在上限前完成而偷偷跳过安全门和验证步骤；这些步骤应该属于不可省略的固定开销。

最后，把优化目标写成可以检查的约束组合。例如“在允许资源内完成，关键验收全部通过，费用不超过上限，无法满足时返回具体阻碍”。不要只告诉系统“尽可能快且尽可能好”，再让它自行决定可以牺牲什么。可靠性、安全、成本与延迟不是四份互不相关的报表，它们共同定义了一个 agent 系统是否值得被信任和实际使用。

到这里，harness 的轮廓已经完整：它组织信息、分配计算、控制权限、收集证据、管理状态，并在不确定性无法被合理消除时停止。模型提供推理和生成能力，harness 把这种能力放进一个能够交付、能够审查、能够恢复的流程。工程成熟度不取决于你画了多少个 agent，而取决于系统能否说明自己做了什么、凭什么判断做对、还剩什么风险，以及为什么现在应该继续或停下。
