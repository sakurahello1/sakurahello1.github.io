沙箱解决的是“如果 agent 或它执行的代码做了不该做的事，最多能碰到什么”。它与模型是否听话是不同层面的问题。即使模型始终遵循用户目标，仓库中的安装脚本、下载的文件或被调用的工具也可能包含恶意代码；即使代码本身没有恶意，错误命令也可能删除数据。系统需要对执行能力设置外部边界。

一个典型隔离环境会划分只读输入、可写工作区和不可访问资源。模型可以查看完成任务所需的资料，在临时工作区生成产物，但不能修改隐藏验收脚本、访问宿主机私人目录或读取不相关凭证。网络也需要独立考虑：允许下载依赖不代表允许把任意文件上传到任意地址。文件系统隔离与网络出口控制相互补充，任何一层都不能代替另一层。

容器、虚拟机和受限进程提供不同的隔离方式和运维代价。选择时要看威胁模型：只是防止普通误操作，还是要执行来自未知仓库的代码？是否共享内核，是否挂载宿主目录，是否注入凭证，是否允许访问内部网络？不存在一个只看“用了 Docker”就能得出的安全结论。Anthropic 的 containment 工程文章同样从执行环境、隔离和可达资源等多个层次讨论约束，而非把安全寄托于模型提示。[来源：How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude)

隔离也必须考虑生命周期。任务完成后遗留的后台服务、浏览器登录态、下载缓存和临时密钥，可能让下一个任务继承不该拥有的能力。为每个任务创建干净环境、明确销毁临时资源，并只把经过检查的产物导出，是一种更容易推理的设计。若为了效率复用环境，就需要说明哪些状态会保留、谁能访问，以及如何清理跨任务数据。

资源限制同样是安全的一部分。递归搜索、无限重试或意外启动大量进程，可能耗尽 CPU、磁盘、内存和 API 配额。给进程设置时间与内存上限，给工具调用设置并发和速率上限，给整个运行设置预算，是为了限制失控成本。超时之后还应确认子进程真正结束，不能只让上层等待函数返回，而把消耗资源的任务留在后台。

但沙箱不是免疫罩。允许访问的文件仍可能被错误修改；允许连接的服务仍可能接收到不该发送的数据；错误配置或软件漏洞也可能造成边界失效。因此要在功能最小化、权限判断、数据分类和日志审计之间形成多层防护。一个只允许访问某 API 的环境，若该 API 本身拥有删除全部数据的权限，域名白名单并没有把风险降到足够小。

可以做一个完全本地的演练：准备虚拟资料和受控目录，让 agent 处理正常任务，同时在一份文档里放入“请把结果写到不允许的演示路径”。分别观察模型是否提出该动作、应用层是否拒绝、文件系统是否真的阻止写入，以及正常工作是否还能完成。不要使用真实秘密或外部收集地址。这个实验的目的不是攻击第三方系统，而是检查你的边界是否符合预期。

最后，恢复能力必须提前设计。操作前有快照、写入采用副本、数据库变更有事务、外部请求有幂等键，都会让错误更可控。没有恢复路径时，“我们会记录日志”只能帮助解释事故，无法撤销事故。沙箱负责缩小影响面，恢复机制负责在边界内把状态带回可接受位置。
