## 从一个文件夹开始

上一讲把记忆按“记什么”和“存在哪”分成了两条轴。这一讲只看其中一个位置，外部存储，回答一个很实际的问题：用什么存、怎么查。

如果你只有几十条项目笔记，第一版记忆系统可以非常朴素：按主题组织 Markdown 或 JSON 文件，每条记下来源和时间，用文件名与关键词检索。就像一个整理得当的文件柜，抽屉上贴着标签，每份文件右上角写着日期和出处。

```text
memory/procurement-demo/
  facts/quote-clay-v2-delivery.json      当前有效
  facts/quote-clay-v1-delivery.json      已被 v2 取代
  episodes/2026-09-30-clay-old-version.md
  procedures/compare-quotes.md
```

目录名直接用了上一讲的三类内容：事实、经历、程序。下面是 `facts/` 里一条适合文件系统的事实记录：

```json
{
  "id": "quote-clay-v2-delivery",
  "project": "procurement-demo",
  "kind": "fact",
  "statement": "报价 clay v2 的交付日期为 2026-10-03",
  "source_id": "quote-clay-v2",
  "observed_at": "2026-09-30T10:00:00Z",
  "valid_for": "quote-clay-v2",
  "supersedes": "quote-clay-v1-delivery",
  "status": "active"
}
```

逐个字段看：`id` 是这条记录的稳定名字，以后更新、引用、删除都靠它；`project` 说明它属于哪个项目；`kind` 是内容类型；`statement` 是记录的内容本身；`source_id` 指回原始报价；`observed_at` 是读到它的时间；`valid_for` 写明它只对哪份报价成立；`supersedes` 说明它**取代**了哪条旧记录；`status` 标明它现在是否有效。

这样做的好处是透明、易修复、容易让人确认到底记了什么。记错了，打开文件改一行；想知道 agent 为什么这么答，顺着 `source_id` 就能找到依据。它是一条低成本的工程起点，但不是对所有规模和所有查询类型的最终答案。下面几节看它在哪里开始吃力，以及别的做法各自补上了什么、又多出了什么成本。

## 关键词找得到名字，找不到说法

文件名、项目字段和 source ID 让精确查找很便宜。查询“quote-clay-v2”时，关键词检索往往直接有效：`grep` 一下，文件就出来了。

换一个问法：“之前那家送货挺快的厂商是哪家？”笔记里写的是“交付日期为 2026-10-03”，没有“送货”，也没有“快”。词面一变，单纯的 `grep` 就吃力了。问题的表达差异，才是考虑语义检索的重要理由之一。

**语义检索**最常见的做法是**向量检索**：用一个嵌入模型把每段文字变成一串数字，也就是向量；意思相近的文字，向量也彼此接近。查询时，把问题也变成向量，找出离它最近的几段。它擅长找表达不同、但语义相近的材料。

代价是：它按“像不像”找，不按“对不对”找。向量检索需要**元数据过滤**（按项目、用户、状态等字段先筛一遍）与**原文核验**：语义相似的旧报价仍可能是错误答案，另一个用户的相似笔记也不应跨权限边界返回。

## SQL：条件本身就是结构

有些问题，条件本身就是结构化的。“列出当前项目仍有效、含税总价不超过预算、并能在 10 月 5 日前交付的报价”，每个条件都对应一个字段：项目、状态、总价、交期。这时没必要先做向量相似度，直接写查询：

```sql
SELECT id, vendor, total_cny, delivery, source_id
FROM quotes
WHERE project = 'procurement-demo'
  AND status = 'active'
  AND total_cny <= 7600
  AND delivery <= '2026-10-05'
ORDER BY total_cny;
```

在采购任务的数据上，它只返回一行：clay，7480 元，2026-10-03，来源 quote-clay-v2。ink 虽然最便宜，含税 7040 元，但交期 10-12，被 `delivery` 条件挡掉；paper 含税 7810 元，被 `total_cny` 条件挡掉。**SQL 适合明确的实体、字段、状态和时间范围**，结果可以精确地解释：每一行为什么在、为什么不在。

它的代价在写入那一端：先要设计表结构，每条记录写入时要把字段填对。“9 月 30 日查询出错，改用带版本参数的查询后解决”这样的经历，硬塞进几个字段会丢掉过程，更适合留在 Markdown 里。

## 图：当关系本身就是问题

还有一类问题，难点不在某个字段，而在**关系**。“哪些供应商依赖同一个零件厂，哪些项目又同时依赖这些供应商？”要回答它，得从零件厂出发，沿着“依赖”关系走一步到供应商，再走一步到项目。这就是[第 10 讲](#lesson-10) 说过的多跳问题。

**知识图谱**把这种信息直接存成图：节点是实体（零件厂、供应商、项目、人），边是实体之间的关系（依赖、供货、负责）。图适用于关系本身是查询核心的情况，多跳关系可以帮助组织查询：沿着边走，比在几百段文字里反复搜索要直接。

但建立图需要实体消歧、关系抽取、来源记录和时间更新。**实体消歧**是判断两个名字是不是同一个东西；**关系抽取**是从文字里认出“谁和谁有什么关系”。这两步都可能出错，而图会把错误放大：

把“林青”和“林 青”错误合并，或者把已经解除的依赖当作当前关系，图遍历会非常自信地传播错误：它给出的是一条完整、看起来有条理的路径，比一句模糊的错话更难被怀疑。所以图上的每条边也要带来源和有效期，实体合并要有规则或人来核对。

GraphRAG 的原始工作用实体关系与**社区摘要**支持面向全局主题的查询。社区摘要，是把图里联系紧密的一群实体归成一个“社区”，预先为每个社区写好摘要。它的研究问题包括 query-focused summarization，也就是针对一个问题对整批材料做总结。像“过去一年的采购笔记里，反复出现的交付风险有哪些”（示意）这样的全局问题，答案不在任何一段里，而分散在所有材料中。GraphRAG 有助于理解为什么某些全局问题无法仅靠抓几个相似片段解决；它并没有证明个人 agent 的几十条笔记都应该建图。[来源：GraphRAG](https://arxiv.org/abs/2404.16130)

## 算总账：写入、失效与删除

选型时要比较总成本，而不是看单次查询显得多先进。第一次演示只展示了“查得到”，长期使用还要面对写入、更新、失效和删除。

| 方案 | 前期要做的 | 日常维护的成本 | 典型的出错方式 |
| --- | --- | --- | --- |
| 文件 + 关键词 | 定目录和命名规则 | 人工组织，保持命名一致 | 措辞一变就搜不到 |
| 向量检索 | 切分、选嵌入模型、建索引 | 资料变了要更新或重建索引，维护元数据过滤 | 找回语义相近的旧记录或越权内容 |
| SQL | 设计表结构 | 写入时把字段填对，结构变了要迁移 | 不适合字段的内容被硬塞进去，丢了过程 |
| 知识图谱 | 实体抽取、关系抽取 | 实体合并、关系维护与错误修正 | 错误合并、过期关系被自信地传播 |

粗略地说，成本是一层层叠上去的：文件方案的成本可能主要在人工组织；向量方案在此之外还需要切分、嵌入、更新索引和过滤；图方案还需要抽取、实体合并、关系维护与错误修正。每多一层，能回答的问题多了一类，要维护、要出错的地方也多了一类。

还有三个问题，往往比首次演示更决定系统能否长期使用：

1. **新资料写入后多久能查到？** 如果索引每天重建一次，今天上午的报价更正，今天下午可能还查不到。
2. **旧记录如何失效？** 是靠 `supersedes` 和 `status` 明确标记，还是指望检索时“新的排在前面”？
3. **用户要求删除时，摘要、索引和缓存是否同步处理？**

第三个问题最容易被忽略，因为删除原始文件的那一刻，一切看起来都完成了：

## 混合流程，以及公平的比较

实际系统很少只用一种检索。一个实用的混合流程是：先用精确字段缩小到项目、时间和权限范围，再用关键词或向量找相关内容；需要关系路径时才走图；最终回到可引用的原始记录。

```figure
  {"at":[1],"pass":[1],"say":"在剩下的记录里用关键词“clay 交付日期”查，命中 quote-clay-v2-delivery。如果问题的措辞和笔记差得远，这一层换成向量检索。"},
  {"at":[2],"say":"这个问题不涉及关系路径，跳过图。只有“clay 供货的项目负责人是谁”这类问题才需要它。"},
  {"at":[3],"pass":[3],"say":"按 source_id 回到原始报价 quote-clay-v2，而不是只看记录里那一句 statement。"},
  {"at":[4],"pass":[4],"say":"核对原文：交付日期 2026-10-03。到这一步，候选证据才成为可以写进答案、可以被引用的事实。"}]}
```

:::key 检索器返回的是候选证据
不论是 grep、向量、SQL 还是图，检索器返回的都是**候选证据**，不是自动生效的事实。它可能过期、可能越权、可能被错误地合并过。回到原始记录核对之后，才能写进答案。
:::

比较几种方案时，公平的比较也应该包含不同的查询类型：

| 查询类型 | 例子 | 通常更顺手的做法 | 只测这一类会得出的偏见 |
| --- | --- | --- | --- |
| 精确名称 | quote-clay-v2 的交期 | 文件名、关键词、SQL | “grep 就够了，向量没用” |
| 同义改写 | 之前那家送货挺快的厂商 | 向量检索 + 元数据过滤 | “向量全面胜出” |
| 多跳关系 | clay 供货的项目负责人是谁 | 图，或结构化之后用 SQL 的 JOIN | “图全面胜出” |
| 全局主题 | 反复出现的交付风险有哪些 | 社区摘要一类的方法 | “必须建图” |
| 时效更正 | clay 最新的交期是哪天 | 带版本与时间字段的过滤 | 忽视了版本字段本身的价值 |

只拿多跳题测图，再宣布图全面胜出，和只拿文件名测 grep、再宣布向量无用，一样缺乏说服力。

:::pitfall 为了显得先进而建图
几十条笔记、问题大多是“某个报价的某个字段”，这时建一张知识图谱，得到的是更多的抽取错误、更多要同步删除的派生数据，查询效果却未必更好。先用文件和字段把事情做对，等真的出现大量多跳或全局问题，再为它们加上相应的检索路径。
:::

下面的实验就是一个很小的比较：同一小份关于 clay 的笔记，用关键词搜索、关系遍历和字段过滤三种方式去查。下拉框里的三个问题里，“负责人是谁”对应上表的多跳关系，“现在的报价”和“最新的交期”都属于时效更正。依次切换，看每一列标成“答得上”“要再核验”还是“找不到”。留意第二个问题：关键词搜索找不到，因为没有一句笔记同时提到 clay 和负责人；图沿着 clay → 项目 ink-lab → 负责人 hao 两跳答出；SQL 用 JOIN 也答得出，关系一旦结构化，SQL 同样能做。再留意字段过滤这一列在三道题上都答得上：这不说明 SQL 总体最好，只说明这三道题恰好都是结构化的问题。上表里的“精确名称”“同义改写”和“全局主题”，这三道题都没有覆盖。实验结果是按固定的一小份笔记写好的，用来对比问题类型，不说明哪种数据库总体更好。

:::recap 小结
- 几十条笔记时，按主题组织的 Markdown 或 JSON、记下来源和时间、用文件名与关键词检索，是透明、易修、便宜的起点，但不是所有规模和查询类型的最终答案。
- 关键词适合精确名称；措辞不同的问题是考虑向量检索的重要理由，但向量检索需要元数据过滤和原文核验，防止返回旧记录或越权内容。
- SQL 适合明确的实体、字段、状态和时间范围；图适合关系本身就是问题的多跳查询，但需要实体消歧、关系抽取、来源和时间维护，否则会自信地传播错误。
- GraphRAG 说明某些全局主题问题无法靠抓几个相似片段解决，但没有证明几十条个人笔记都该建图。
- 选型要算总账：写入后多久可查、旧记录怎样失效、删除时摘要、索引和缓存是否同步清除。
- 实用的混合流程是字段缩小范围、关键词或向量找内容、必要时走图、回到原始记录；检索结果是候选证据，比较时要覆盖精确名称、同义改写、多跳、全局主题和时效更正。
:::
