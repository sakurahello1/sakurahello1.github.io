## 失败时，最终答案是最不够用的证据

飞机出了事，调查人员不会只听机长最后说的一句话。他们去找黑匣子：飞行数据记录器记下高度、速度和各个操纵面的位置，驾驶舱录音记下舱内说了什么。有了这些，才能说清楚是哪一刻、哪个系统出了问题。黑匣子不记机长心里怎么想，它记的是事后可以核对的事件。

agent 也一样。它失败时，最终答案往往是最不够用的证据。一句“无法完成采购”没有告诉我们：是搜索没找到、工具超时、权限被拒绝、保存失败，还是验证器误判？这五种原因的修法完全不同。另一方面，把全部运行文本无差别地存下来，也会产生隐私与排查负担：在几万行对话里找一个 HTTP 500，本身就是一项工作。

**可观测性**（observability）指的是从系统留下的记录，推断它内部发生了什么的能力。它的目标，是记录足够重建外部事件的结构化信息。这份记录就叫 **trace**：一次运行从开始到结束、按时间和因果串起来的事件记录。


## 一条最小 trace 记什么

一个最小 trace 应包含：运行 ID、父子任务关系、模型与工具版本、目标和验收版本、工具输入输出引用、时间戳、权限判定、产物哈希、预算使用及终态原因。下表把每一项放回采购任务里，看它各自回答什么问题：

| 字段 | 采购任务里的样子 | 回答的问题 |
| --- | --- | --- |
| 运行 ID | `run-42` | 这是哪一次运行 |
| 父子任务关系 | 子任务 `price-1`，父任务 `run-42` | 这一步属于哪个任务，由谁派出 |
| 模型与工具版本 | 模型名与版本，`lookup_vendor` 的版本 | 行为变了，是不是换了版本 |
| 目标和验收版本 | 需求 v1，验收合同 v2 | 用的是哪一份标准 |
| 工具输入输出引用 | `lookup_vendor(clay)` → `quote-clay-v2` | 每个结论的依据能不能重新读取 |
| 时间戳 | 精确到毫秒 | 先后顺序，每一步花了多久 |
| 权限判定 | `place_order` → ask → 用户批准 | 这个动作是谁放行的 |
| 产物哈希 | `out/final.json` 的 sha256 | 验收看到的和交付的是不是同一份文件 |
| 预算使用 | token、费用、墙钟时间 | 花了多少，花在哪 |
| 终态原因 | failed：下单接口返回 HTTP 500 | 为什么停下 |

几个字段看起来琐碎，却常常是破案的关键。设想同一个采购任务上周通过、这周失败。如果 trace 记了版本，第一眼就能看出这中间 `lookup_vendor` 换了一版（这是假设的情形），返回的交期格式从 `2026-10-03` 变成了 `10/03`；没记版本，就只能把模型、提示、数据、网络挨个怀疑一遍。目标和验收版本也一样：验收合同改过一次，旧运行的“通过”就不能直接和新运行的“失败”相比。

表里的**哈希**是对文件内容算出的一串固定长度的“指纹”，内容哪怕改一个字节，指纹就完全不同。记下产物的哈希，事后就能确认“验收器检查的”和“交给用户的”是同一份文件，没有在中间被换掉。

落到数据上，一条 trace 事件大致是这样（字段名是本课的示意，不是某个标准格式）：

```json
{"run_id": "run-42", "task_id": "order-1", "parent_id": "run-42", "seq": 17,
 "ts": "2026-09-30T14:02:07.310+08:00", "kind": "tool_call",
 "tool": "place_order", "tool_version": "v2",
 "args_ref": "blob://run-42/17/args", "result_ref": "blob://run-42/17/result",
 "policy": {"decision": "ask", "approved_by": "user"},
 "status": "error", "http_status": 500,
 "budget": {"tokens": 18420, "wall_ms": 64100}}
```

注意 `args_ref` 和 `result_ref`：参数和结果本身不直接塞进这条记录，而是存成一个可以按需调取的引用。原因后面讲 trace 的隐私时会说。另外，关键的状态变化，比如下单前后的订单表，应有快照或可重新读取的对象，否则“订单系统里没有这一单”也只是一句转述。

这里需要的是可观察的决策与行动证据，不需要公开模型完整的私有思维链；一段很长的推理文字，也不能代替真实的工具结果。

:::pitfall 把推理文字当成 trace
模型写下“我已确认 clay 的交期是 10-03”，不等于它真的查过。[第 2 讲](#lesson-2)说过，写出来的理由是给人看的解释，不是证据。trace 里能拿来核对的，是那次 `lookup_vendor(clay)` 调用和它返回的 `quote-clay-v2`，而不是模型怎么描述这次调用。
:::

## 把几条轨道对齐到同一条时间线

再看[第 16 讲](#lesson-16)的那个假保存：agent 点了保存，看到“保存成功”，宣布完成，第二天数据却不见了。单看最终截图，无法知道发生了什么，截图上只有那句“保存成功”（一张截图能证明什么、不能证明什么，[第 18 讲](#lesson-18)专门讲过）。

办法是把几条轨道**按时间关联**起来：点击事件、网络请求、响应错误、toast（界面上短暂弹出的提示条）出现的时刻，以及数据库快照。对齐之后就能发现，界面在写入失败时仍然显示了成功。要对得上，各层记录得带着同一个运行 ID，时间戳也得来自能相互对照的时钟，否则只是四份各说各话的日志。

浏览器自动化工具 Playwright 的 Trace Viewer，就是把动作、DOM 快照、截图、网络与控制台信息关联起来展示，体现了浏览器任务中这种时间对齐的价值。[来源：Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer)

下面的实验就是那次假保存的 trace，四条轨道分别是 agent、界面、网络和数据库。拖动“时间”滑块，或者点“自动播放”，一列一列往后看。留意 300 ms 那一列：界面弹出“保存成功”，agent 报告“已保存”，网络轨道却是 HTTP 500，数据库还是旧值。只看界面那一行是成功，只看 agent 那一行也是成功；四行对齐，才看得出它们和网络、数据库这两行对不上。页面底部的说明也值得一读：回看 trace 只是读取记录，不会再点一次保存。

::lab

## 多 agent：时间顺序不等于因果

群聊记录是按时间排的。可你想知道“这个决定是因为谁的哪句话”，看的不是谁最后发言，而是谁回复了谁、引用了哪一条。

多 agent 系统也要保留这种**因果关系**：一个结论是哪个 worker 提出的，来自哪个版本的资料，主节点什么时候采用了它，之后又触发了什么动作？仅按时间排序所有日志，不一定能还原并行的因果。看一段按时间排好的日志：

```text
14:01:02  price-1  读取 三家报价
14:01:02  deliv-1  读取 quote-clay-v2
14:01:03  price-1  报告 #3：ink 最便宜，含税 7040 元；交期未核对
14:01:04  deliv-1  报告 #4：clay 10-03 到货，在期限内
14:01:05  harness  压缩上下文，生成摘要 #5
14:01:06  main     决定 #7：选 ink
14:01:06  main     提议 place_order(ink, 1)，事件 #9
```

主节点选了 ink，而 ink 的交期是 10 月 12 日，晚于期限。决定 #7 是因为哪条消息？日志里紧挨着它的是摘要 #5，可这份摘要由哪些报告压缩而来、压缩时丢了什么，日志的排列看不出来；顺着时间往前找，最先碰到的报告是 #4，它说的是 clay，和“选 ink”对不上，线索就断在这里。两个 worker 同时在跑，谁先写进日志，只取决于谁先返回，和谁影响了谁无关。

为消息保留 `task_id`、`parent_id`、`caused_by` 和版本引用，就能沿着因果往回追：追踪错误从哪里进入，在哪次压缩中丢掉了限制条件，又在哪一步被当成了确定事实。


## “回放”的三种意思

“再看一遍”至少有三种做法，就像一场戏：看当晚的录像；在布景、道具和对手戏都跟那晚一模一样的舞台上再演一遍；或者只给演员同样的开场，让他们再即兴一次。三种做法得到的东西完全不同。

- **审计回放**：只是展示已经记录的动作和证据，什么都不重新执行。
- **环境重放**：在冻结的初始状态或模拟的工具响应上，重建一次执行。
- **重新采样**：再次把相同的输入发给模型。

它们的可重复性不同：

```figure
{"kind":"compare","title":"三种回放，重复的是不同的东西","cols":[
  {"title":"审计回放","tone":"ok","items":["重新执行了什么：什么都没执行，只读记录","结果一样吗：一样，因为只是在看记录","有副作用吗：没有","适合回答：当时到底发生了什么"]},

```

一次完整的排查，三种往往都会用上，而且有先后。先做审计回放，读 trace，定位失败发生在哪一层；再做环境重放，把供应商接口换成返回录制响应的模拟服务，让失败在隔离环境里稳定地重现；修好以后，用同一个环境重放确认它不再出错；最后重新采样几次，看模型在这个场景下的表现是不是稳定。反过来，一上来就“再跑一次看看”，跑通了也说明不了问题修好了，可能只是这次运气好。

尤其不能把审计记录直接当成执行脚本。trace 里第 17 步是 `place_order(clay, 1)`，照着 trace “重演”一遍，就会真的再向供应商发出一次下单请求。重新发送邮件、重新创建订单或者再次扣款，都会产生副作用。安全的重放应使用隔离环境、模拟服务或幂等机制，并且明确哪些步骤只展示、哪些步骤真的执行：

幂等键（附在请求上的唯一编号，接收方凭它识别重复请求，见[第 22 讲](#lesson-22)）能挡住重复，但有前提。对外部请求采用幂等键之前，还要确认目标服务的语义与有效期：对方是否真的支持按这个编号去重，这个编号会被记住多久。本地给请求贴一个标签，并不自动让远端操作具备幂等性。

## trace 本身也是敏感数据

trace 记得越全，越好排查，也越危险。一条完整的 trace 可能包含用户的邮件正文、订单金额、网页全文，甚至不小心打印出来的 API key。

OpenAI Agents SDK 提供模型调用、工具、handoff（把任务交接给另一个 agent）和自定义事件的 tracing 能力，但采集的内容可能包含敏感的输入输出。生产系统应当审查当前版本的配置、存储位置、访问控制和保留期，而不是默认“调试日志不算用户数据”。[来源：OpenAI Agents SDK tracing 文档](https://github.com/openai/openai-agents-python/blob/main/docs/tracing.md)

日志策略可以采用最小化原则：记录动作类型和资源标识，敏感正文按需要脱敏，或存为受控引用（就是前面 JSON 里的 `args_ref`：记录里只有一个地址，取原文要单独授权）；为不同角色提供不同的可见范围；设置明确的保留期限。

| 内容 | 怎样记 | 谁能看（示意） |
| --- | --- | --- |
| 动作类型、资源 ID、时间、权限判定 | 原样记录 | 排查问题的工程师 |
| 报价、订单金额 | 原样记录或受控引用 | 采购负责人和排查人员 |
| 邮件正文、网页全文 | 脱敏，或存为受控引用、按需调取 | 需要时单独授权 |
| API key、令牌 | 不记原文，只记用了哪一个凭证的编号 | 没有人 |

:::pitfall 哈希不是脱敏
对证据做哈希，有助于确认完整性，但哈希本身不让原始内容脱敏，也不证明内容正确。比如把手机号哈希后写进日志：手机号的可能取值有限，别人把所有号码挨个算一遍哈希，就能对出原号码。哈希只说明“内容没被改过”，不说明“内容是对的”，更不说明“内容是安全的”。加密、权限和数据删除仍然需要独立设计。
:::

## 先分类，再动手修

有了 trace，排查的第一步不是改代码，而是**给失败分类**。修错了层，往往比不修更糟：

| 失败类别 | trace 里的样子 | 错误的修法 | 该往哪个方向修 |
| --- | --- | --- | --- |
| 环境 | 工具超时、服务返回 5xx | 换一个更强的模型 | 修环境，或加退避重试 |
| 执行 | 参数不合法、调用了不存在的工具 | 在提示里多写几遍“小心” | 修工具契约与参数校验 |
| 协调 | 摘要丢了限制，报告版本对不上 | 让主节点“更仔细” | 修交接包和压缩规则 |
| 授权 | 策略门 deny | 另找一条通道绕过去 | 申请授权，或者停下 |
| 评分 | 验收过严或过松 | 把正确实现改坏去迎合验收 | 修验收合同本身 |

其中三种误修最常见，也最伤人：工具超时不一定需要换模型；验收过严，不应该通过改坏正确实现来迎合；权限被拒绝，不应通过另找通道来绕过。后两种尤其危险，因为它们会让指标变好看，系统却变坏了。只有能区分环境、执行、协调、授权与评分错误，迭代才会朝正确的方向前进。

:::key trace 的价值
trace 的价值不是让演示更炫，而是让工程判断有证据可依：出了错，能说清错在哪一层、从哪里进入、该修哪里。
:::

:::recap 小结
- 失败时，最终答案是最不够用的证据；可观测性的目标，是记录足够重建外部事件的结构化信息，而不是无差别保存全部文本。
- 最小 trace 包含运行 ID、父子任务、模型与工具版本、目标和验收版本、工具输入输出引用、时间戳、权限判定、产物哈希、预算和终态原因；要的是可核对的行动证据，不是模型完整的思维链。
- 把界面、网络、数据库等轨道对齐到同一条时间线，才看得出“显示成功、实际失败”；多 agent 系统还要用 `task_id`、`parent_id`、`caused_by` 和版本引用保留因果，时间顺序不等于因果。
- 审计回放、环境重放、重新采样的可重复性不同；审计记录不能当执行脚本，安全的重放要用隔离环境、模拟服务或幂等机制，而幂等要以远端服务真的支持为前提。
- trace 本身是敏感数据，要最小化、分角色可见、设保留期；哈希只证明完整性。排查先分类，再修对应的那一层。
:::
