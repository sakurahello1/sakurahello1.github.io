:::goal 读完这一讲，你能回答

## 压缩之后，最先丢的是“后来才重要”的东西

写摘要的人，只能根据**当下**觉得什么重要来取舍。可是长任务里，很多细节要到后来才显出分量。

设想这样一段会话。一开始，用户说了一句“只能建议，不能下单”。接下来几十轮都在讨论价格：哪家便宜，哪家含税后超预算，哪家交期来得及。窗口满了，历史被压缩，摘要里只剩一句“为用户选择电脑”。在写摘要的那一刻，几十轮比价显然是主角，那句开场白像是客套话。新的上下文于是可能继续优化推荐，却已经失去了**动作边界**：什么能做、什么不能做。

另一个常见问题，是忘掉进行中的后台任务。压缩前，agent 提交了一个要跑很久的测试或导出作业；压缩后，新的上下文不知道它还在跑，于是又启动了第二个。

```figure

 "msgs":[
  ["用户","agent","只能建议，不能下单",{"say":"第 1 轮，用户划下动作边界：只能建议，不能下单。"}],
  ["agent","后台任务","提交交期核查 #17",{"say":"第 12 轮，agent 提交了一个要跑很久的交期核查任务，编号 delivery-check-17。"}],

  ["agent","agent","压缩：为用户选择电脑",{"bad":true,"say":"窗口满了，历史被压成一句“为用户选择电脑”。动作边界没写进去，正在运行的 #17 也没写进去。"}],
  ["agent","用户","继续优化推荐",{"say":"新的上下文继续优化推荐，看上去一切正常。但“不能下单”已经不在它眼前了，如果工具表里有下单工具，就没有东西拦住它。"}],
```

## compaction 是一次有损的状态迁移

**compaction**（上下文压缩）可以理解成一次有损的**状态迁移**：旧的上下文退出，新的上下文要继承完成任务所需的最小状态。

打个比方：医院交接班。下班的护士不会只留一句“病人情况稳定”。医嘱写在病历里，接班的人会重新翻看；正在输的液、半小时后要做的检查，记在交接单上；化验单原件放在档案里，需要时去调。口头交代只是其中一部分。

compaction 也一样。自然语言摘要可以是其中一部分，但稳定的规则、文件、运行中的操作、可以恢复的证据，都应该各有一条**明确的路径**，而不是全部挤进摘要里、指望它转述准确：

## Claude Code 怎么做：分类恢复

Claude Code 的公开文档提供了一个具体案例。依据 2026 年 9 月 30 日读取的页面，它在压缩前后做了这些事（下面的表格是对文档描述的整理，细节以文档为准）：

| 类别 | 文档描述的处理 |
| --- | --- |
| 摘要请求本身 | 文档提到 v2.1.198 的摘要请求继承会话的 thinking 配置 |
| 根级 `CLAUDE.md`、无路径限定的规则 | 压缩后重新注入 |
| auto memory、计划等内容 | 压缩后重新注入 |
| 路径相关的规则 | 随后续的文件读取再加载 |
| 近期文件 | 重读一部分最近读过或编辑过的文件 |
| 技能内容 | 重新注入 |
| 后台任务 | 给出提醒 |

先解释几个名词。`CLAUDE.md` 是放在项目里、写给 Claude Code 读的说明文件，常用来写项目约定和规则；**无路径限定的规则**对整个项目生效，**路径相关的规则**只对匹配特定路径模式的文件生效（可以是某个目录，也可以是某类文件），所以要等读到这类文件时才需要加载。**技能**（skill）是可以按需加载的一段操作说明，[第 15 讲](#lesson-15)会讲。

表格第一行也值得想一想：摘要本身就是一次模型调用，它用什么配置，同样会影响摘要的质量和花费，所以连“怎样写摘要”也属于压缩设计的一部分。

这些细节说明，产品并不只依赖“一段万能摘要”来恢复现场。对照上一节的图：规则走“重读”，文件走“索引加重读”，后台任务走“提醒”，摘要只负责叙述做到了哪里。[来源：Claude Code Context Window](https://code.claude.com/docs/en/context-window)

实现细节有明确的版本性。例如，当前页面写到最多重读五个已读或编辑过的文件，较大的文件可能只保留路径；技能正文的重新注入也有单项和总量的预算。这些数字今天是这样，下个版本就可能变。

## 自己写 harness：从结构化检查点开始

如果自己写 harness，可以从一个**结构化检查点**开始：用固定的字段，把继续工作必需的状态写下来。用采购任务举例：

```json
{
  "goal": "比较供应商并给出建议，不下单",
  "completion": "推荐满足预算和日期，且引用当前报价",
  "constraints": {"budget_cny": 7600, "deadline": "2026-10-05"},
  "source_versions": {"clay": "quote-clay-v2"},
  "verified": ["已按 quote-clay-v2 确认 clay 含税总价为 7480 元"],
  "pending": [{"job_id": "delivery-check-17", "state": "running"}],
  "next_action": "查询 delivery-check-17，不重新提交任务",
  "unknown": ["最终交付承诺仍待核实"],
  "evidence": ["artifact://quotes/quote-clay-v2"]
}
```

这个模板是工程建议，并非 Claude Code 的内部摘要格式。逐个字段看，它们分别堵住了前面的哪个漏洞：

- `goal` 里写明“不下单”，`completion` 写明什么才算完成：动作边界和验收标准不再依赖摘要的措辞。
- `constraints` 和 `source_versions` 把数字和版本写死：新上下文不必从叙述里猜预算是多少、报价是哪一版。
- `verified` 与 `unknown` 分开：**已经验证过的**和**尚未知晓的**不会混在一句“基本确定”里。
- `pending` 和 `next_action` 明确记录进行中的操作，并直接写出“不重新提交”：对应开头那个被重复提交的后台任务。
- `evidence` 是索引，不是原文：原文留在磁盘，需要时再取。

重要之处在于两点：区分“已验证”与“尚未知晓”，以及明确记录进行中的操作。

还有一个容易被忽略的问题：这些字段**由谁来写**。如果整张检查点都让模型在压缩时凭记忆写出来，它不过是换了格式的摘要，同样会漏。更稳妥的分工是：

| 字段 | 谁来写 | 依据什么 |
| --- | --- | --- |
| `goal`、`constraints` | harness 代码 | 用户的原始任务；用户修改约束时，由代码覆盖旧值 |
| `source_versions`、`evidence` | harness 代码 | 工具返回里的版本号和存档路径 |
| `verified` | 验证器 | 只有通过确定性检查的结论才写进来 |
| `pending` | harness 代码 | 提交后台任务时留下的登记记录 |
| `next_action`、`unknown` | 模型起草，代码检查格式 | 模型对下一步和缺口的判断 |

原则是：能由代码从事实记录里直接填的字段，就不要让模型去“回忆”。模型擅长判断下一步该做什么、指出还有什么不知道；代码擅长准确记下它自己做过的事，比如提交了哪个任务、读的是哪个版本。

写的时机也有讲究。检查点应该在每次关键状态变化之后就更新：拿到一个验证过的结论，提交或结束一个后台操作，用户修改了约束。如果等到窗口快满时才一次性补写，要记的东西早已埋在很长的历史里，补写本身就成了一次有损压缩。

但检查点也会过期。新一轮启动后，不能无条件相信检查点里的状态：报价版本可能又更新了，后台任务可能已经结束，仓库的 HEAD（当前最新的提交）可能已经变化。恢复时应该先核对最关键的外部状态，再执行下一项动作：

```figure
{"kind":"flow","title":"恢复时先核对，再行动","dek":"检查点记录的是写下它那一刻的世界；动手之前，先看世界变了没有。","nodes":{
  "ckpt":{"at":[0,0],"text":"读检查点","sub":"目标 · 约束 · 待办","icon":"doc"},
  "check":{"at":[1.5,0],"text":"核对外部状态","sub":"版本 · 任务 · HEAD","icon":"search","tip":"只核对会改变下一步决定的那几项，不必把所有东西重查一遍。"},
  "act":{"at":[3,0],"text":"执行下一步","sub":"next_action","icon":"bolt"},
  "stale":{"at":[1.5,1.6],"text":"状态变了","sub":"先更新检查点","icon":"warn","tone":"b"}},

  {"on":["ckpt"],"say":"新一轮开始，先读检查点：目标、约束、已验证的结论、进行中的操作、下一步。"},
  {"on":["ckpt","check"],"edges":["ckpt>check"],"say":"动手之前，先核对最关键的外部状态：报价还是 quote-clay-v2 吗？delivery-check-17 还在跑吗？仓库 HEAD 变了吗？"},
  {"on":["check","stale"],"edges":["check>stale"],"bad":["stale"],"say":"假设 clay 的报价出了新版本。检查点里“已验证”的 7480 是按旧版本算的，现在不能再算作已验证，要移回待核实。"},
  {"on":["stale","check"],"edges":["stale>check"],"say":"更新检查点，再核对一遍，直到关键状态和记录对得上。"},
  {"on":["check","act"],"edges":["check>act"],"ok":["act"],"say":"对得上才执行 next_action：查询 delivery-check-17 的结果，而不是重新提交一份交期核查。"}]}
```

:::pitfall 把检查点当成事实
检查点是“上一次写下时的记录”，不是“现在的事实”。恢复后直接照着 `next_action` 执行，看似高效，其实是在用过期的信息做决定。尤其是 `verified` 一栏：它验证的是写下那一刻的外部状态，外部状态变了，它就要重新验证。
:::

## 压缩的质量可以测

一段摘要读起来简洁、通顺，不说明它能让任务接着干下去。压缩质量可以直接测试，而且应该测。

测试的做法是：构造一个长任务，在早期给出三条硬约束，中途修改其中一条，再掺进大量无关的日志。压缩之后，要求模型继续完成任务，然后观察三件事：

| 观察项 | 可以怎样构造 | 失败是什么样子 |
| --- | --- | --- |
| 旧约束是否被错误复活 | 中途把截止日从 10-05 改成 10-04 | 压缩后仍按 10-05 判断交期 |
| 已完成的工作是否被重复 | 压缩前已经算出 7480、已提交 delivery-check-17 | 压缩后又算一遍，或再提交一次核查 |
| 精确证据能否找回 | 压缩后问 paper 的报价编号 | 答不出来，或者编一个编号 |

对照组也要设好：保留完整历史跑同一个任务，作为对照。有了它，才能分清一个错误是压缩造成的，还是模型本来就会犯；如果完整历史下也会把交期判错，那就不该算在压缩头上。然后比较三种做法：自由摘要、结构化检查点、检查点加原文检索。我们关心的是**恢复是否成功**，而不只是摘要看起来是否简洁。这套测法是本讲自己设计的，并不是下面这篇文章里的实验；该文支持的只是一个前提：长任务里单靠压缩不够，还需要进度文件这类结构化产物。[来源：Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

第一行尤其值得注意。“中途修改”是压缩最容易出错的地方：原始约束出现得早、被重复得多，修改只出现过一次。摘要如果按“出现频率”来取舍，就可能留下旧值、丢掉新值。结构化检查点的好处是，约束字段只有一个位置，新值会直接覆盖旧值。

下面的实验是这组对照的一个极简版本。先点“继续工作”把窗口填满，再选一种压缩方式，点“压缩并恢复”。选“一句自然语言摘要”时，恢复后的窗口里除了“目标：买一台笔记本”，只剩“挑一台性价比高、交付快的电脑”这一句摘要：这正是本讲开头的故事，“不得实际下单”连同预算、交期、精确报价一起丢了。换成“结构化交接”，三条约束都在，但 clay 的精确报价只剩一个索引 quote-clay-v2，要回磁盘去取；换成“按索引从磁盘取回原文”，右边磁盘上那一条会亮起来，四条事实全部恢复。这个实验的场景是固定的，它只对比几种交接方式留住了什么，没有测量任何模型的压缩准确率。

::lab

:::key 一句话
compaction 是一次有损的状态迁移：摘要只负责叙述，规则、运行中的操作和证据各走自己的恢复路径；恢复之后先核对外部状态，再行动。
:::

:::recap 小结
- 压缩最容易丢的是后来才显得重要的细节，比如早期的动作边界“只能建议，不能下单”，以及仍在运行的后台任务。
- compaction 是有损的状态迁移：新上下文要继承完成任务所需的最小状态，规则、文件、运行中操作和证据应各有明确的恢复路径。
- 依据 2026-09-30 读取的 Claude Code 文档，它会重新注入规则、记忆与计划，按需再加载路径规则，重读部分近期文件，重注入技能并提醒后台任务；具体数值有版本性，可带走的是“分类恢复、保留索引、避免重复运行”。
- 自己写 harness 可以从结构化检查点开始，关键是区分已验证与未知，并明确记录进行中的操作；恢复时先核对报价版本、任务状态、仓库 HEAD 等外部状态。
- 压缩质量要用恢复是否成功来测：看旧约束是否复活、已完成工作是否重复、精确证据能否找回，并与完整历史对照。
