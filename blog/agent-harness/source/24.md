设想两个方案。A 用一个模型运行两分钟，B 用五个模型运行十分钟。B 的结果更好，能否证明协作有效？还不能。额外预算本身可能已经足够解释差异。要识别架构收益，至少需要一个同样获得更多预算的单体对照，最好再加入多个独立候选加统一选择器的对照。否则我们不知道收益来自分工、并行采样，还是单纯想得更久。

“等计算”也需要说明具体匹配了什么。相同 token 数不等于相同硬件 FLOPs；不同模型、上下文长度、缓存状态和服务实现都会影响成本。对托管 API，开发者往往无法观察内部计算量。此时可以诚实地称为总 token 预算匹配，并同时报告美元成本和墙钟时间。不能因为实验里每组上限都是十万 token，就声称它们消耗了严格相同的物理算力。

一个有辨别力的实验可以准备两组任务：一组是可独立处理的多个资料块，另一组是有强顺序依赖的状态机操作。比较基础单体、加预算单体、独立多候选、集中协调四种方案。保持模型版本、工具、初始环境、验收器和题目一致；评估器消耗也计入预算。先做固定总 token 的比较，再做固定费用和固定延迟约束的比较，避免一个实验试图回答所有效率问题。

题目之间应采用配对比较：每一种方案都尝试同一批任务，才能减少题目难度差异的干扰。模型存在随机性时，需要重复 trial，并报告波动或区间。工具请求可能受到真实网络变化影响，应记录运行时间与服务状态；若使用冻结工具响应，则明确它测量的是受控环境中的推理与协调，不是完整线上行为。超时、调用失败和预算耗尽必须计入结果，不能在统计时悄悄删除。

预算控制最好放在协调器中，而不是仅在每个 prompt 里写“请节约”。并发 worker 会同时消耗资源，简单地让各分支自行检查剩余额度，可能造成超额。可以先为分支预留额度，执行后结算，再把未用额度归还共享池。模型调用费用、搜索或数据库费用、容器运行时间与验证成本分别记录。应用层的 token 上限是预算代理；服务端实际使用量应在响应后核对。

使用官方 SDK 可以明确地组织并发调用，但 async 本身不会建立协作，也不会自动执行预算治理。下面展示独立分支的最小形态，省略了实际生产中必要的限流、持久状态、取消、审计与预算预留实现：

```python
import asyncio
import os
from openai import AsyncOpenAI

# 独立API示意；仅在读者自己调用时产生费用，不在导入时运行。
async def independent_candidates(task, approved_base):
    if approved_base != "https://api.deepseek.com":
        raise ValueError("示例只授权当前DeepSeek目的地")
    async with AsyncOpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                           base_url=approved_base, max_retries=0, timeout=60) as client:
        async def propose(strategy):
            r = await client.chat.completions.create(
                model="deepseek-flash", max_tokens=600,
                messages=[{"role":"user", "content":f"{task}\n方向：{strategy}"}],
                extra_body={"thinking":{"type":"disabled"}})
            c = r.choices[0] if r.choices else None
            usable = bool(c and c.finish_reason == "stop" and c.message.content)
            return {"status":"candidate" if usable else "incomplete",
                    "answer":c.message.content if usable else None,
                    "finish_reason":c.finish_reason if c else None,
                    "usage":r.usage.model_dump() if r.usage else None}
        # 预留总输出上限1200，两分支各600；仍需整体deadline与最终验收。
        return await asyncio.wait_for(asyncio.gather(
            propose("需求与约束"), propose("失败与反例")), timeout=120)
```

不要在不同架构中偷偷改变其他条件。例如给集中式更详细的任务说明、给单体更少工具，或者只允许多 agent 使用独立验证器，都会让“架构效果”混入别的增益。消融实验可以逐步移除通信、验证或角色分工，观察哪些组件真正有贡献；但消融后的提示和运行条件也要合理，否则可能只是把系统人为拆坏。

最终应展示准确率、成本与延迟的取舍，而不仅是一名冠军。如果一个方案在同等成功率下更便宜，或同等费用下更准确，它可能位于更优的 Pareto 前沿；若同时更贵、更慢、成功率更低，则没有必要因其多 agent 标签而保留。关于 agent 评估忽视成本的问题，《AI Agents That Matter》提供了系统性讨论。[来源：AI Agents That Matter](https://arxiv.org/abs/2407.01502)

本部分的核心经验可以压缩成一句话：多 agent 改变的是计算分配、信息流和责任边界，收益必须通过任务相关、预算透明的实验来证明。下一部分会进一步讨论，当这些系统真正拥有文件、网络和外部账户权限时，怎样让错误停留在可控范围内。
