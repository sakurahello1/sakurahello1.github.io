## 多花了预算的赢，还不能算赢

两个学生准备同一场考试。一个自己复习了两个小时；另一个拉上四个朋友，五个人一起复习了十个小时。第二个学生考得更好。能说“小组学习更有效”吗？还不能。他们花掉的时间多得多，也许随便哪个学生独自复习同样久，也能考这么好。

设想两个方案。A 用一个模型运行两分钟，B 用五个模型运行十分钟。按“模型数 × 分钟”粗算，B 用掉的资源是 A 的 25 倍。B 的结果更好，能否证明协作有效？还不能。额外预算本身可能已经足够解释差异。

要识别架构收益，至少需要一个同样获得更多预算的单体对照，最好再加入多个独立候选加统一选择器的对照。**对照**（control）是只改变一个因素的比较组：它和被检验的方案在其他方面都一样，只差你想检验的那一处。否则我们不知道收益来自分工、并行采样，还是单纯想得更久。

## “等计算”到底等的是什么

“给每个方案同样的计算量”说起来简单，做起来要先回答：同样的**什么**？

相同 token 数不等于相同硬件 FLOPs（浮点运算次数，衡量硬件实际做了多少计算）。不同模型、上下文长度、缓存状态和服务实现都会影响成本。举一个直观的例子：同样输出 1 000 个 token，接在 2 千 token 的上下文后面，和接在 10 万 token 的上下文后面，服务器要做的计算差别很大。对托管 API，开发者往往无法观察内部计算量。

此时可以诚实地称为**总 token 预算匹配**，并同时报告美元成本和墙钟时间。不能因为实验里每组上限都是十万 token，就声称它们消耗了严格相同的物理算力。

| 预算口径 | 怎样测 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |

| 美元 | 实际用量乘单价，工具与容器费用另列 | 真实花了多少钱 | 用户要等多久 |
| 墙钟 | 从提交任务到交付答案的时间戳 | 用户要等多久 | 花了多少钱 |

## 设计一个有辨别力的实验

**有辨别力**的意思是：实验结果能把不同的解释区分开。如果无论哪种解释成立，实验都会给出一样的结果，这个实验就白做了。

一个有辨别力的实验可以准备两组任务：一组是可独立处理的多个资料块，另一组是有强顺序依赖的状态机操作。比较基础单体、加预算单体、独立多候选、集中协调四种方案：

| 方案 | 做法 | 它回答的问题 |
| --- | --- | --- |
| 基础单体 | 一个 agent，常规预算 | 起点在哪里 |
| 加预算单体 | 一个 agent，预算与多 agent 方案相同 | 想得更久能不能追上 |
| 独立多候选 | 几个分支各自解题，统一选择器挑一个 | 多试几次能不能追上 |
| 集中协调 | 协调器拆分、派发、整合 | 分工协调有没有额外收益 |

两组任务的作用是检验[第 23 讲](#lesson-23)的依赖结构假设：如果假设成立，集中协调在资料块任务上的相对收益，应当比在状态机任务上更大；如果两组看不出差别，这个假设就要打折扣。

保持模型版本、工具、初始环境、验收器和题目一致；评估器消耗也计入预算。先做固定总 token 的比较，再做固定费用和固定延迟约束的比较，避免一个实验试图回答所有效率问题。三种约束问的是三个不同的问题：同样的读写量下谁更准，同样的钱谁更准，让用户等同样久谁更准。混在一个实验里，你分不清结果是被哪一个约束决定的。

几个统计上的细节同样重要：

- **配对比较**：每一种方案都尝试同一批任务，逐题比较，才能减少题目难度差异的干扰。
- **重复 trial**：一次 trial 是某个方案在某道题上的一次独立运行。模型存在随机性时，需要重复 trial，并报告波动或区间，而不是只报一个数。
- **工具环境**：工具请求可能受到真实网络变化影响，应记录运行时间与服务状态。若使用冻结工具响应（事先录好工具的返回值，每次回放同一份，本课的采购报价就是这样一份冻结数据），则明确它测量的是受控环境中的推理与协调，不是完整线上行为。
- **失败也是结果**：超时、调用失败和预算耗尽必须计入结果，不能在统计时悄悄删除。

:::example 为什么要配对
示意：方案甲和方案乙各做 20 道题，其中有一道谁都做不出来的难题。如果甲、乙做的是两批不同的题，而这道难题恰好只落在甲的那一批，甲的成功率就被冤枉地拉低了 5 个百分点。配对比较让两边做同一批题，逐题看“这道题上谁对谁错”，难题对两边一视同仁；剩下的差异才更可能来自方案本身。
:::

## 预算要由协调器来管

预算控制最好放在协调器中，而不是仅在每个 prompt 里写“请节约”。

:::pitfall 在提示里写“请节约预算”
这句话最多影响模型怎样措辞，管不住账单：模型可能照做，也可能不照做；它也看不到别的分支此刻花了多少。预算是 harness 的职责，要落在协调器的代码里，由它决定一次调用能不能发出去。
:::

而且即使每个 worker 都很自觉，也挡不住下面这种情况。

并发 worker 会同时消耗资源，简单地让各分支自行检查剩余额度，可能造成超额。更稳的做法是先为分支预留额度，执行后结算，再把未用额度归还共享池：

把这个机制写成代码，核心只有两个方法。下面是本教程的示意写法，不是某个 SDK 的内置功能：

```python
class BudgetPool:
    """应用层预算池示意：先预留，后结算，没用完的退回。"""

    def __init__(self, total_tokens):
        self.available = total_tokens

    def reserve(self, amount):
        # 检查和扣减在同一个同步步骤里完成，中间没有 await，
        # 其他协程插不进来。多线程或多进程时要改用锁或数据库事务。
        if amount > self.available:
            return False
        self.available -= amount
        return True

    def settle(self, reserved, used):
        # used 以服务端返回的实际用量为准；超出预留时 available 会变少，超额被记下来而不是被忽略。
        self.available += reserved - used


async def run_branch(pool, estimate, call_model):
    """estimate：这次调用预计的输入加输出 token 上限。"""
    if not pool.reserve(estimate):
        return {"status": "skipped", "reason": "budget"}
    used = estimate  # 调用失败、拿不到用量时，按预留额记账
    try:
        reply = await call_model()
        used = reply["usage"]["total_tokens"]
        return {"status": "done", "reply": reply}
    finally:
        pool.settle(estimate, used)
```

`reserve` 回答“能不能开跑”，`settle` 在调用结束后把账算清。`run_branch` 里的 `finally` 保证调用即使抛出异常，预留的额度也会结算，不会被永久占住。

账本还要分开记：模型调用费用、搜索或数据库费用、容器运行时间与验证成本分别记录，最后才能回答“钱花在了哪里”。另外要记住，应用层的 token 上限是**预算代理**；服务端实际使用量应在响应后核对，上面的 `settle` 用的就是服务端报告的数。

使用官方 SDK 可以明确地组织并发调用，但 async 本身不会建立协作，也不会自动执行预算治理。下面展示独立分支的最小形态，省略了实际生产中必要的限流、持久状态、取消、审计与预算预留实现：

```python
import asyncio
import os
from openai import AsyncOpenAI

# 独立API示意；仅在读者自己调用时产生费用，不在导入时运行。
async def independent_candidates(task, approved_base):
    if approved_base != "https://api.deepseek.com":
        raise ValueError("示例只授权当前DeepSeek目的地")
    async with AsyncOpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                           base_url=approved_base, max_retries=0, timeout=60) as client:
        async def propose(strategy):
            r = await client.chat.completions.create(
                model="deepseek-flash", max_tokens=600,
                messages=[{"role":"user", "content":f"{task}\n方向：{strategy}"}],
                extra_body={"thinking":{"type":"disabled"}})
            c = r.choices[0] if r.choices else None
            usable = bool(c and c.finish_reason == "stop" and c.message.content)
            return {"status":"candidate" if usable else "incomplete",
                    "answer":c.message.content if usable else None,
                    "finish_reason":c.finish_reason if c else None,
                    "usage":r.usage.model_dump() if r.usage else None}
        # 预留总输出上限1200，两分支各600；仍需整体deadline与最终验收。
        return await asyncio.wait_for(asyncio.gather(
            propose("需求与约束"), propose("失败与反例")), timeout=120)
```

对照这一讲的内容读这段代码：`asyncio.gather` 让两个分支同时发出请求，墙钟接近较慢的那一个，而不是两者之和；两个分支互相看不到对方，这就是“独立多候选”，谈不上协作。每个分支的 `max_tokens=600` 是输出上限，两个加起来 1 200，这是写死在代码里的预算，不是由协调器动态分配的。`max_retries=0` 关掉了 SDK 的自动重试，避免失败时悄悄多花钱；`finish_reason` 不是 `"stop"` 的回答（比如被截断）标成 `incomplete`，而不是当成候选；每个分支都带回服务端报告的 `usage`，供事后核对。最外层的 `wait_for` 是整体截止时间。它仍然缺一个选择器和一个验收器，拿到两个候选之后选哪一个、对不对，都还没有回答。

## 别在不同架构之间偷偷改条件

不要在不同架构中偷偷改变其他条件。例如给集中式更详细的任务说明、给单体更少工具，或者只允许多 agent 使用独立验证器，都会让“架构效果”混入别的增益。这些改动往往不是故意的：搭多 agent 系统时，你自然会花更多心思写协调器的说明，而单体基线常常是随手搭的。

## 交一张取舍表，而不是一个冠军

最终应展示准确率、成本与延迟的取舍，而不仅是一名冠军。原因很简单：不同的使用者在乎不同的东西，一个“综合最好”的冠军替他们做了本该由他们做的选择。

这里需要一个词：**Pareto 前沿**。如果找不到另一个方案在成功率、费用、延迟上都不比它差、并且至少一项更好，这个方案就在 Pareto 前沿上；反过来，如果存在这样的方案，它就被**支配**了，没有理由选它。看一张虚构的结果表：

| 方案（虚构数字） | 成功率 | 每题费用 | 墙钟 | 在不在前沿上 |
| --- | --- | --- | --- | --- |
| 基础单体 | 60% | 0.4 元 | 40 秒 | 在：最便宜、最快 |
| 加预算单体 | 68% | 1.6 元 | 150 秒 | 不在：独立多候选花一样的钱，更准也更快 |
| 独立多候选 | 71% | 1.6 元 | 50 秒 | 在 |
| 集中协调 | 69% | 1.7 元 | 70 秒 | 不在：比独立多候选更贵、更慢、成功率更低 |

如果一个方案在同等成功率下更便宜，或同等费用下更准确，它可能位于更优的 Pareto 前沿；若同时更贵、更慢、成功率更低，则没有必要因其多 agent 标签而保留。反过来，假如表里的集中协调成功率是 80%，它就回到了前沿上：更贵、更慢，但更准。值不值得，要看你的场景对准确率和等待有多敏感，而这正是取舍表要留给读者判断的部分。关于 agent 评估忽视成本的问题，《AI Agents That Matter》提供了系统性讨论。[来源：AI Agents That Matter](https://arxiv.org/abs/2407.01502)

:::key 本部分的一句话
多 agent 改变的是计算分配、信息流和责任边界，收益必须通过任务相关、预算透明的实验来证明。
:::

:::recap 小结
- 多花了预算的赢不能直接归功于协作：至少要有同预算的单体对照，最好再加“独立多候选 + 统一选择器”对照，才能把想得更久、多试几次和分工协调分开。
- 用托管 API 时，诚实的说法是“总 token 预算匹配”，并按服务端用量核对，同时报告美元和墙钟；不能声称消耗了相同的硬件算力。
- 有辨别力的实验用两组依赖结构不同的任务比较四种方案，控制模型、工具、环境、验收器和题目，配对比较、重复 trial，超时和失败照样入账。
- 并发 worker 的预算要由协调器先预留、后结算、未用退回；async 只负责并发，不负责协作和预算治理。
- 不在架构之间偷偷改说明、工具或验证器；消融要保持条件合理；最后交出准确率、成本和延迟的取舍表，被支配的方案不因多 agent 标签而保留。
:::
