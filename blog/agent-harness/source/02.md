## 模型只能看见你写下的那几行

第一天去一家公司上班，前台递给你一张分机表。表上写着“8001 财务报销”“8002 电脑报修”，你遇到事情就知道该拨哪个号。假如整张表只有一行“8000 什么事都找这里”，你拨过去以后还是得猜：对方能办什么？要准备什么材料？办不成会怎样？

模型选择工具时的处境比这更极端。它看不到工具的源码，也不能走过去当面问一句。它能依据的只有四样东西：工具的**名称**、**描述**、**参数说明**，以及此前调用这个工具得到的**反馈**。[第 2 讲](#lesson-2)里 harness 交给模型的“工具列表”，指的就是这些。以本课实验里的 `lookup_vendor` 为例，模型实际收到的是这样一段定义：

```json
{
  "type": "function",
  "function": {
    "name": "lookup_vendor",
    "description": "读取虚构供应商报价、税率、交期和证据 ID；无采购副作用",
    "parameters": {
      "type": "object",
      "properties": {"id": {"type": "string", "enum": ["clay", "ink", "paper"]}},
      "required": ["id"],
      "additionalProperties": false
    }
  }
}
```

这几行里每一处都在向模型传递信息。名字说明它是“查供应商”；描述说明它会返回什么，并且特意写明“无采购副作用”；`enum`（枚举）把 `id` 限定为三个合法取值；`required` 说明这个字段必须给；`additionalProperties: false` 的意思是“除了列出的字段，一个都不许多”。这段定义的格式叫 **JSON Schema**，是一种用 JSON 描述“一段 JSON 应该长什么样”的通用写法。

所以，一个工具不只是一个 Python 函数加上一段 JSON。对模型来说，**这段定义就是工具的全部**。一个叫 `do_task` 的万能工具，会把大量隐含知识推给模型：它到底能查什么、能改什么、失败了如何恢复？名字越宽泛，成功路径就越依赖模型去猜。

“窄”也不等于“越碎越好”。Anthropic 那篇工具设计文章提醒过一个常见错误：把现有的每个 API 端点原样包成一个工具。工具完全可以在内部串起好几次底层调用，比如用一个 `schedule_event` 代替分开的“列出用户”“列出日程”“创建日程”三个工具。文章还给了两条很实用的建议：写描述时，想象自己在向团队里的新同事介绍这个工具；参数名要不含糊，与其叫 `user`，不如叫 `user_id`。[来源：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

换句话说，`do_task` 的毛病不在于它“做的事多”，而在于**它的定义说不清它会做什么**。

## 一份完整的契约，回答五个问题

药盒里的说明书会写：治什么病，怎么吃、吃多少，什么情况下不能吃，可能有什么不良反应，吃多了怎么办。一个你从没见过的药，读完说明书也能安全地用。

工具的**契约**（contract）就是它的说明书，指调用方和工具之间约定好的全部内容，比参数格式多得多。一份好的工具契约，至少回答五个问题：

1. **做什么**：这个工具完成哪一件事。
2. **接收什么输入**：有哪些参数，各自的类型和取值范围。
3. **需要什么前置条件**：调用之前，哪些事情必须已经成立。
4. **会产生什么副作用**：调用之后，外部世界有没有被改变。
5. **失败意味着什么**：出错时，事情是“没发生”“发生了一半”，还是“不知道发生了没有”。

把采购任务里的工具和一个假想的下单工具放在一起比一比（本课不会真的下单，`submit_order` 只是为了说明问题）：

| 问题 | `lookup_vendor(id)` | `compute_total(id, quantity)` | 假想的 `submit_order(quote_id, quantity, operation_id)` |
| --- | --- | --- | --- |
| 做什么 | 读一家供应商的报价、税率、交期和来源编号 | 按报价算含税总价 | 按一份报价创建订单 |
| 输入 | `id` 只能是 clay、ink、paper | `id` 加整数 `quantity` | 报价编号、数量、操作编号 |
| 前置条件 | 无 | 无 | 报价仍然有效，用户已经授权 |
| 副作用 | 无，只读 | 无，本地计算 | 有：真的产生一张订单 |
| 失败意味着 | 没查到，可以核对参数再查 | 参数不合规，改了再算 | 订单可能已经建好，也可能没有，要先查清 |

最后两行决定了执行策略。像 `lookup_quote(vendor_id, version)` 或本课的 `lookup_vendor(id)` 这样的只读查询，可以直接执行，失败了也可以放心重试；`submit_order(quote_id, quantity, operation_id)` 会产生订单，要求报价有效且用户已授权。**它们即使参数外形相似，执行策略也应完全不同。** 这种区别不能靠模型临场判断，而要写进 harness 的**工具注册表**：一张固定的表，每一行把一个工具名对应到它的函数和契约。

## 形状对了，不等于事情对了

去银行柜台办转账，表格上的金额栏只能填数字，这是格式。柜员收到表格还要再看三件事：账上有没有这么多钱，这张卡是不是你本人的，这笔转账是不是刚刚已经办过一次。格式检查和业务检查是两回事，前者通过了，后者一样可能不通过。

工具参数也是这样。**输入 schema 描述形状，业务验证描述现实约束。**

| 参数 | JSON Schema 能确认的 | 还需要业务检查回答的 |
| --- | --- | --- |
| `quantity: 999` | 是整数 | 一次采购 999 台合理吗？本课规定每次只能 1 到 3 台 |
| `id: "clay"` | 是字符串，并且在枚举之内 | 当前用户有权访问这家供应商吗？ |
| `operation_id: "op-7"` | 是一个格式正确的字符串 | 这个请求是不是已经执行过，还能不能再执行一次？ |

`quantity` 是整数，不意味着 999 台采购量合理；供应商 ID 是字符串，不意味着当前用户能访问该供应商；`operation_id` 格式正确，不意味着请求可以重复执行。这些检查应该放在 **host 程序**（运行 harness 的你自己的程序）或者服务端，这样安全性才不会依赖模型刚好遵守提示。[来源：OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling)

写成代码，一个最小的检查大致如下。它和本页实验做的是同一类检查，只是换成了 Python（示意，省略了参数长度限制等细节）：

```python
import json

VENDORS = {"clay", "ink", "paper"}

# 注册表：工具名 → 允许的字段、是否只读
REGISTRY = {
    "lookup_vendor": {"fields": {"id"}, "read_only": True},
    "compute_total": {"fields": {"id", "quantity"}, "read_only": True},
}


def check_call(name, raw_args):
    """返回 None 表示放行；否则返回一条交回模型的错误。"""
    spec = REGISTRY.get(name)
    if spec is None:
        return {"error": "unknown_tool", "tool": name}
    try:
        args = json.loads(raw_args)
    except json.JSONDecodeError:
        return {"error": "invalid_json"}
    if not isinstance(args, dict) or set(args) != spec["fields"]:
        return {"error": "bad_fields", "expected": sorted(spec["fields"])}
    # 先确认是字符串：列表、对象这类值不能直接拿去查集合，会抛异常
    if not isinstance(args["id"], str) or args["id"] not in VENDORS:
        return {"error": "bad_enum", "field": "id", "allowed": sorted(VENDORS)}
    if name == "compute_total":
        q = args["quantity"]
        # JSON 里的 true 在 Python 里也算 int，要单独排除
        if not isinstance(q, int) or isinstance(q, bool):
            return {"error": "bad_type", "field": "quantity", "expected": "integer"}
        if not 1 <= q <= 3:  # 业务规则：schema 只管得到“是整数”
            return {"error": "policy", "rule": "quantity 仅允许 1 到 3"}
    return None
```

注意返回值：检查不通过时，函数不抛异常了事，而是给出一条**说清原因的错误**。这条错误会作为观察交回模型，模型下一步就能改正参数，而不是对着一句“失败”发呆。

:::pitfall 把规则写进描述，不等于规则生效
在工具描述里写上“一次最多买 3 台”是有用的：模型会更少地提出 999。但这只是降低出错的概率。真正挡住 999 的，只能是执行前那一行 `if not 1 <= q <= 3`。提示写得再好，也会有模型没遵守的那一次，而那一次恰好可能是代价最大的一次。
:::

下面的实验把一次工具调用要过的检查拆成五道关，检查的内容和本页 agent 实际使用的 `dispatch()` 一致（实验按关卡逐个演示，五关都过了才真正调用 `dispatch()`）。在“提议”下拉框里依次选**不存在的工具**、**多了一个字段**和**形状对，但违反业务规则**，每选一个就点“送进 harness”。留意三件事：`delete_order` 在第 ② 关就被拦下，因为注册表里没有它；多出来的 `endpoint` 字段想把请求引到一个外部网址，第 ③ 关“字段不多不少”把它挡住；`quantity: 999` 一路通过前四关，直到第 ⑤ 关的业务规则才被拦下。最后再选**合法调用**，看它真的执行并返回 7480。

::lab

## 返回值：小结论直接给，大证据稳定引用

你请同事去查昨晚的测试为什么挂了。他可以把一万行日志原封不动地转给你；可以只回一句“日志在 logs.txt”；也可以告诉你“23 个测试挂了 1 个，是 `test_expired_login`，期望返回 401，实际返回 200，完整日志我放在第 083 次运行的归档里了”。第三种回复最有用：你立刻知道下一步查什么，要细节时也知道去哪里找。

工具的返回值也要这样设计。原因在于，返回的内容会写回上下文，而上下文是有限的，并且每一圈都要重新读一遍（[第 2 讲](#lesson-2)画过这张账）。

比较实用的模式是“**小结论直接返回，大证据稳定引用**”：

```json
{
  "status": "partial",
  "operation_id": "test-run-083",
  "summary": "23 个测试中有 1 个失败",
  "failures": [
    {"name": "test_expired_login", "expected": 401, "actual": 200}
  ],
  "artifact_ref": "artifact://test-runs/083",
  "truncated": true,
  "next_cursor": null
}
```

逐个字段看：`status` 说明整体结果（这里是“部分通过”）；`summary` 和 `failures` 是模型最需要的小结论；`artifact_ref` 是完整证据的**引用**，也就是一个以后还能凭它取回原文的稳定地址；`truncated: true` 老实交代“这里没有给全”；`next_cursor` 是分页用的游标，为 `null` 说明没有下一页。模型读完就知道下一步要检查过期登录的逻辑；需要完整栈信息时，再通过读取工具访问归档。

引用必须具有明确的**可访问范围**与**生命周期**：谁能读它，它能保存多久。一个即将被清理的临时文件路径，不能承担跨会话证据索引的责任。反过来，也不要把一切都变成指针。Anthropic 的工具设计建议强调的是返回有意义的上下文，并对结果做过滤、分页或截断；把大证据改成稳定引用，则是本课自己的做法。同一篇文章还建议优先返回有意义的名字，少用对模型没有意义的底层技术编号；如果有时需要简要结果、有时需要详细结果，可以给工具加一个取值为 concise 或 detailed 的 `response_format` 参数，让 agent 自己选。[来源：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

回到采购任务。`lookup_vendor("clay")` 的返回很小：报价 6800、税率 10%、交期 2026-10-03、来源 `quote-clay-v2`，全部直接给出就好。其中的 `quote-clay-v2` 就是一个稳定引用：验收器检查“来源是否正确”时，核对的正是它。

## 错误也要设计，超时最危险

网上付款时点了“支付”，页面转了半天，最后显示“网络超时”。这时候最不该做的，就是马上再点一次：钱可能已经扣了，只是结果没能传回你的页面。

工具的错误同样应该**机器可读**，也就是用一个固定的错误码表明是哪一类错误，让 harness 能按类别分支处理：

| 错误码 | 含义 | 下一步该怎么做 |
| --- | --- | --- |
| `not_found` | 要找的对象不存在 | 提示核对 ID |
| `permission_denied` | 没有权限 | 停止，或者请求授权 |
| `rate_limited` | 被限流了 | 按明确的策略延迟后再试 |
| `timeout` | 没等到结果 | 先判断操作是否可能已经发生 |

错误码是给 harness 分支用的；给模型看的部分，最好再附一句能照着改的说明。前面那篇文章也建议，把错误写成具体、可操作的改进提示，而不是一个含义不明的错误码或一整段调用栈。

表里最难处理的是最后一行。只读工具超时，重试无非多花一点时间；有副作用的工具超时，情况完全不同。网络连接断开时，远端可能已经完成了订单创建，此时直接重试会产生第二张订单。

这里用到了[第 1 讲](#lesson-1)提过的**幂等**：同一个请求执行一次和执行多次，效果相同。稳妥的方案有两种：用稳定的操作 ID 去查询结果，或者依赖后端的幂等契约（后端承诺“同一个 `operation_id` 只会生效一次”）。两样都没有的时候，就应当保留“不确定”这个状态，而不是猜测失败。一个说“不知道订单建没建成，请人工核对”的 agent，比一个悄悄下了两次单的 agent 可靠得多。

:::example 同一个超时，两种工具
`lookup_vendor("paper")` 超时了：它是只读的，harness 可以直接重试，最坏也就是多等几秒。

假想的 `submit_order` 超时了：它有副作用，harness 不能重试，而要先用操作编号查询；查不到就把这一步记为“不确定”，交给用户确认。两次超时的错误码一模一样，处理方式完全相反，区别只来自契约里“副作用”那一行。
:::

## 接入 MCP：接口统一了，信任没有自动到来

USB 接口统一以后，什么设备都能插上电脑。可是“插得上”不等于“可以信”：一个来路不明的 U 盘照样可能带着病毒。

**MCP**（Model Context Protocol，模型上下文协议）做的是工具世界里类似 USB 的事。它为工具发现、输入 schema 和结果结构提供协议层约定：harness 可以用统一的方式问一个 MCP 服务器“你有哪些工具”，拿到每个工具的名称、描述、输入 schema，以及可选的 **annotations**（描述工具行为的标注），再用统一的方式调用它们。规范还区分了两类错误：协议层面的错误，比如调用了不存在的工具；以及工具执行中的错误，比如输入校验失败、业务逻辑出错，这类错误放在结果里并标记 `isError: true`，规范建议把它们交给模型，好让模型自己纠正参数。

但接入 MCP 服务器不会自动建立信任。来自服务的描述与 annotations 可以帮助调度，不能替代宿主对权限和风险的判断。规范本身也写明，除非服务器是可信的，客户端必须把工具的 annotations 当作不可信的信息。工具返回的网页、日志或文档也仍然是外部数据，其中出现“忽略原指令”的文字，不应获得控制 harness 的权限。[来源：MCP Tools 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

:::pitfall 服务器说“只读”，不代表它真的只读
一个 MCP 工具在描述里写“只读，安全”，这是服务器的自我声明，不是你验证过的事实。第三方服务器尤其如此。把它登记进注册表时，副作用和权限级别要由你自己判断；拿不准的，按有副作用处理。网页和文档里的“指令”该怎样防，[第 28 讲](#lesson-28)会专门讲。
:::

:::recap 小结
- 模型只能依据工具的名称、描述、参数和此前的反馈来选择和调用工具；定义说不清的地方，就只能靠模型去猜。
- 一份完整的工具契约回答五个问题：做什么、接收什么输入、需要什么前置条件、有什么副作用、失败意味着什么；有没有副作用要登记在注册表里，由它决定执行路线。
- JSON Schema 只检查形状；数量是否合理、有没有权限、能不能重复执行，要在 host 程序或服务端单独检查，并把说清原因的错误交回模型。
- 返回值遵循“小结论直接返回，大证据稳定引用”，引用要有明确的访问范围和生命周期。
- 有副作用的操作超时，不能当成失败直接重试：先用稳定的操作编号查询，或依赖后端幂等；都做不到时，如实保留“不确定”。
- MCP 统一了工具的发现与调用方式，但不带来信任：服务器的声明只作参考，工具返回的内容只是数据。
:::
