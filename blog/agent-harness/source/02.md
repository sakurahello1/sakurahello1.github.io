一个工具不只是 Python 函数加上一段 JSON。模型选择工具时，只能依据它看到的名称、描述、参数和此前反馈。一个叫 `do_task` 的万能工具，会把大量隐含知识推给模型：它到底能查什么、能改什么、失败如何恢复？名字越宽泛，成功路径越依赖模型猜测。

好的工具契约至少回答五个问题：做什么，接收什么输入，需要什么前置条件，会产生什么副作用，失败意味着什么。例如 `lookup_quote(vendor_id, version)` 是只读查询；`submit_order(quote_id, quantity, operation_id)` 会产生订单，要求报价有效且用户已授权。它们即使参数外形相似，执行策略也应完全不同。

输入 schema 描述形状，业务验证描述现实约束。`quantity` 是整数，不意味着 999 台采购量合理；供应商 ID 是字符串，不意味着当前用户能访问该供应商；`operation_id` 格式正确，不意味着请求可以重复执行。把这些检查放在 host 程序或服务端，才不会让安全性依赖模型刚好遵守提示。[来源：OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling)

返回值也需要设计。直接把一万行日志塞回上下文，会挤掉当前任务的重要信息；只返回 `logs.txt`，模型又可能不知道里面有什么、是否值得打开、该从哪一行开始。比较实用的模式是“小结论直接返回，大证据稳定引用”：

```json
{
  "status": "partial",
  "operation_id": "test-run-083",
  "summary": "23 个测试中有 1 个失败",
  "failures": [
    {"name": "test_expired_login", "expected": 401, "actual": 200}
  ],
  "artifact_ref": "artifact://test-runs/083",
  "truncated": true,
  "next_cursor": null
}
```

模型可以立刻知道下一步要检查过期登录逻辑；需要完整栈信息时，再通过读取工具访问归档。引用必须具有明确的可访问范围与生命周期。一个即将被清理的临时文件路径，不能承担跨会话证据索引的责任。Anthropic 的工具设计建议强调有意义的上下文、结果过滤与分页，而不是一律把内容变成指针。[来源：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

错误同样应该机器可读。`not_found` 可以提示核对 ID；`permission_denied` 应停止或请求授权；`rate_limited` 可以根据明确策略延迟；`timeout` 则需要先判断操作是否可能已经发生。网络连接断开时，远端可能已经完成了订单创建。此时直接重试会产生第二张订单。稳妥方案是用稳定操作 ID 查询结果，或者依赖后端幂等契约；没有这样的能力，就应保留“不确定”，而不是猜测失败。

MCP 为工具发现、输入 schema 和结果结构提供协议层约定，但接入 MCP 服务器不会自动建立信任。来自服务的描述与 annotations 可以帮助调度，不能替代宿主对权限和风险的判断。工具返回的网页、日志或文档也仍是外部数据，其中出现“忽略原指令”的文字，不应获得控制 harness 的权限。[来源：MCP Tools 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
