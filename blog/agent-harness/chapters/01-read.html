ReAct：行动带来新证据

初学者常把 ReAct 理解为固定格式：先输出一段 Thought，再输出 Action，再输出 Observation。格式确实便于讲解，但真正有价值的是它形成的信息反馈关系。行动使模型获得此前没有的事实；这些事实又改变接下来的决策。ReAct 原论文研究了推理与行动交错的方法，在问答、事实核查和交互环境中进行实验。论文结果依赖当时的模型与任务，不能直接推导出现代 coding agent 的固定收益。来源：ReAct

还是采购任务。系统最初知道预算与交付期限，尚不知道三家报价。第一步读取报价，发现 A 最便宜，但交付日期过晚；第二步读取 B 的新版本规格，发现旧记录里的内存已被更正；第三步计算 B 的含税总价，发现它满足预算。推荐 B 的依据来自这几次观察。若读取新规格后仍按旧规格继续，就是循环结构存在、反馈机制却没有发挥作用。

在代码修复场景中，这个区别更明显。启动测试给出 ModuleNotFoundError: settings，直觉动作可能是安装一个叫 settings 的包。更稳妥的动作是先查看项目布局。如果仓库里已经有 app/settings.py，真正的问题可能是导入路径。运行测试不仅给出失败信号，也应改变下一项检查的方向。修复后重新运行相关测试，才形成一次完整的反馈闭环。

这里的“动作摘要”是供人理解轨迹的简短理由，不代表我们观测到了模型真实的内部思维。ReAct 也不要求把所有内部推理打印到界面上。对执行系统而言，最有用的可观测信息往往是动作名称、经过验证的参数、工具结果、时间、资源版本和停止原因。

循环本身还需要防止空转。连续查询相同文件没有获得新信息，可能说明工具描述模糊，也可能说明模型无法把观察整合进去。harness 可以记录相同调用签名，对无进展重复给出提醒或停止；但不能简单禁止重复读文件，因为文件可能已经被另一项操作修改。重复检测需要结合资源版本与动作副作用。

什么时候不用完整循环？如果用户只是要求把一小段已给出的文字改写，环境没有新事实可提供，一次调用就可能足够。ReAct 的成本来自额外模型调用、工具延迟和更长历史。它值得使用的条件，是下一次观察有机会改变决策，或者执行结果必须经过验证。
