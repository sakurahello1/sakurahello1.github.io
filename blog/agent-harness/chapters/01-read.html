ReAct：行动带来新证据

读完这一讲，你能回答

  • ReAct 里真正值钱的东西是什么：是那三个英文词，还是别的？
  • 一圈循环里，谁决定、谁执行、谁把结果送回去？
  • 为什么“多看一步”有时候能救命，有时候只是白花钱？
  • 循环空转时，harness 靠什么发现，又不能怎么“治”？

先破一个误会：ReAct 不是一种输出格式

很多教程一上来就画一张三行的图：Thought，Action，Observation，然后告诉你“模型就是这样一行一行输出的”。图没有错，但它容易让人把注意力放在格式上：似乎只要让模型按这三个词写字，就有了 agent。

真正起作用的是格式背后的信息关系：模型每做一次行动，就从外部世界拿回一点它此前不知道的事实；这些事实又会改变它下一步怎么走。行动带来新证据，新证据改变决策，这条反馈链才是重点。ReAct 原论文研究的就是推理与行动交错进行的做法，在问答、事实核查和交互环境里做了实验。需要注意，论文的数字属于当时的模型和任务，不能直接搬来推断现代 coding agent 一定有多少收益。来源：ReAct

打个比方。闭卷考试时，你只能凭脑子里已有的东西作答；开卷考试时，你可以先翻资料，翻到的内容会改变你接下来写什么。ReAct 就是让模型从“闭卷”变成“开卷”，而且每翻一页都能根据看到的内容决定翻哪一页。

用采购任务走一遍

回到我们贯穿全课的采购任务：含税预算 7600 元，10 月 5 日前必须交付，三家供应商 clay、ink、paper 各有各的报价和交期。系统一开始只知道预算和期限，不知道任何一家的报价。

这里有三处值得记住：

  1. 模型从头到尾没有执行任何东西。 它每次只是提出请求，执行者始终是 harness。
  2. 报价来自工具，不是模型的记忆。 所以答案里可以带上来源编号，事后能对账。
  3. 第二步的决定依赖第一步的结果。 如果 clay 的报价已经超预算，模型就不会去算它的总价，而是改查下一家。这种“看完再决定”，就是循环带来的价值。

换一个更接近日常开发的场景

启动测试，得到一行报错：ModuleNotFoundError: settings。看到“找不到模块”，最顺手的动作是 pip install settings。可是先查一下项目布局，也许 app/settings.py 早就存在，真正的问题只是导入路径不对。 运行测试不仅告诉你“失败了”，还应该改变你下一项检查的方向。修完再跑一次相关测试，才算走完一个完整的闭环。

有循环，不等于有反馈

看到一个 while 循环里调用了工具，就说它是 ReAct，其实太早了。循环只是结构；反馈是结构上跑着的信息有没有真正改变决策。两者可以脱节。

举一个虚构的例子。假设 harness 缓存了一条 clay 的旧记录：交期 2026-10-09，是很久以前查到的。这一圈模型重新调用 lookup_vendor，拿到的是 quote-clay-v2：交期 2026-10-03。新记录明明把旧记录更正了。如果模型在后面的推理里仍然引用 10-09，那么循环转了、工具调了、结果也写回了上下文，反馈机制却没有发挥作用：新事实进了上下文，没有进入决策。

这也是为什么验收不能只看过程有多“勤奋”。工具调用得再多，也要去核对：最终答案里用到的每个事实，是不是来自最新的观察。后面讲验证的几讲会回到这件事。

一条好的观察，应该带什么

要让新旧信息能被分辨，观察本身就得带足够的元数据。一个采购查询返回的结果，至少应该有这几样：

观察里的内容为什么需要
返回的事实（价格、交期、税率）决策直接依据它
来源编号，比如 quote-clay-v2事后可以对账；也能看出这条和旧版本不是同一份
取得时间或资源版本判断它会不会已经过期；空转检测也要用到版本（见下文）
是否成功，以及错误信息失败同样是观察：让模型看见“被拒绝”，它才可能换一条路

把工具结果当成“事实”直接塞回去

工具返回的内容也可能过期、出错，甚至在后面的课里你会看到，它也可能被别人动过手脚。写回上下文时，带上来源和版本，比只写数值更值得。

这里的“动作摘要”，是给人看的简短理由，用来帮读者理解这条轨迹。它不代表我们观察到了模型真实的内部思考，ReAct 也没有要求把所有内部推理都显示在界面上。对执行系统来说，往往最有用、也便于事后核对的信息是：动作名称、通过校验的参数、工具结果、时间、资源版本，以及最后为什么停止。

别把“写出来的理由”当成证据

模型写一段头头是道的理由，并不能证明那段理由就是它决定动作的真实原因。要判断一次运行对不对，看的是工具返回了什么、验收器查到了什么，而不是模型自己怎么解释。

循环会空转，harness 要能发现

循环有一个天然的风险：模型反复做没有新信息的事。比如连续三次读同一个文件，每次得到一模一样的内容，却不肯换个思路。

所以不能简单地“禁止重复读文件”：修改文件之后再读一次，是完全正常的验证。重复检测要结合资源版本和动作的副作用来看。重复也不一定是模型的问题，也可能是工具描述含糊，模型根本没读懂结果。

什么时候不用完整循环

循环不是免费的。每多一圈，就多一次模型调用、一次工具延迟，上下文也更长。

场景要不要完整循环原因
把一小段已给出的文字改写不用，一次调用就够环境里没有新事实可拿，多转几圈只是浪费
查三家报价再比较要每一次查询的结果都会影响下一步查谁、算什么
修复一个测试失败要不看报错就动手是猜，改完不重跑无法确认
结果必须经过验证要，且要有独立验证见后面“验证”部分几讲

一句话：下一次观察有机会改变决策，或者执行结果必须经过验证，循环才值得。

小结

  • ReAct 的价值不在 Thought / Action / Observation 三个词，而在行动带来新证据、新证据改变决策这条反馈链。
  • 一圈循环里：模型只负责提出下一步，harness 负责校验与执行，结果再写回上下文。
  • “动作摘要”是给人看的解释，不是模型内部思考的记录；更可靠的依据是工具结果和验收结果。
  • 空转要靠“调用签名 + 资源版本”联合判断，不能简单禁止重复。
  • 循环有成本：只有下一次观察可能改变决策，或结果必须验证时，才值得完整循环。
