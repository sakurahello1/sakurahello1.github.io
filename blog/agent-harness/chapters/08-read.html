Claude Code compact与恢复

一次压缩最容易丢失的，往往是后来才显得重要的细节。早期用户说“只能建议，不能下单”，中间讨论了几十轮价格，压缩后只剩“为用户选择电脑”。新上下文可能继续优化推荐，却失去了动作边界。另一个常见问题是把进行中的后台任务忘掉，重新启动第二个测试或导出作业。

可以把 compaction 理解成一次有损状态迁移：旧上下文退出，新的上下文要继承完成任务所需的最小状态。自然语言摘要可以是其中一部分，但稳定规则、文件、运行中操作与可恢复证据也应有明确路径。

Claude Code 的公开文档提供了一个具体案例。依据 2026 年 9 月 30 日读取的页面，文档提到 v2.1.198 的摘要请求继承会话 thinking 配置；压缩后会重新注入根级 CLAUDE.md、无路径限定规则、auto memory 与计划等内容，路径相关规则随后续文件读取再加载。它还描述了重读部分近期文件、技能内容重注入及后台任务提醒等机制。这些细节说明，产品并不只依赖“一段万能摘要”恢复现场。来源：Claude Code Context Window

实现细节有明确版本性。例如当前页面写到最多重读五个已读或编辑文件，较大文件可能只保留路径；技能正文重注入也有单项和总量预算。学习这些设计时，更值得带走的是“分类恢复、保留索引、避免重复运行”的思想。不要把某个版本的数值写成所有 agent 都必须遵守的规则，也不要把这些产品行为推断为某种通用压缩算法的最优解。

如果自己写 harness，可以从结构化检查点开始：

{
  "goal": "比较供应商并给出建议，不下单",
  "completion": "推荐满足预算和日期，且引用当前报价",
  "constraints": {"budget_cny": 8000, "deadline": "2026-10-10"},
  "source_versions": {"B": "quote-B-v2"},
  "verified": ["已按 v2 报价确认 B 总价为 7800 元"],
  "pending": [{"job_id": "delivery-check-17", "state": "running"}],
  "next_action": "查询 delivery-check-17，不重新提交任务",
  "unknown": ["最终交付承诺仍待核实"],
  "evidence": ["artifact://quotes/quote-B-v2"]
}

这个模板是工程建议，并非 Claude Code 的内部摘要格式。重要之处在于区分“已验证”与“尚未知晓”，以及明确记录进行中的操作。新一轮启动后，也不能无条件相信检查点里的状态：报价版本可能又更新，后台任务可能已经结束，仓库 HEAD 可能变化。恢复应先核对最关键的外部状态，再执行下一项动作。

压缩质量可以直接测试。构造一个长任务，早期给三条硬约束，中途修改一条，再加入大量无关日志。压缩后要求继续完成任务，观察旧约束是否被错误复活、已完成工作是否重复、精确证据能否找回。保留完整历史作为对照，同时比较自由摘要、结构化检查点、检查点加原文检索。我们关心的是恢复成功，而不只是摘要看起来简洁。来源：Effective harnesses for long-running agents
