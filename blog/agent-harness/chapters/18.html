  • 一次审批应该发生在什么时刻，审批界面至少要回答哪几个问题？
  • 两个验证器意见不一时，什么时候该去查，什么时候该去问人？
  • 升级给人时要交代什么？怎样知道人工介入真的起了作用？

每一步都问，等于没问

装软件时，你大概见过这样的安装向导：“下一步”“下一步”“我同意”“下一步”。点到第五次，几乎没人还在读窗口里写了什么，某一页上默认勾好的“顺便安装浏览器工具栏”，就这样被一路确认了过去。

agent 也一样。把每一步都弹出“是否继续”，不等于实现了安全。用户很快会机械地点确认，而系统把本应承担的判断负担转移给了人：出了事，记录上写着“用户已确认”，可用户点下去的那一刻，既没有足够的信息，也没有足够的注意力去判断。这种一路点确认、越点越不看的现象，常被叫作审批疲劳。

反过来，把所有步骤都隐藏在“全自动”背后，也会使用户直到后果发生才知道 agent 如何解释了任务。设想用户只说了一句“买一台笔记本，预算 7600 元”，agent 把预算理解成了不含税的标价，于是 paper 的 7100 元看起来在预算内；等账单寄来，用户才发现含税是 7810 元（示意）。误解发生在第一步，暴露在最后一步。

所以 Human-in-the-loop（HITL，人在环中：在 agent 的运行流程里安排人的判断）这个词本身说明不了什么。好的人工介入设计，需要说明人到底在控制什么：控制哪个决定，在什么时刻，凭什么信息。

人可以站在四个位置

提到“人工介入”，多数人想到的是运行中的确认弹窗。其实那只是四个位置之一。控制位置可以分成四层：

  1. 任务开始前，人确定目标、资源范围、预算和不可触碰的边界。
  2. 运行中，对高风险、不可逆或授权不清的动作进行审批。
  3. 完成后，人抽样检查、验收，并决定是否回滚。
  4. 长期治理，人维护政策、评估集与升级机制。

把这四个位置放到采购任务上，人在每一处控制的东西都不一样：

位置人控制的是什么采购任务里的样子
任务开始前目标、资源范围、预算、边界含税预算 7600 元，10-05 前交付，只在 clay、ink、paper 里选，只买一台
运行中高风险、不可逆、授权不清的动作查报价、算总价不问人；真正下单时停下来问
完成后抽样检查、验收、是否回滚核对订单、总价和报价来源是否一致，决定是否撤单
长期治理政策、评估集、升级机制发现“预算”常被误读成不含税，就写进政策和测试用例

这张表说明了一件容易被忽略的事：一个无需逐次点击确认的流程，仍然可以在人设定的狭窄空间里运行。是否有人逐步盯着屏幕，与是否存在有效的人类控制，并不是同一个问题。范围、预算和边界定得好，运行中需要人拍板的时刻就会很少，而每一次都值得认真看。

四个位置各有代价。任务开始前的边界要求人事先把约束说清楚，可人想不到所有情况；运行中的审批最直接，却会打断人、拖慢任务；完成后的验收不打扰运行，但只能补救那些还能撤回的错误；长期治理见效最慢，要攒够一批运行记录才知道该改什么。所以不要把控制全压在某一个位置上，尤其不要全压在运行中的弹窗上。

一个不逐次确认、却处处有人控制的流程

一个每周整理销售周报的助手（虚构）：任务开始前，负责人规定了它只能读内部销售表、只能把周报发给本组、不能对外发送；运行中，它从读数据到生成周报都不需要任何确认；完成后，负责人每周一抽看周报里的几个数字；有一次发现汇总数和明细对不上，团队就在政策里加了一条“发送前核对合计”，并把这个例子放进评估集。整个过程没有一个确认弹窗，可人在三个位置上都握着控制。

在对的时刻，批准具体的动作

考虑一个邮件助手。读取用户指定的线程、归纳观点、在私有草稿中准备回复，通常有明确且可逆的边界：草稿写坏了，删掉重写就是。发送给外部联系人则不同，它改变了外部世界；如果内容包含报价承诺或敏感个人信息，错误成本更高。

审批应该发生在信息足够完整、动作尚未执行的时刻。太早，人还不知道 agent 要做什么；太晚，事情已经做完了。让用户在一开始批准一个抽象的“处理此事”，然后由 agent 自行选择收件人、承诺金额和附件，不是充分知情的控制。

审批界面至少应回答六个问题：将执行什么动作，对谁或哪个资源执行，会发送哪些数据，会形成什么承诺，能否撤回，以及支持这个动作的证据是什么。

审批也不必一条一条来。对于差异很小的重复操作，可以在政策允许范围内提前批准一个清晰的批次，比如“给这 20 位已确认的内部同事发送同一份会议纪要”（示意）。但目标、数据范围、金额或风险发生实质变化时，原来的授权不能无限外推。批准应该绑定具体动作及其参数，不能只是聊天记录里孤立的一个“好”。怎样把动作规范化、取指纹、设有效期，第 26 讲会给出代码。

下面的实验是一道最小的审批门。“模型提议”下拉框里有四个 agent 可能提出的动作，选一个，点“交给 harness”，看它沿着“外部数据 → 模型提议 → 策略门 → 执行器 → 实际状态”这条流水线走多远。依次试一遍：读取 clay 的报价一路放行，没有问你；把报价写到 /etc/quotes、把 API key 发往备注里的网址，都在策略门被直接拒绝，也没有问你；只有“真的下单买 clay”停在策略门，弹出“需要你批准”的卡片。四个动作里只有一个需要人，这正是本讲想要的分配：规则能判断的，不打扰人。再拿上面六个问题审一审这张卡片：动作、对象和金额（clay × 1，含税 7480 元）写了，“只批准这一次”交代了授权范围；报价来源 quote-clay-v2 和能否撤回没有写，真实系统里应当补上。先点“拒绝”，再重跑一次点“批准这一次”，比较两次的结果。页面里没有真实的下单或网络执行器，“执行”只是记录。

什么分歧值得打扰人

两位同事，一个说会议室订在三楼，一个说订在五楼，你会打开预订系统查一下，而不是召集大家投票。另外两位同事，一个觉得海报应该更简洁，一个觉得信息太少，这就没有系统可查了，只能去问负责这张海报的人到底想要什么。

agent 系统里也有这两类分歧。人工应该处理的，是无法由客观事实消解的那一类。

系统应区分价值判断缺失与可通过工具解决的事实分歧。前者交给人，是因为答案本来就在人那里：用户偏好什么、品牌要什么、先保哪一头，模型再聪明也只能猜。后者交给人，则是把本该由机器完成的核对工作推给了人，人多半也只能去做同样的检查，还白白多了一次打扰。

问人的时候，问题要具体。“你觉得这样可以吗？”几乎没有信息量；“A 方案一屏放下全部参数但字很小，B 方案只放三项核心参数、其余折叠，你更看重哪一点？”才让人能在几秒钟里给出一个有用的回答。

升级给人时，说清为什么

客服把电话转给主管时，如果只说“这个你来处理一下”，主管得从头再问一遍；如果说“客户要求退全款，理由是商品破损，照片在工单里，按规定我最多只能退一半”，主管三十秒就能拍板。

agent 把问题交给人，叫作升级（escalation）。一种实用做法是把升级原因写进状态机，也就是一张事先定义好的表：系统处在哪种状态、遇到什么情况、下一步去哪。升级原因可以分成五种：授权缺失、目标冲突、证据不足、不可逆动作、环境漂移。每一种原因都有明确的下一步，而不是统一返回“需要人工”。

升级原因交给人的信息采购任务里的例子（示意）
授权缺失需要哪项权限，为什么需要要调用下单接口，但这次任务只授权了查询
目标冲突几个选项，以及各自的代价用户既说“越便宜越好”，又说“最好 10-05 前到”：ink 含税 7040 元但 10-12 才到，clay 含税 7480 元能按时到
证据不足已经检查了哪些条件，哪些无法检查查到了 clay 的价格，但交期字段缺失，无法确认 10-05 前能到
不可逆动作一张回答了六个问题的审批卡下单 clay × 1，含税 7480 元，来源 quote-clay-v2
环境漂移哪里变了，变化前后有什么不同下单前复查，发现报价编号已经不是 quote-clay-v2

每一行背后是同一个原则：缺权限时说明需要哪项权限以及为什么；证据不足时列出已经检查与无法检查的条件；目标冲突时展示选项及代价；不可逆动作给出完整的审批卡；环境漂移说清变化本身，让人判断原来的计划还算不算数。把原因分开还有一个好处：事后可以统计哪一类升级最多。如果“授权缺失”占了大头，该改的是任务开始前的授权范围；如果“证据不足”占了大头，该补的是工具和数据。

人的注意力是稀缺资源

人类注意力是稀缺资源。harness 的职责之一，就是把这份资源保留给机器无法可靠代替的决策，并在交出去的时候，把做决定所需的信息一次备齐。

人也会出错：把审批当成要测量的东西

人也会出错，尤其在上下文不足和时间压力下。一个在第四十次弹窗前已经连续点了三十九次“确认”的人，看到第四十张卡片时，很可能也只花一秒。因此 HITL 的效果要测量，而不是默认它是万能兜底。

其中误批准率不会自己出现在日志里：审批当时没人知道这一单该不该批。一种做法是定期抽出一批已经批准的动作，交给另一个人在不赶时间的情况下重审，看其中有多少本该拒绝。

两种信号尤其值得注意。若每百次审批只有一次真正值得停下来，应该研究另外九十九次能否被更好的范围约束替代：把它们挪到“任务开始前”那个位置，一次定好规则。若重要风险常被一眼略过，则需要改进信息展示，比如把“能否撤回”“承诺金额”放到卡片最显眼的地方，而非继续堆叠更多警告文字。

用“用户已确认”代替安全

审批记录只能说明“有人点了按钮”，不能说明“有人看懂了风险”。如果一套系统出事后的第一反应是翻出确认记录、证明责任在用户，这套审批多半只是在转移判断负担。衡量它的，应该是上表那些数字，而不是弹窗的数量。

小结

  • 每一步都弹窗确认，会让人机械点击，把判断负担转给了没有足够信息的人；全自动则让人直到后果发生才知道 agent 怎样理解了任务。
  • 人可以在四个位置控制 agent：任务开始前划定目标、范围、预算和边界，运行中审批高风险动作，完成后抽样验收与回滚，长期维护政策、评估集与升级机制；有人盯着屏幕不等于有有效控制。
  • 审批应落在信息完整、动作未执行的时刻，回答动作、对象、数据、承诺、能否撤回和证据六个问题，并绑定具体参数；目标、数据、金额或风险变了，就要重新批准。
  • 价值判断缺失交给人，并提出具体问题；可以用工具查清的事实分歧，先查路径、版本和环境，不要急着打断用户。
  • 升级原因写进状态机，每种原因交代不同的信息；HITL 的效果要用审批量、等待时间、误批准率等数字来测量，而不是默认它是兜底。
