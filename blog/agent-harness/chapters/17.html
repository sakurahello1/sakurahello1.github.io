许多 agent 演示有一个视觉错觉：当系统能看截图、移动鼠标、点击按钮时，我们容易觉得它已经像人一样看到了全部情况。实际上，截图只是某一时刻、某个视口中的像素。它能揭示标题被遮挡，却不能证明保存已经持久化；能看到按钮，却不能证明按钮绑定了正确事件；能显示报表数值，却不能说明这些数值来自最新的数据源。

因此，多模态验证的出发点不应该是“多加几种输入”，而应该是列出失败模式，再选择有辨别力的观测。界面排版问题要看实际渲染；可访问性问题需要检查语义结构和键盘操作；交互问题需要执行状态转换；权限和持久化问题需要跨会话、跨身份验证；性能问题需要耗时、网络请求与服务指标。不同模态可以互相补充，也可能互相矛盾，而矛盾正是值得继续调查的信号。

以“用户能编辑个人资料并保存”为例。DOM 可以告诉我们输入框有正确的 label，自动化脚本能够定位并填写；截图可以检查小屏幕下保存按钮是否被固定底栏盖住；网络记录可以确认请求确实发出以及响应是否异常；重新打开页面可以检查用户实际能否找回修改；数据库或可信 API 可以进一步确认写入的是正确用户、正确字段。这里不要求每个产品都拥有数据库直连权限。无法访问持久层时，跨会话重开仍然比仅看一次 toast 更强，只是证据边界不同。

OSWorld 将真实计算机环境中的多模态操作与执行式评估结合起来，提供了一个具体范例：agent 使用什么观察来行动，和评估器检查什么环境状态来判断成功，是两个可以分离的问题。它并不意味着所有桌面任务都能被现成脚本完美验收。来源：OSWorld

视觉评价尤其需要具体标准。“做得更高级”会让评估器追逐自己的审美；“在 360 像素宽的视口下，正文不横向溢出，主要操作无需横向滚动，文本与背景具有足够可辨识度”更容易检查。主观体验仍然存在，但可以用目标读者、反例、参考样式和人工标注样本校准。数字评分也不应该掩盖不同维度：一个漂亮但不能保存的页面，不能靠美观得分抵消数据丢失。

实际系统可以给每条证据加上采集时间、环境标识和对象版本。例如截图属于 build-17，而数据库检查来自 build-16，就不能把两者拼成同一版本已经通过的证明。异步系统还要明确等待条件：点击保存之后，等待的是按钮恢复可点、请求返回，还是新值已经能通过独立读取看到？固定睡眠三秒只说明等了三秒，不说明系统达到了目标状态。

以下是可选的其他供应商示例，需另配OPENAI_API_KEY与支持视觉的模型，不沿用本页DeepSeek凭据或baseURL。APPROVED_SCREENSHOT_URL必须指向已明确授权发送的截图；仅为接口示意，开发未在线调用。

在 OpenAI 官方 Python SDK 中，可以通过 Responses API 向支持图像输入的模型传入文本与截图 URL。下面演示的是视觉审阅这一小环节，模型名与图像权限须由部署环境配置；它没有代替浏览器执行、持久层检查或最终完成门。接口依据：OpenAI Python SDK

import os
from openai import OpenAI

client = OpenAI()
response = client.responses.create(
    model=os.environ["OPENAI_VISION_MODEL"],
    input=[{
        "role": "user",
        "content": [
            {"type": "input_text", "text": (
                "按提供的视觉验收条件审阅截图。"
                "仅判断画面能支持的主张；"
                "不可推断保存、权限或点击是否有效。"
                "条件：主要按钮无遮挡，正文无明显裁切。"
            )},
            {"type": "input_image", "image_url": os.environ["APPROVED_SCREENSHOT_URL"]},
        ],
    }],
)
visual_review = response.output_text

截图上传本身也属于数据传输。包含客户记录、私人消息或令牌的画面，不能因为目的是“验证”就自动获得外发许可。先裁减不必要区域、脱敏、确认数据处理边界，再采集所需证据。多模态带来的是更丰富的观察能力，同时也增加了隐私与成本负担；采集策略应该由验收需要决定。
