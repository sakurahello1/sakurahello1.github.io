截图里什么都有，又什么都没有

看 agent 操作电脑的演示，容易产生一种视觉错觉：它能看截图、移动鼠标、点击按钮，我们便觉得它已经像人一样看到了全部情况。

先看清截图是什么。截图是某一时刻、某个视口中的像素。视口（viewport）指浏览器窗口当前显示的那块区域：滚动到下面的内容不在里面，窗口换一个宽度，排版也可能完全不同。所以截图能回答的问题很具体，也很有限：

  • 它能揭示标题被遮挡，却不能证明保存已经持久化（写进了关掉页面也不会丢的存储）。
  • 它能看到按钮，却不能证明按钮绑定了正确的事件。
  • 它能显示报表数值，却不能说明这些数值来自最新的数据源。

你很可能遇到过这样的事：在网页上改了资料，点保存，角落里弹出一条绿色的“保存成功”，刷新之后改动却不见了。这种短暂出现的提示条常被叫作 toast。它由前端代码直接画出来，有的页面为了显得快，不等服务器回话就先把它弹出来。截图拍到这条提示，只能说明前端代码运行到了“显示提示”那一行。

这一讲说的多模态验证，就是把截图、页面结构、网络记录、存储状态等不同种类的观测组合起来，让每一种去回答它擅长的那个问题。点图里的方块，可以看到每一站可能出什么错。

先列失败模式，再挑观测

医生不会给每位病人都做全套检查。他先想“可能是哪几种病”，再挑能把它们区分开的那项检查。验证也应该这样做：多模态验证的出发点不是“多加几种输入”，而是先列出失败模式，再选择有辨别力的观测。

“有辨别力”的意思是：有缺陷和没有缺陷时，这项观测的结果不一样。上面那条提示条就几乎没有辨别力，保存成功时它出现，保存失败时它也可能出现，看一百次也分不出这两种情况。

不同的失败模式，要找不同的观测。表里的可访问性（accessibility）指读屏软件用户、只用键盘的用户也能正常使用界面；浏览器会把页面整理成一棵“可访问性树”，记录每个元素是什么、叫什么名字。

失败模式有辨别力的观测这种观测回答不了的
排版：遮挡、裁切、溢出按目标视口宽度渲染出的截图数据有没有写入
可访问性语义结构与键盘操作画面在视觉上是否清楚
交互真正执行一次状态转换，看状态是否改变改变有没有持久化
权限与持久化跨会话重开，换一个身份再读小屏幕上的排版
性能耗时、网络请求与服务指标功能本身对不对

以“用户能编辑个人资料并保存”为例，几种观测各司其职。DOM（浏览器里表示页面结构的元素树）可以告诉我们输入框有正确的 label，自动化脚本能够定位并填写；截图可以检查小屏幕下保存按钮是否被固定底栏盖住；网络记录可以确认请求确实发出，以及响应是否异常；重新打开页面，可以检查用户实际能否找回修改；数据库或可信 API 可以进一步确认写入的是正确用户、正确字段。

不同模态可以互相补充，也可能互相矛盾，而矛盾正是值得继续调查的信号。看一个专门骗过浅层证据的缺陷：修改被写进了另一个用户的记录，而页面显示的内容来自浏览器的本地缓存。

这里不要求每个产品都拥有数据库直连权限。无法访问持久层时，跨会话重开仍然比仅看一次 toast 更强，只是证据边界不同：它能证明“离开这个页面之后还读得回来”，却不能证明写进了正确的那一行。要让重开真的“跨会话”，最好换一个干净的会话去读，比如换一个浏览器配置，或者先清掉本地缓存，否则就会像上图第四层那样，读到的还是自己的缓存。报告里应当写明用了哪种证据、边界在哪里，不要把“刷新后还在”写成“已写入数据库”。

没看到问题，不等于通过

一种证据看不到某类缺陷时，它给出的“没问题”没有信息量。这时正确的结论是“证据不足”，并说明缺的是哪一类证据，而不是 PASS。一个判定只有在“有缺陷时它会失败”的前提下，它的“通过”才有意义。

下面的实验把这张表做成了一个小装置。一个笔记应用要把“周五交报价单”改成“周四交报价单”。你先在“埋下的缺陷”里暗中放一个问题，再在“验证手段”里选一种证据，点“运行并验收”。三张卡片（界面、数据库、trace）里被点亮的，就是这次验收真正看过的证据；trace 是运行过程的记录。建议按这个顺序试：先埋“保存按钮被弹窗挡住”，选“看一张截图”，截图就能识破；再埋“只存在内存里，刷新就没”，还用截图，结论变成“证据不足”，换成“点击后刷新页面再看”才能识破；最后埋“写进了另一个用户的记录”，刷新也会被骗过，只有“刷新 + 查数据库 + 查 trace”能看到数据库里多出来的 user_b 那一行。也试一次“没有缺陷”配“看一张截图”：明明没有问题，实验仍然判“证据不足”，因为这份证据分不出有缺陷和没缺陷。页面里的缺陷，以及“哪种证据能看到哪种缺陷”，都是预设的故障模型，用来说明证据强弱，不是某个评估器的实测结果。

用来行动的眼睛，和用来判定的眼睛

考过驾照的人对这个安排不陌生：学员靠自己的眼睛看路、打方向盘，判定有没有压线的却是场地里的传感器。学员觉得自己开得很稳，并不影响系统记下一次压线。

agent 操作界面时，也可以有两双眼睛。一双用来行动：agent 看截图、读可访问性树，决定下一步点哪里。另一双用来判定：任务结束后，检查环境是否真的到达了目标状态。OSWorld 将真实计算机环境中的多模态操作与执行式评估结合起来，提供了一个具体范例：agent 使用什么观察来行动，和评估器检查什么环境状态来判断成功，是两个可以分离的问题。来源：OSWorld 这里的执行式评估，是指运行检查程序去读取环境的实际状态，比如某个文件是否存在、某项设置是否变成了目标值，而不是去读 agent 的自述。

为什么要分开？如果判定也只看 agent 看过的那几张图，agent 的盲区就会原封不动地变成评估器的盲区：被弹窗挡住的地方，两者都看不见；页面读的是缓存，两者都被骗。这正是第 16 讲说的独立性：验证者要有一条不经过被验证者的证据来源。

本课的采购任务也是这样验收的。验收器不读模型写的解释，只检查最终 JSON：能否解析、供应商是不是 clay、含税总价是不是 7480 元、来源是不是 quote-clay-v2、交期是不是 2026-10-03。界面任务的验收器，同样应该尽量去读状态。

这种分离也有代价。检查程序要有人写，要有读取权限，任务一变，检查也得跟着改。有些目标本来就没有能用脚本读出的“正确状态”，比如一个页面看起来是否清楚。OSWorld 是一个范例，但它并不意味着所有桌面任务都能被现成脚本完美验收。剩下的那部分，要靠写得足够具体的视觉标准。

视觉标准：写成能检查的句子

装修时对师傅说“弄得高级一点”，结果多半是师傅心目中的高级。换成“踢脚线和墙面齐平，缝隙不超过一毫米”（示意），双方就能拿尺子对着量。

视觉评价尤其需要具体标准。“做得更高级”会让评估器，不管是人还是模型，去追逐自己的审美；“在 360 像素宽的视口下，正文不横向溢出，主要操作无需横向滚动，文本与背景具有足够可辨识度”更容易检查。后一句的每个短语都对应一次能执行的观测：把视口设成 360 像素宽，看页面有没有超出；找到主要按钮，看它不滚动时是否可见；检查文字和背景的颜色差异。

模糊的说法可检查的写法（示意）
做得更高级360 像素宽的视口下，正文不横向溢出，主要操作无需横向滚动
按钮要醒目主要按钮在首屏可见，没有被固定底栏或弹窗遮挡
文字要清楚文本与背景具有足够可辨识度，正文没有被裁切

主观体验仍然存在，不是所有感受都能写成规则。这部分可以用目标读者、反例、参考样式和人工标注样本来校准：告诉评估器页面是给谁看的，给它几个“不合格”的反例和一个“合格”的参考，再拿一批人工标过的截图，检查它的判断和人是否一致。

用一个总分掩盖不同维度

数字评分不应该掩盖不同维度：一个漂亮但不能保存的页面，不能靠美观得分抵消数据丢失。比如（虚构）美观 9 分、功能 0 分，平均下来 4.5 分，看上去“还凑合”，用户的修改却全丢了。功能和数据正确性这类维度应当各设门槛，任何一项不过就不通过，而不是和其他分数加在一起。

等待要有条件，证据要带标签

网页、服务器、数据库各自按自己的节奏工作。点下保存之后，提示条出现、请求返回、数据落盘，并不发生在同一时刻。这样的系统叫异步系统。验证它时，验收脚本必须写明等待条件：点击保存之后，等待的是按钮恢复可点、请求返回，还是新值已经能通过独立读取看到？

固定睡眠三秒只说明等了三秒，不说明系统达到了目标状态。服务端快的时候，三秒绰绰有余；慢的时候，截图拍下的只是一个还没发生的“成功”。几种等待条件能证明的东西差别很大：

等待条件满足时说明了什么仍然说明不了什么
固定睡三秒过去了三秒系统有没有到达任何状态
按钮恢复可点前端认为这次提交结束了服务端有没有写入
请求返回成功服务端接受了这次请求写入的对象对不对，能不能读回
独立读取看到新值新值在页面之外也读得到这次读取没有覆盖的用户和字段

好的等待条件还要配一个超时上限：在上限内等到了，就进入判定；等不到，就判失败并记下最后一次读取的结果，而不是无限期地等。

时间还带来另一个问题。去医院体检，每张化验单上都印着姓名、日期和检查科室；把一个人上个月的血常规和另一个人今天的心电图订在一起，谁也不会把它当成一份体检报告。验证证据也需要这样的标签：实际系统可以给每条证据加上采集时间、环境标识和对象版本。

多记这几个字段，代价只是采集时多写几行；换来的是任何一份证据都能被追问一句：你说的是哪个系统、哪个时刻？

留意提示词里的两句限制：“仅判断画面能支持的主张”“不可推断保存、权限或点击是否有效”。它们对应这一讲的第一张图：模型看到的也只是像素，它能判断按钮有没有被遮挡、正文有没有被裁切，却和截图本身一样，不知道数据存没存。验收条件也写成了上一节那种可检查的句子，而不是“看看好不好看”。所以 visual_review 只是一份证据：它要带上这张截图的时间、环境和版本标签，和其他证据一起进入完成门，而不是直接成为“任务完成”的依据。

还有一件容易忽略的事：截图上传本身也属于数据传输。包含客户记录、私人消息或令牌的画面，不能因为目的是“验证”就自动获得外发许可。先裁减不必要区域、脱敏、确认数据处理边界，再采集所需证据。

采集多少，由验收需要决定

多模态带来的是更丰富的观察能力，同时也增加了隐私与成本负担：每多拍一张图、多传一次，就多一份存储、传输和审阅的开销，也多一次泄露的机会。采集策略应该由验收需要决定：要回答哪个问题，就采集能回答它的那一份证据。

小结

  • 截图是某一时刻、某个视口里的像素：它能回答“用户看到了什么”，回答不了“系统存下了什么”；提示条和数据写入走的是两条路。
  • 多模态验证先列失败模式，再挑有辨别力的观测：排版看渲染，可访问性看语义结构和键盘，交互要执行状态转换，权限与持久化要跨会话、跨身份，性能看耗时与请求。
  • 不同证据互相矛盾时，不投票也不取平均，矛盾就是继续调查的线索；看不到某类缺陷的证据只能给出“证据不足”，不能给出 PASS。
  • 用来行动的观察和用来判定的状态可以分开，验收尽量直接读状态；OSWorld 是这种组合的范例，但不是所有任务都有现成脚本可验。
  • 视觉标准要写成可检查的句子，关键维度各设门槛；等待要写明条件而不是固定睡眠，证据要带时间、环境和版本标签。
  • 截图外发也是数据传输：先裁剪、脱敏、确认边界，采集多少由验收需要决定。
