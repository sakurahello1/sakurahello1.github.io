Trace与replay：可见不等于可复现

当 agent 失败时，最终答案往往是最不够用的证据。“无法完成”没有告诉我们是搜索没找到、工具超时、权限被拒绝、保存失败，还是验证器误判。另一方面，把全部运行文本无差别保存，也会产生隐私与排查负担。可观测性的目标，是记录足够重建外部事件的结构化信息。

一个最小 trace 应包含运行 ID、父子任务关系、模型与工具版本、目标和验收版本、工具输入输出引用、时间戳、权限判定、产物哈希、预算使用及终态原因。关键状态变化应有快照或可重新读取的对象。这里需要的是可观察的决策与行动证据，不需要公开模型的完整私有思维链；一段很长的推理文字也不能代替真实工具结果。

以前面的假保存为例，单看最终截图无法知道发生了什么。把点击事件、网络请求、响应错误、toast 出现和数据库快照按时间关联后，就能发现界面在写入失败时仍显示成功。Playwright Trace Viewer 将动作、DOM 快照、截图、网络与控制台信息关联起来，展示了浏览器任务中这种时间对齐的价值。来源：Playwright Trace Viewer

多 agent 系统还要保留因果关系。一个结论是哪个 worker 提出的，来自哪个版本的资料，主节点什么时候采用，之后触发了什么动作？仅按时间排序所有日志，不一定能还原并行因果。为消息保留 task_id、parent_id、caused_by 和版本引用，可以追踪错误从哪里进入、在哪次压缩中丢掉限制条件，又在哪一步被当成确定事实。

“回放”至少有三种含义。审计回放只是展示已经记录的动作和证据；环境重放是在冻结的初始状态或模拟工具响应上重建执行；重新采样则是再次向模型发送相同输入。它们的可重复性不同。模型服务、检索结果、时间、随机性和外部状态都会变化，因此看得见 trace，不代表下一次执行必然逐字逐步一致。

尤其不能把审计记录直接当执行脚本。重新发送邮件、重新创建订单或再次扣款会产生副作用。安全的重放应使用隔离环境、模拟服务或幂等机制，并明确哪些步骤只展示、哪些真的执行。对外部请求采用幂等键之前，还要确认目标服务的语义与有效期；本地给请求贴一个标签，并不自动让远端操作具备幂等性。

OpenAI Agents SDK 提供模型调用、工具、handoff 和自定义事件的 tracing 能力，但采集内容可能包含敏感输入输出。生产系统应审查当前版本的配置、存储位置、访问控制和保留期，而不是默认“调试日志不算用户数据”。来源：OpenAI Agents SDK tracing 文档

日志策略可以采用最小化原则：记录动作类型和资源标识，敏感正文按需要脱敏或存为受控引用；为不同角色提供不同可见范围；设置明确保留期限。对证据做哈希有助于确认完整性，但哈希本身不让原始内容脱敏，也不证明内容正确。加密、权限和数据删除仍然需要独立设计。

排查时应先给失败分类，再修改系统。工具超时不一定需要换模型；验收过严不应该通过改坏正确实现来迎合；权限拒绝不应通过另找通道绕过。只有能区分环境、执行、协调、授权与评分错误，迭代才会朝正确方向前进。trace 的价值不是让演示更炫，而是让工程判断有证据可依。
