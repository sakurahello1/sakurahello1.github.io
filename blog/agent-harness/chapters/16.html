“请再检查一遍”是最便宜的可靠性技巧，也最容易被过度解释。模型再次阅读自己的答案，可能发现算术疏漏、变量遗漏或前后矛盾；也可能把正确答案改错。重复推理给了模型另一次机会，却没有自动带来新的事实。如果第一次失败源于未知的 API 行为，再写两千字自我反思通常无法替代一次真实调用。

讨论自纠错时，应分开三种活动。内生纠错是在没有新增环境信息时重新分析已有问题与答案。外部证据纠错是执行程序、读取日志、查询事实或实际操作界面，利用新的观测改变判断。交互式澄清则处理目标本身的歧义：用户说“尽量快”，究竟愿意牺牲多少成本或质量？这种问题没有一个测试可以替用户作决定。把三者统称为 reflection，会掩盖它们不同的信息来源和失败方式。

研究结论也不适合压缩成“LLM 不能自纠错”。2023 年的《Large Language Models Cannot Self-Correct Reasoning Yet》发现，被测模型在若干无外部反馈的推理设置中，内生纠错能力有限，有时出现退化。之后的 SCoRe 使用专门的多轮强化学习训练，展示了内生纠错的改善。二者研究的模型、训练方法和实验条件不同，不能拿一个标题取消另一个结果。来源：2023 年自纠错研究；SCoRe

对工程师而言，更有用的问题是：这一轮修正引入了什么信息？假设 agent 写出一个日期比较函数，把字符串按字典序排序。当所有日期都是 ISO 格式时，几个样例可能恰好通过；面对“9/30/2026”和“10/1/2026”，问题才暴露。让模型“认真检查”可能碰巧想到格式差异，但运行覆盖不同格式的测试，能把一个模糊怀疑变成可复核的反例。修正之后，再运行原来的成功案例，才能知道它有没有修好一处又弄坏另一处。

外部证据同样需要审查。一条报错可能来自测试环境缺少依赖，而不是实现错误；一个网页可能过时；数据库查询可能连错实例。验证反馈应尽量包含可定位的信息：输入、期望、实际输出、环境版本，以及最小复现步骤。“测试失败，请修复”虽然简短，却可能逼着 agent 在没有依据时猜测。相反，把十万行日志全部塞进上下文，也可能淹没关键异常。好的反馈是经过选择的证据，不是越长越好的上下文。

如果要测量一种反思提示是否有效，不能只展示一个修好的例子。可以准备一组有确定答案的小程序题，保存模型的首次回答，然后分别进行无新增信息的复查、带测试反馈的修复、以及独立重新采样。让各组使用相近的总预算，记录错误改对、正确改错、保持不变三种转移。若只统计错误题里有多少被救回来，忽略原本正确的题被破坏了多少，会系统性高估方法收益。这是本教程建议的实验，并未声称已复现任何论文数值。

纠错循环还需要明确的终止条件。失败证据相同、修复动作相同、结果也相同，说明循环没有取得信息进展；继续盲目重试只会消耗预算。系统可以尝试不同诊断工具、缩小复现范围，或者在授权范围内恢复到上一个稳定版本。当问题是缺失权限、需求冲突或外部服务不可用时，应报告真实阻碍。它不应靠把“仍未验证”改写成“基本完成”来结束任务。

一个务实的顺序是：先让廉价、确定的检查筛掉明显问题；再针对失败收集新证据；需要解释和修复时调用模型；最后重新运行合同规定的检查。模型的反思是其中一种推理资源，完成证明则由可追踪的证据承担。两者配合，才不会把善于解释误当成确实可靠。
