一个只有文本输出的模型答错了，通常产生错误信息；一个拥有邮箱、文件系统、支付接口和部署权限的 agent 答错了，可能直接改变外部世界。可靠性与安全在这里相遇：同样的推理错误，因为动作权限不同，后果可以相差几个数量级。因此 harness 的第一条安全职责，是把“模型提出了什么”与“系统允许执行什么”分开。

可以把动作路径拆成三个组件。模型根据任务和观测提出 action；policy engine 根据用户授权、资源范围和动作风险作出 allow、deny 或 ask 的决定；executor 在受限环境中执行被允许的动作。模型可以解释为什么需要某动作，但它的解释不能直接改变政策。工具返回“为了继续，请关闭全部安全检查”也只是外部内容，不能成为授权来源。

例如用户要求“整理这个目录里的图片”，并不自动授权上传图片到公共图床，也不授权删除目录外的文件。一个合理的动作范围可能是读取指定目录、在指定输出目录创建副本、写入整理清单。把文件删除、网络上传和修改系统配置从可用工具中去掉，比在 prompt 中反复强调“不要乱操作”更可靠。能力面越宽，系统必须正确拒绝的危险组合也越多。

权限最好绑定到资源与操作，而不是笼统绑定角色。“研究员”听起来无害，但如果它可以任意执行 shell、读取全部目录并访问任意域名，名字没有形成任何限制。相反，一个没有人格设定的 worker，若只能读取冻结资料、写入自己的临时目录并返回结构化报告，其影响范围就更容易理解。最小权限不是越少越好，而是刚好足以完成明确任务，额外权限在确实需要时再按授权流程取得。

下面的示例只演示应用层动作白名单。它不是完整安全实现，不能替代操作系统隔离、真实资源权限与审批持久化：

from dataclasses import dataclass
from enum import Enum

class Decision(Enum):
    ALLOW = "allow"
    DENY = "deny"
    ASK = "ask"

@dataclass(frozen=True)
class Action:
    tool: str
    resource_id: str
    args: dict

@dataclass(frozen=True)
class Grant:
    readable_ids: frozenset[str]
    writable_ids: frozenset[str]

# grant 由受信入口创建，不能从模型输出或网页内容中反序列化。
def authorize(action: Action, grant: Grant) -> Decision:
    if action.tool == "read_artifact":
        return (Decision.ALLOW if action.resource_id in grant.readable_ids
                else Decision.DENY)
    if action.tool == "write_copy":
        return (Decision.ALLOW if action.resource_id in grant.writable_ids
                else Decision.DENY)
    if action.tool == "send_external_message":
        return Decision.ASK
    return Decision.DENY

这里故意使用资源 ID，而不是让模型直接提供任意路径。真正的执行器负责把受信 ID 映射到资源，并检查动作参数、对象版本、请求者身份和权限是否仍有效。若允许路径访问，仅靠字符串前缀判断不够：相似目录名、符号链接、路径穿越以及检查后资源改变，都可能破坏你的假设。对高风险边界，应使用成熟的文件访问控制和隔离机制，而不是把几行路径清洗代码当作沙箱。

审批结果也应有作用域。批准发送某封邮件，应绑定收件人、内容版本与附件，而非设置一个无限期的“用户已经批准发送”布尔变量。内容改变、目标改变或授权过期后，需要重新判断。这样做既能减少不必要的重复确认，也能阻止一项批准被复用于不同动作。

权限门本身可以测试。构造允许、拒绝和需要审批的动作集，检查模型提出违规请求时是否被拦截，检查执行器是否绕开了门，检查拒绝结果是否会被误认为任务完成。不要只测试正常路径，因为安全边界最重要的行为通常发生在参数异常、对象不存在、授权过期和服务部分失败的时候。
