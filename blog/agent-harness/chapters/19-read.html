Human-out-of-the-loop：有边界的自主

读完这一讲，你能回答

  • 为什么“能不能无人审批”是一种运行模式的属性，而不是模型能力的等级？
  • 一个适合自主运行的任务长什么样？把它扩大一圈，风险为什么会发生质变？
  • 放行一个无人审批的流程之前，要过哪几道筛选？
  • 模型自报“置信度 0.96”为什么不够？什么证据更可靠？
  • 怎样分步上线？系统在什么情况下必须自己停下来？

自主是一种运行模式，不是模型的等级

新同事入职第一周，你可以放心让他整理共享盘里的临时文件夹，却不会让他独自签一份大额合同。不是因为他整理文件时更聪明，而是这两件事做错了以后，后果有多大、能不能及时发现、能不能挽回，完全不同。

Human-out-of-the-loop（人在环外）指运行过程中没有人逐步审批。无人逐步审批，最适合被理解为一种经过验证的运行模式，而不是一个模型能力等级。相同模型可以自主整理临时目录，却不适合在无人确认的情况下执行重大资产转移。决定因素不只是它答对问题的比例，还包括四样东西：

  • 错误影响范围：错了会波及多少对象、多少钱、多少人。
  • 可检测性：错了能不能被及时发现。
  • 可恢复性：发现之后能不能撤回、重做。
  • 授权是否明确：用户到底允许它做什么，边界写没写清楚。

这四样都不是模型的属性，而是任务加上 harness 的属性。同一个模型，放进一个写入可撤销、检查可执行、边界清楚的流程里，就可以放手；放进一个删除不可逆、结果没人核对的流程里，就不行。

“人在环外”也不等于人不在场。回想第 19 讲的四个位置：自主运行时，运行中的审批撤掉了，任务开始前的边界、完成后的抽查和长期治理还在，而且要做得更扎实，因为它们成了人仅剩的控制点。

从一个很窄的任务开始

可以从一个很窄的任务开始：在隔离目录（一个只供这个任务读写、和其他文件分开的目录）里，把指定 CSV 转成标准格式，输出到新文件，保留原件。输入范围固定，成功条件清楚，写入可撤销，敏感数据不离开允许的边界。

这个任务之所以能放手，不是因为转换本身简单，而是因为出错的方式都被框住了。每一项检查都对准一种具体的错误：行数对不上，说明转换时丢了行或多出了行；字段和类型不对，说明列对错了位置，比如把日期读成了文字；唯一性检查抓重复记录；转换前后的总量，比如金额列的合计，能抓住“1,200”被误读成“1”这类数字解析错误（示意）。写坏了可以删掉重来，没见过的列会触发停止。每一种可能的失败，都有一个对应的发现办法和一个对应的退路。

把同一套流程扩展为“自动清理公司所有数据”时，风险发生了质变。

未知文件类型、共享权限、隐含业务约定和不可逆删除，都会进入动作空间。不能因为小任务成功率很高，就推断大范围任务也适合完全无人介入。上线过程应该逐步扩大任务分布和权限范围，并在每次扩大之前，补充针对新失败模式的验收。

放行之前的七道筛选

一个候选流程至少需要满足几项条件：

  1. 授权覆盖明确；
  2. 验收大部分可执行；
  3. 操作遵循最小权限；
  4. 失败能在造成过大影响之前被发现；
  5. 状态可恢复，或动作具备幂等性；
  6. 成本和时间有上限；
  7. 对未知输入有安全停止路径。

有两个词需要解释。第 3 条的最小权限，是说只给任务刚好够用的权限：转换 CSV 的流程只需要读一个文件、写一个目录，就不该拿到删除权限或网络权限。它不能防止模型出错，但能限制出错时最多能坏到什么程度。第 5 条里的幂等性，是说同一个动作执行一次和执行多次，结果一样。比如“把订单状态设为已发货”执行两遍没有区别，“再下一单”执行两遍就是两单。

七条里有几条管的是“别出错”，更多管的是“出了错怎么办”：能不能及早发现，能不能退回，最多花掉多少，遇到意外会不会停。无人审批的流程里没有人在旁边随时喊停，这些事后的兜底就必须事先装好。

把这七条放到采购任务上试一试：查报价、算总价显然可以自主，那么真正下单呢？

这是一组工程筛选条件，不是充分性的数学证明。七条都满足，只说明没有发现明显的理由不放手；它不保证不会出事。高后果领域，比如医疗、金融、法律相关的操作，仍需遵守适用的专业、组织和法律要求，不能用教程中的检查表取代它们。

下面的实验和上一讲是同一个装置，这次换个角度看：有边界的自主长什么样。把“模型提议”里的四个动作依次交给 harness，数一数有几个完全没有经过你。读取 clay 的报价被自动放行；写 /etc/quotes 和把 API key 发往网址被自动拒绝。拒绝也是自主的一部分：系统在边界上自己停住，用不着人来拦。只有“真的下单买 clay”停下来等你。再对照上面的七道筛选想一想：要让下单也变成无人审批，还缺什么？至少要补上撤回的路径，或者一个能接受的损失上限，外加下单后独立核对订单的验收。页面里的“执行”只是记录，没有真实的下单。

置信度 0.96 说明不了什么

天气预报说“降水概率 30%”，背后是多年预报和实际天气的对账：说 30% 的那些日子里，大约三成真的下了雨。一个同事说“这事我有九成把握”，你却不知道他的“九成”平时准不准。前者是校准过的概率，后者只是一句话。

所以，尤其不要把模型自报“置信度 0.96”当作唯一的放行标准。这个数字可能只是语言输出，未必经过校准。更可靠的信号来自可测证据：

信号它回答的问题采购任务里的样子
测试覆盖了哪些输入这类输入以前验证过吗三家报价的格式都在测试集里
独立读取是否匹配结果和另一条来源对得上吗下单后查询订单，总价确实是 7480 元
历史相似任务上的漏检率检查器过去漏掉过多少错误过去的采购记录里，总价检查漏过几次
多个检查器是否一致不同角度的检查结论一样吗预算检查和交期检查都通过
当前运行是否偏离已验证的分布这次输入和验证过的像不像突然出现第四家供应商，就属于偏离

最后一行值得多说一句。分布在这里指“验证时见过的那一类输入”。系统在三家供应商、一台笔记本的任务上验证过，不代表它在二十家供应商、五十台设备的任务上同样可靠。当前输入越不像验证过的样子，过去的成功率就越说明不了现在。

即使使用经过校准的概率，也应把错误损失纳入决策。同样一分的失败概率，在重排草稿和发送正式合同之间，意味着完全不同的风险：前者出错，损失是重排一次的几分钟；后者出错，可能是一份收不回的承诺。放不放手，看的是“失败的可能性”和“失败的代价”两样东西，而不是其中一样。

小任务的成功率，不能直接搬到大任务上

在隔离目录里转换 CSV 连续成功了很多次，说明的是“这一类任务、这一套边界”下系统表现好。把它挪到“清理公司所有数据”上，输入、权限和可恢复性全都变了，原来的成功率就不再是证据。每扩大一次范围，都要为新出现的失败模式补上验收。

分三步上线

新司机拿到驾照，通常先在熟悉的路上开，再上高速，再跑长途，而不是第一天就开夜车跑山路。自动化上线也可以这样分三步。

影子模式（shadow mode）是第一步：系统照常提出动作，但由已有流程执行，比较建议与真实决策。它像一个只看不动手的实习生，所有建议都记下来，和老员工的实际做法逐条对照。对照时要看的不只是“一致的比例”，更要看不一致的那些落在哪里：如果分歧集中在某一类输入上，比如带退货记录的订单，那么这一类就先不放手，其余的可以进入下一步。

三步各有代价。影子模式要求新旧两套流程并行，人力没有省下来，还要花功夫对照；小范围自动执行意味着收益也被限制在小范围里；扩大覆盖后的随机抽样，是一笔永远不会消失的检查成本。换来的是：每一次放手，都有证据撑着，而且每一步都能退回上一步。这里只是渐进部署的建议；每一步的通过标准应由任务风险与实际数据决定。

知道什么时候停

最重要的停止规则是：系统发现自己已经离开获得授权且经过验证的工作区间时，能够停下来。这里的“工作区间”，就是前面那些条件一起圈出来的范围：授权覆盖的动作、验证过的输入、能核对的结果。对采购 agent 来说，区间就是三家供应商、一台笔记本、含税 7600 元以内、报价编号是核对过的那几个；冒出第四家供应商、数量变成两台、报价编号变了，都说明它已经走到了区间之外。区间之外不一定会出错，但此前的验证已经说明不了这里的情况，继续做下去，就是在没有证据的地方冒险。

离开区间的时刻，往往伴随着一个很诱人的“继续”的办法。无法确认写入是否成功时，不应不断重复发送：

另外两种情形也一样。无法辨认账户时，不应挑一个最像的；验证器之间出现无法解释的差异时，不应取平均分掩盖冲突。

情形诱人的做法应当的做法
无法确认写入是否成功再发一次先查询状态；查不清就停下，报告“状态未知”
无法辨认账户挑一个最像的停下，列出候选和各自的依据，请人确认
验证器之间出现无法解释的差异取平均分保留冲突，先查原因，查不清再升级

两个同名账户

财务助手收到指令“给王磊退款 300 元”（虚构），系统里却有两个叫王磊的客户，一个上周有退货记录，一个没有。挑“最像的那个”看起来很合理，可一旦挑错，钱就退给了别人。正确的做法是停下来，把两个账户和各自的依据列出来，请人确认。多等几分钟的代价，远小于一笔退错的款。

成熟的自动化既知道如何继续，也知道何时继续会把不确定性变成真实损失。

这一部分最终建立的不是“模型从此不会错”，而是一条更扎实的完成链：用户目标被明确表达，执行受到边界约束，结果由适当证据支持，剩余的不确定性被如实暴露。接下来增加 agent 数量时，这条链不仅不能消失，还要面对更多信息交接和错误传播，第 21 讲从五种架构讲起。

小结

  • 无人逐步审批是一种经过验证的运行模式，不是模型能力等级；决定能否放手的是错误影响范围、可检测性、可恢复性和授权是否明确。
  • 从边界清晰的窄任务开始：输入固定、成功条件可查、写入可撤销、没见过的情况就停；把范围扩大一圈，风险会发生质变，小任务的成功率不能外推。
  • 放行前逐条检查七个条件：授权明确、验收可执行、最小权限、失败能及早发现、可恢复或幂等、成本时间有上限、未知输入能安全停下；它们是工程筛选，不是安全证明。
  • 模型自报的置信度可能只是语言输出；应看测试覆盖、独立读取、历史漏检率、检查器是否一致和是否偏离已验证分布，并把失败的代价一起算进去。
  • 上线分影子模式、小范围自动、扩大覆盖三步，每一步都能退回；离开授权且验证过的区间时，系统要能自己停下，不重发、不乱挑、不取平均。
