Human-in-the-loop：把人放在正确位置

把每一步都弹出“是否继续”，不等于实现了安全。用户很快会机械地点确认，而系统把本应承担的判断负担转移给了人。反过来，把所有步骤都隐藏在“全自动”背后，也会使用户直到后果发生才知道 agent 如何解释了任务。好的人工介入设计，需要说明人到底在控制什么。

可以把控制位置分成四层。任务开始前，人确定目标、资源范围、预算和不可触碰的边界；运行中，对高风险、不可逆或授权不清的动作进行审批；完成后，人抽样检查、验收和决定是否回滚；长期治理中，人维护政策、评估集与升级机制。一个无需逐次点击确认的流程，仍然可以在人设定的狭窄空间里运行。是否有人逐步盯着屏幕，与是否存在有效的人类控制，并不是同一个问题。

考虑一个邮件助手。读取用户指定的线程、归纳观点、在私有草稿中准备回复，通常有明确且可逆的边界。发送给外部联系人则改变了外部世界；如果内容包含报价承诺或敏感个人信息，错误成本更高。审批应发生在信息足够完整、动作尚未执行的时刻。让用户批准一个抽象的“处理此事”，然后由 agent 自行选择收件人、承诺金额和附件，不是充分知情的控制。

审批界面至少应回答：将执行什么动作，对谁或哪个资源执行，会发送哪些数据，会形成什么承诺，是否能撤回，以及支持这个动作的证据是什么。对于差异很小的重复操作，可以在政策允许范围内提前批准一个清晰的批次；但目标、数据范围、金额或风险发生实质变化时，原来的授权不能无限外推。批准应该绑定具体动作及其参数，不能只是聊天记录里孤立的一个“好”。

人工还应处理无法由客观事实消解的分歧。两个验证器一个认为页面简洁，一个认为信息不足，继续让它们争论十轮不一定接近用户偏好。若目标读者、品牌要求或取舍优先级没有定义，正确动作可能是提出一个具体问题。相反，如果一个验证器说文件存在、另一个说不存在，先检查路径、版本和环境，比立即打断用户更合适。系统应区分价值判断缺失与可通过工具解决的事实分歧。

人也会出错，尤其在上下文不足和时间压力下。因此 HITL 的效果要测量，而不是默认它是万能兜底。可以记录审批量、等待时间、被用户改正的错误类型、误批准率，以及审批后是否仍发生事故。若每百次审批只有一次真正值得停下来，应该研究另外九十九次能否被更好的范围约束替代；若重要风险常被一眼略过，则需要改进信息展示，而非继续堆叠更多警告文字。

一种实用做法是把升级原因写进状态机：授权缺失、目标冲突、证据不足、不可逆动作、环境漂移。每一种原因都有明确下一步，而不是统一返回“需要人工”。例如缺权限时说明需要哪项权限以及为什么；证据不足时列出已经检查与无法检查的条件；目标冲突时展示选项及代价。人类注意力是稀缺资源，harness 的职责之一，就是把这份资源保留给机器无法可靠代替的决策。
