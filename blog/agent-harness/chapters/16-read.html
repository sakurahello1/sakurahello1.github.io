“再检查一遍”能带来什么

考试时检查自己的卷子，你可能发现一处进位写错了，也可能把本来对的答案改错。至于本来就不会的那道题，看多少遍也还是不会，除非允许你翻书。

“请再检查一遍”是最便宜的可靠性技巧，也最容易被过度解释。模型再次阅读自己的答案，可能发现算术疏漏、变量遗漏或前后矛盾；也可能把正确答案改错。重复推理给了模型另一次机会，却没有自动带来新的事实。如果第一次失败源于未知的 API 行为，再写两千字自我反思通常无法替代一次真实调用。

放到采购任务里看得更清楚。假设模型交出的答案把 clay 的总价写成了 6800 元，忘了加税。如果上下文里本来就有“税率 10%”这条资料，让它再检查一遍，它有可能发现漏算，改成 7480。可如果它从来没查过 clay 的交期，再检查多少遍，也变不出“2026-10-03”这个日期。复查只能重新组织已有的信息，缺的信息要从外面拿。

先问：这一轮带来了什么新信息

判断一次纠错值不值得做，先看它有没有引入新信息，以及新信息从哪里来。没有新信息的复查，最多是把已有信息重新想一遍。

三种纠错，三种信息来源

讨论自我纠错时，应分开三种活动。内生纠错是在没有新增环境信息时，重新分析已有的问题与答案。外部证据纠错是执行程序、读取日志、查询事实或实际操作界面，利用新的观测改变判断。交互式澄清则处理目标本身的歧义：用户说“尽量快”，究竟愿意牺牲多少成本或质量？这种问题没有一个测试可以替用户作决定。

活动新信息从哪里来擅长什么典型的失败
内生纠错没有新信息，重新分析已有的问题与答案算术疏漏、漏掉变量、前后矛盾把对的改错；对不知道的事无能为力
外部证据纠错执行程序、读日志、查事实、操作界面把模糊的怀疑变成可复核的反例证据本身有问题：环境缺依赖、网页过时、连错实例
交互式澄清向用户问清目标目标本身有歧义，测试无从判断该问的没问，自己替用户做了取舍

把三者统称为 reflection（反思），会掩盖它们不同的信息来源和失败方式。一个 agent 在修 bug 时说“让我反思一下”，接下来可能是在重读自己的代码，也可能是去跑了一次测试，这两件事的可靠程度完全不同。

第三种最容易被跳过，因为它看起来像“没做事”。设想采购任务的一个虚构变体：用户只说“尽快到货”，没给截止日；某家供应商加 300 元可以提前三天发货。多花 300 元值不值？这不是模型复查能想清楚的，也不是任何测试能判定的，它取决于用户心里的取舍。agent 在这里自己拍板，无论选哪边，都是替用户做了决定。该做的是把选项和代价摆出来，问一句。

研究结论也不适合压缩成“LLM 不能自纠错”。2023 年的《Large Language Models Cannot Self-Correct Reasoning Yet》发现，被测模型在若干无外部反馈的推理设置中，内生纠错能力有限，有时出现退化。之后的 SCoRe 使用专门的多轮强化学习训练，展示了内生纠错的改善。（强化学习指用奖励信号来调整模型的一类训练方法。）二者研究的模型、训练方法和实验条件不同，不能拿一个标题取消另一个结果。来源：2023 年自纠错研究；SCoRe

对工程来说，这两项研究放在一起给出的提醒是：内生纠错能不能起作用，不能脱离具体的模型、训练方法和实验条件来谈；不能默认有，也不能默认没有，要在自己的任务上测。本讲后面会讲怎样测。

这一轮修正带来了什么新信息

对工程师而言，更有用的问题是：这一轮修正引入了什么信息？

看一个具体例子。假设 agent 写出一个日期排序函数，把日期当成字符串，按字典序排序。当所有日期都是 ISO 格式（2026-09-30 这种年-月-日的写法）时，字典序恰好就是时间顺序，几个样例都能通过；面对“9/30/2026”和“10/1/2026”，问题才暴露。

好反馈是挑过的证据

外部证据同样需要审查。一条报错可能来自测试环境缺少依赖，而不是实现错误；一个网页可能过时；数据库查询可能连错实例。

所以拿到一条失败证据，先别急着让模型改代码，先问这条证据本身靠不靠得住。测试报“找不到模块”，要先确认测试环境装的依赖和项目声明的一致；查询结果和预期不符，要先确认连的是哪个数据库、哪个版本。否则模型会非常认真地去修一段本来没有错的代码，而且可能真把它“修”坏。

验证反馈应尽量包含可定位的信息：输入、期望、实际输出、环境版本，以及最小复现步骤（能让错误重新出现的最少操作）。“测试失败，请修复”虽然简短，却可能逼着 agent 在没有依据时猜测。相反，把十万行日志全部塞进上下文，也可能淹没关键异常。好的反馈是经过选择的证据，不是越长越好的上下文。

挑选证据本身也要花功夫：验证器得知道哪条检查失败、输入是什么、期望是什么，才能写出中间那一栏。这正是 第 16 讲 要求每条检查都带证据引用的另一个好处：失败时，反馈几乎是现成的。

下面的剧场演示的就是一条“恰好”的反馈。上一轮的答案已经交了：{"vendor":"clay","total":6800,"delivery":"2026-10-03","source":"quote-clay-v2"}，漏算了税。这次不给工具，图里的“调用校验”和“工具执行”两格是暗的。点“播放录像”：验收器先检查这份旧答案，五项里只有“含税 7480 元”不通过；接着，一条“验收器反馈”作为新消息进入上下文，写着哪一项不对、依据哪份报价（quote-clay-v2）、价格和税率各是多少、应当怎样算；模型带着原来的任务、上一轮的答案和这条反馈重新作答，验收器再把五项全部查一遍。

看的时候留意两点。第一，这条反馈几乎把正确数字递到了模型手里，是最容易的一种修复；现实中的反馈常常只能给出期望和实际，找原因还得靠模型自己。第二，改过的答案要完整地重新验收，而不是只看改过的那一项。你也可以点“用我的模型运行”，看看别的模型拿到同样的反馈会怎样改。

怎样量一种纠错方法有没有用

展示一个修好的例子很有说服力，但它不能说明一种方法总体上有用。

如果要测量一种反思提示是否有效，不能只展示一个修好的例子。可以准备一组有确定答案的小程序题，保存模型的首次回答，然后分别进行三种处理：无新增信息的复查、带测试反馈的修复，以及独立重新采样（不看第一次的答案，从头再答一次）。让各组使用相近的总预算，记录三种转移：错改对、对改错、保持不变。

为什么要有“独立重新采样”这一组？因为模型每次输出本来就有随机性，同一道题再答一次，也可能碰巧答对。如果“复查”的净收益（错改对的题数减去对改错的题数），和“干脆重新答一次”的净收益差不多，那复查提示本身并没有多做什么，功劳属于“多试了一次”。这一组就是用来扣掉这部分运气的对照。

若只统计错误题里有多少被救回来，忽略原本正确的题被破坏了多少，会系统性高估方法收益。下图用虚构的数字演示这种记账方式。

什么时候该停

修 bug 的人都有过这种经历：同样的改法试了第三遍，报错一字不差，还在试。这时候缺的不是再试一次，而是换个思路，或者承认卡住了。

纠错循环还需要明确的终止条件。失败证据相同、修复动作相同、结果也相同，说明循环没有取得信息进展；继续盲目重试只会消耗预算。系统可以尝试不同的诊断工具、缩小复现范围，或者在授权范围内恢复到上一个稳定版本。当问题是缺失权限、需求冲突或外部服务不可用时，应报告真实阻碍。它不应靠把“仍未验证”改写成“基本完成”来结束任务。

判断“原地打转”的办法，和 第 2 讲 检测循环空转的思路相同：把每一轮的失败证据、修复动作和结果当成一个签名，和前几轮比较。签名一样，就说明这一轮没有带来新信息。

把“仍未验证”写成“基本完成”

预算快用完了，检查还没通过，于是最终报告写成“主要功能已完成，个别细节待优化”。这句话让任务看起来结束了，却把最重要的信息藏了起来：哪一项没过、为什么没过、卡在哪里。如实写“未完成：第 2 项失败，原因是测试环境无法连接数据库”，下一个接手的人或 agent 才知道从哪里继续。

最后，把这一讲收成一个务实的顺序：

  1. 先让廉价、确定的检查筛掉明显的问题；
  2. 再针对失败收集新证据；
  3. 需要解释和修复时调用模型；
  4. 最后重新运行合同规定的检查。

这个顺序的道理在于成本和可靠程度。确定的检查（解析、类型、单元测试、数据库约束）便宜，结果通常也不会因为换一次运行而变；它们先把能机械发现的问题筛掉，模型就不用在这些问题上花调用次数。模型的长处是解释一个失败、提出一个修改，放在有了具体证据之后，它才有东西可以解释。最后一步回到合同，是因为修改本身也可能引入新的问题。

模型的反思是其中一种推理资源，完成证明则由可追踪的证据承担。两者配合，才不会把善于解释误当成确实可靠。

小结

  • “再检查一遍”给了模型另一次机会，却不自动带来新事实：它可能修好疏漏，也可能把对的改错，对缺失的信息无能为力。
  • 纠错要分三种：内生纠错（没有新信息）、外部证据纠错（执行、读日志、查事实、操作界面）、交互式澄清（问清目标）；统称“反思”会掩盖它们不同的信息来源和失败方式。
  • 研究结论不能压缩成一个标题：2023 年的研究发现被测模型在无外部反馈时内生纠错有限，SCoRe 用专门的多轮强化学习训练改善了它；二者条件不同，工程上要在自己的任务上测。
  • 好反馈是挑过的证据：输入、期望、实际输出、环境版本和最小复现步骤；太少逼模型猜，太多淹没关键信息。修正后要把新旧检查全部重跑。
  • 衡量纠错方法要同时记错改对、对改错和不变三种转移，并控制预算；失败证据、动作和结果都不变时停止盲目重试，换路或如实报告阻碍。
