五种agent架构

读完这一讲，你能回答

  • 为什么数模型调用的次数，数不出系统里有几个 agent？该问哪四个问题？
  • 单体、独立式、集中式、去中心式、混合式，这五种架构各自把上下文、行动和整合交给了谁？
  • 每种架构在采购任务上会怎样成功，又会怎样失败？
  • 选架构时，为什么要先画依赖图，而不是先设计角色？
  • “团队规模”为什么要拆成独立采样数、同时运行数、职责种类数三个变量？

数模型调用，数不出 agent

看一家公司的工资单，你能数出有多少人，却数不出有几个部门、谁向谁汇报、出了问题谁负责。多 agent 系统也是这样。

把系统中的模型调用次数画出来，不能直接得到 agent 数量。一个 agent 可能连续调用模型二十次，期间搜索、写代码、测试；五个并行模型调用也可能只是对同一个问题采样五个答案。理解架构时，要问四个问题：

  1. 谁拥有上下文：哪些信息只有它读得到？
  2. 谁能够采取行动：谁能调用工具、改变外部状态？
  3. 谁负责整合结果：几份结论由谁合成最终答案？
  4. 错误由谁发现和修正：出了错，谁看得见，谁有权改？

以下沿用单体、独立式、集中式、去中心式和混合式这五类拓扑（谁和谁相连、信息怎样流动的结构）作为讨论语言；真实系统可以在一次任务中切换拓扑。分类参考：Towards a Science of Scaling Agent Systems，v3

接下来五节，用同一个采购任务把五种拓扑各走一遍：含税预算 7600 元，10 月 5 日前交付，候选 clay、ink、paper。正确答案是 clay，含税 7480 元，来源 quote-clay-v2，10 月 3 日交付。每张图都回答上面四个问题，并指出这种架构最典型的失败处。

单 agent：一条连续的决策循环

一位老医生从问诊、看片子到开药全程自己来，病人说的每一句话、片子上的每一处阴影，都直接进了同一个脑子，不用转述给别人。

单 agent 架构只有一条主要决策循环。它读到的环境反馈能直接影响后续行动，不需要先压缩成给同伴看的消息。本课前二十讲的采购 agent，都是这种架构。

这种连续性是优势，而非必须尽快摆脱的“入门形态”。

一个适合单 agent 的问题

修复一个跨三个模块的事务错误，比如订单服务偶尔把同一件商品的库存扣两次（虚构）。追查它要先读下单接口的调用链，发现两个模块加锁的顺序不一致，再去数据库里看那几条重复扣减记录的时间，最后回头改代码、重跑测试。每一步都依赖上一步刚看到的东西，单一执行者可以连续追踪调用链、锁顺序与数据库状态。要是把这三段拆给三个 agent，每个都只看到一段，还得花大量篇幅互相解释自己看到了什么。

它的局限在于：长任务可能积累过多上下文（第 8 讲起讲过窗口会满），独立探索也难以同时展开。改善它的第一步，常常是更好的工具、状态管理和验证，而不是增加角色。

独立式：多条分支，一个聚合器

考试时三个同学各做同一道题，交卷前对一下答案，这是个好习惯。可要是三个人都从同一本印错了的参考书上学的，对答案只会让那个错误显得更有把握。

独立式架构把相同问题或不同候选方案交给多个分支，各自执行，最后统一选择或合并。负责最后这一步的组件叫聚合器（aggregator）。例如让几个分支分别寻找同一问题的不同解释，再由测试决定哪一种成立。

它保留了探索差异，却把困难推给聚合器：至少一个分支答对，并不意味着系统能识别哪个答对。多数投票适合答案可比且错误不高度相关的情况；若所有分支读取同一条错误资料，多数只会稳定地重复错误。三个分支用同一个模型、同一段提示、同一份资料时，它们的错误往往是相关的，这时再加分支，买到的主要是同一个错误的更多副本。

所以独立式真正需要投入的，是一个比分支更可靠的挑选办法：能执行的测试、确定性的约束检查，或者一个独立的验收器。代价也很直接：每个分支都完整地跑一遍任务，花费大约是单 agent 的若干倍。

集中式：一个调度者，几个工作者

装修时，包工头把水电、木工、油漆派给不同的师傅，自己统一工期、材料标准和最后的验收。师傅们各干各的，有事找包工头。

集中式架构由协调者分解任务、派发子任务、收集结果并决定下一步。协调者也叫调度者或主节点，被派活的一方叫工作者（worker）。做行业研究时，可以让不同 worker 查询不同市场，而主 agent 负责统一时间范围、定义和证据标准。

这种结构容易管理责任和交付，但协调者也会成为瓶颈。它如果把任务拆错，所有 worker 都可能高效完成错误的局部目标；如果只有它能接触全局信息，其上下文窗口和整合能力就成为系统上限。拆分还有一个隐藏成本：工作者的结论要写成报告交回来，报告写得含糊，调度者就只能猜。这一点第 22 讲专门讲。

下面的剧场就是一个最小的集中式团队，任务还是采购。点“播放录像”，看上方的图：目标先到调度者，调度者把三家报价按列切开，价格工作者只拿到 id、价格、税率和来源编号，交期工作者只拿到 id、交期和来源编号；两份报告汇到“汇合作答”，由它写出 JSON，最后过验收器。有三处值得留意。第一，这里的拆分是程序写死的，不是模型决定的：真正调用模型的只有两个工作者和汇合那一步，所以下方表盘的“模型调用”走到 3，“工具调用”一直是 0。第二，两个工作者是一个接一个运行的：这个团队有两种职责，却没有并行，这正是本讲最后要区分的“职责种类数”和“同时运行数”。第三，工作者只写两三句中文，不输出 JSON，汇合那一步要从自由文本里找出数字；逐条读下方的消息，看看工作者的报告是否干净利落。也可以点“用我的模型运行”，用你自己连接的模型再跑一次。

去中心式：同伴之间直接说话

一个没有主持人的讨论组，谁发现问题都可以直接找相关的人，效率很高；可也常常出现这种情况：第一个发言的人说得很笃定，后面的人纷纷附和，讨论很快结束，结论却是错的。

去中心式架构允许同伴直接交换消息。一个 worker 发现某数据口径冲突，可以直接要求另一个 worker 复查，不必凡事经过主节点。

这对于相互关联的探索可能有帮助，但不能把自由讨论等同于更强推理。每次交流都消耗预算，并可能使原本不同的答案快速收敛到最先出现或最有说服力的错误。

一致不是证据

意见一致是通信结果，不能自动成为事实证据。三个同伴都同意 ink，只说明这句话在它们之间传开了；ink 能不能按时到，要回到报价原文去查。去中心式系统同样需要一个不参与讨论、只看证据的验收环节。

混合式：集中协调，局部横向

大多数真实团队都长这样：有一个项目负责人定范围、做验收，但前端和后端的同事不会为了一个字段名专门开会请示负责人，而是自己商量着定。

混合式架构保留集中协调，同时允许局部横向沟通。例如后端和前端 worker 可以共同确认接口，但由主节点控制需求范围、验收和合并。

它有更大的设计自由，也更容易出现责任模糊：接口变更由谁批准？共享文件谁能写？两个 worker 同时认为对方会补测试怎么办？

用一句“请积极协作”代替协议

这些问题属于协议设计，不能依靠角色提示里的一句“请积极协作”解决。提示只能影响模型说话的倾向，管不住两个同时发生的写入，也补不上没人认领的测试。谁批准、谁能写、谁负责，要写成规则，最好由 harness 来执行，比如共享文件只对一个工作者开放写权限。

怎样选：先画依赖图，再数三个变量

五种架构放在一起，对照开头的四个问题：

架构谁拥有上下文谁整合结果错误由谁发现典型的失败
单体一个 agent 拥有全部它自己它自己的检查与外部验收上下文越积越长，难以同时探索
独立式每个分支各一份，互不相通聚合器聚合器的挑选办法至少一个答对，却认不出是哪个；相关错误被多数放大
集中式调度者握全局，工作者各握一片调度者调度者与验收器拆错了全盘皆错；调度者成为瓶颈
去中心式各握一片，靠消息互通同伴之间协商同伴互相复查通信耗预算；收敛到最先出现或最有说服力的错误
混合式主节点握范围，工作者局部共享主节点主节点验收加局部互查责任模糊：谁批准、谁能写、谁补测试

表格能帮你认出一个系统属于哪一类，却不能替你选。选择架构时，可以先把任务画成依赖图：每个子任务是一个点，“B 要用到 A 的结果”就从 A 画一条线到 B。彼此独立、输入稳定的分支适合并行；后一步必须读取前一步产生的最新状态时，强行拆分会增加同步负担。

采购任务就是一个例子。查三家报价彼此独立，可以拆开并行；“挑出答案”却必须同时看到价格和交期，两条线在这里汇合。所以集中式那张图里，拆分发生在查询阶段，最后仍要有一个整合者。

不要按职业名先创造产品经理、工程师、审查员、测试员一整套组织，再寻找事情让他们做。先识别三样东西：需要隔离的上下文、可并行的工作、必须独立的验证；再决定是否需要多个 agent。很多时候，答案仍然是一个单 agent 加一个独立的验收器。

还有一个实用区分：独立采样数、同时运行数、职责种类数是三个变量。

变量它数的是什么例子收益来自
独立采样数同一问题独立求解了几次十次独立采样可以顺序运行搜索更广
同时运行数同一时刻有几个在跑四个并行 worker 可以承担相同职责等待更短
职责种类数有几种不同的分工一个模型也可以在隔离上下文中执行不同角色责任划分更清楚

上面的剧场正好能说明这一点：它有两种职责，同时运行数却是 1，每个工作者也只采样一次。将这三件事混成“团队规模”，会让你无法解释收益究竟来自搜索更广、等待更短，还是责任划分更清楚。后面几讲会一直用到这个区分：第 23 讲读论文里的架构对比，第 24 讲算协调的成本，第 25 讲在等预算下比较。

小结

  • 模型调用次数数不出 agent 数量；理解架构要问四个问题：谁拥有上下文，谁能行动，谁整合结果，错误由谁发现和修正。
  • 单 agent 的观察直接变成下一步，连续性是优势而不是入门形态；它的局限是上下文变长、难以同时探索，改进通常先从工具、状态管理和验证入手。
  • 独立式保留了探索差异，难题落在聚合器：至少一个答对不等于认得出；错误相关时，多数投票只会稳定地重复错误。
  • 集中式责任清楚，但拆错了会让所有工作者高效完成错误的局部目标，调度者的上下文和整合能力是系统上限；去中心式能直接纠错，也会快速收敛到最先出现或最有说服力的错误，一致不是证据。
  • 混合式多了横向沟通的自由，也多了责任空白，要靠协议而不是提示来解决；选架构先画依赖图，并把独立采样数、同时运行数、职责种类数分开来看。
