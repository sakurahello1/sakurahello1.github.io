五种agent架构

把系统中的模型调用次数画出来，不能直接得到 agent 数量。一个 agent 可能连续调用模型二十次，期间搜索、写代码、测试；五个并行模型调用也可能只是对同一个问题采样五个答案。理解架构时，要问谁拥有上下文，谁能够采取行动，谁负责整合结果，以及错误由谁发现和修正。以下沿用单体、独立式、集中式、去中心式和混合式这五类拓扑作为讨论语言；真实系统可以在一次任务中切换拓扑。分类参考：Towards a Science of Scaling Agent Systems，v3

单 agent 架构只有一条主要决策循环。它读到的环境反馈能直接影响后续行动，不需要先压缩成给同伴看的消息。比如修复一个跨三个模块的事务错误，单一执行者可以连续追踪调用链、锁顺序与数据库状态。这种连续性是优势，而非必须尽快摆脱的“入门形态”。它的局限在于长任务可能积累过多上下文，独立探索也难以同时展开。改善它的第一步常常是更好的工具、状态管理和验证，而不是增加角色。

独立式架构把相同问题或不同候选方案交给多个分支，各自执行，最后统一选择或合并。例如让几个分支分别寻找同一问题的不同解释，再由测试决定哪一种成立。它保留了探索差异，却把困难推给聚合器：至少一个分支答对，并不意味着系统能识别哪个答对。多数投票适合答案可比且错误不高度相关的情况；若所有分支读取同一条错误资料，多数只会稳定地重复错误。

集中式架构由协调者分解任务、派发子任务、收集结果并决定下一步。做行业研究时，可以让不同 worker 查询不同市场，而主 agent 负责统一时间范围、定义和证据标准。这种结构容易管理责任和交付，但协调者也会成为瓶颈。它如果把任务拆错，所有 worker 都可能高效完成错误的局部目标；如果只有它能接触全局信息，其上下文窗口和整合能力就成为系统上限。

去中心式架构允许同伴直接交换消息。一个 worker 发现某数据口径冲突，可以直接要求另一个 worker 复查，不必凡事经过主节点。这对于相互关联的探索可能有帮助，但不能把自由讨论等同于更强推理。每次交流都消耗预算，并可能使原本不同的答案快速收敛到最先出现或最有说服力的错误。意见一致是通信结果，不能自动成为事实证据。

混合式架构保留集中协调，同时允许局部横向沟通。例如后端和前端 worker 可以共同确认接口，但由主节点控制需求范围、验收和合并。它有更大的设计自由，也更容易出现责任模糊：接口变更由谁批准？共享文件谁能写？两个 worker 同时认为对方会补测试怎么办？这些问题属于协议设计，不能依靠角色提示里的一句“请积极协作”解决。

选择架构时，可以先把任务画成依赖图。彼此独立、输入稳定的分支适合并行；后一步必须读取前一步产生的最新状态时，强行拆分会增加同步负担。不要按职业名先创造产品经理、工程师、审查员、测试员一整套组织，再寻找事情让他们做。先识别需要隔离的上下文、可并行的工作和必须独立的验证，再决定是否需要多个 agent。

还有一个实用区分：独立采样数、同时运行数、职责种类数是三个变量。十次独立采样可以顺序运行；四个并行 worker 可以承担相同职责；一个模型也可以在隔离上下文中执行不同角色。将这三件事混成“团队规模”，会让你无法解释收益究竟来自搜索更广、等待更短，还是责任划分更清楚。
