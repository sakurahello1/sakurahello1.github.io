窗口会满，任务不能归零

读完这一讲，你能回答

  • 裁剪、压缩、检索、子任务隔离、检查点，分别治哪一种病？

任务一长，窗口就会满

前几讲的采购任务只有三家供应商，几圈就结束了。现在假设它扩展成一项连续的工作：先确定预算，再收集几十家供应商，比较历史报价，等待新的交付日期，最后提交一份建议。这可能要持续几十轮。

每一轮的工具结果都会加入历史。很快就会出现几类问题：

  • 请求超过了上下文窗口，也就是模型一次调用最多能读入的 token 数，调用直接失败；
  • 调用变慢：每一轮都要把越来越长的历史重新读一遍；
  • 费用增加：输入 token 按量计费，历史越长越贵；
  • 最隐蔽的一种：虽然没有超长，模型却忽略了早期的硬约束，比如一开始说好的“只建议，不下单”。

图里每一行的总长度都在变，不变的是蓝色的系统提示和那条金色的硬约束。硬约束没有变少，只是被淹没了。位置和干扰怎样影响模型用上一条信息，第 10 讲会专门讨论；这一讲先回答一个更基本的问题：窗口装不下时，系统该怎么办。

仓库和工作台：日志不等于上下文

最常见的第一反应是：“我把所有聊天都存下来了，不会丢。”这无法直接解决问题。会话日志可以有几百 MB，但一次模型调用只能看到这一次输入里的内容。

打个比方：日志是仓库，上下文是工作台。资料在仓库里，不等于已经摆在工作台上；工作台上堆得越满，也不等于每件东西都更容易找到。真正要设计的，是每次开工前把哪些东西从仓库搬上工作台。

为此，建议先把系统中的信息分成四层：

层它是什么生命周期采购任务里的例子
上下文这一次调用实际可见的 token一次调用这一轮发给模型的全部消息
事件日志发生过什么：调用、结果、时间整个任务，事后审计也要用第 3 轮调用 lookup_vendor(clay)，返回 6800 元
工作状态当前目标、已完成、待办、版本、正在运行的操作任务进行期间，不断更新已按 quote-clay-v2 算出 7480；paper 待查
长期记忆未来任务可能复用的事实或经验跨任务这位用户的采购一律只建议、不下单

四层可以共用某种存储技术，比如都放在同一个数据库里，但概念上要分开。否则你会用一段聊天摘要同时承担审计日志、任务计划、用户画像和故障恢复，最后哪一项都不可靠：审计要的是原样记录，计划要的是最新状态，画像要的是跨任务的稳定事实，恢复要的是精确到版本的现场，一段文字满足不了四种要求。记忆本身怎样分类、怎样存取，第 12 讲起会展开。

溢出时的五种手段

窗口装不下时，处理办法至少有五种。它们常被笼统地叫作“压缩”，其实各自解决不同的问题：

手段做什么解决什么代价
裁剪把可以恢复的大块旧结果移出上下文大段原文占着位置移出的内容要有地方存、有办法找回
压缩把一段历史改写成更短的摘要过程太长有损：摘要没写的，从此看不见
检索需要时再把原文取回来精确细节不能丢要有稳定的索引，还要判断什么时候该取
子任务隔离局部工作放进一个独立的上下文里做，只把结果带回来局部细节淹没主线子任务看不到主线全貌，交接要设计
检查点保存继续执行必需的状态中断或换一个上下文后接着干要决定哪些状态算“必需”，恢复时还要核对

同一份一万行的测试日志，三种手段的做法完全不同。把日志归档，只把失败摘要留在上下文里，是结果裁剪；把“我们做过什么”写成五百字，是压缩；下一轮根据错误名取回对应的堆栈，是检索。这个日志例子是为说明三者的区别而设的示意。相关做法的讨论见：来源：Effective context engineering for AI agents

采购任务里的五种手段

几十家供应商的完整报价单，只留“已查 34 家，候选 3 家，原文见 quotes/ 目录”，这是裁剪。把前二十轮的比价过程写成一段总结，这是压缩。用户突然问某家的保修条款，按编号把那一家的报价原文取回，这是检索。让一个子任务专门核对历史价格，只把“有无异常”带回主线，这是子任务隔离。在每轮结束时写下目标、约束、已验证的数字和正在等待的交期查询，这是检查点。

后两种手段容易被忽略。子任务隔离的思路是分工：让一个子任务在自己的上下文里跑完几十轮历史价格核对，主线只收到一句“有无异常、依据是哪几份报价”。主线的工作台因此保持干净，代价是子任务看不到主线的全貌，它交回来的结论也要单独验证（多 agent 的部分会细讲）。检查点和压缩看上去相似，方向却相反：压缩是把过去写短，检查点是为将来写下继续工作所必需的东西，比如约束、已验证的结论、正在等待的操作。第 9 讲会专门讨论检查点里该写什么。

这些手段通常组合使用。组合的顺序也有讲究：能裁剪就先裁剪（原文完整保存在别处，随时可以取回），不得不压缩时再压缩，因为压缩掉的东西，只有在原文仍然存在时才救得回来。这就引出了这一讲最重要的一点。

压缩是有损的：保留什么，怎样找回

关于压缩，最危险的误解是：它能把任意长的历史无损地塞进一段固定长度的摘要。

假如原文包含二十个报价的完整字段，摘要只保留了三家候选。以后突然要比较第十七家的保修条款，摘要很可能答不出来。若原始记录仍然存在，并且有稳定的索引（一个不会变的编号或路径，能准确指向那一条原文），系统还可以回去补查；若原文已经丢失，这次遗漏就可能再也无法恢复。

因此，设计压缩时要同时问两个问题：

  1. 这次摘要保留什么？
  2. 将来发现缺了什么时，怎样找回来？

只回答第一个问题的压缩，等于在赌未来不会需要被丢掉的东西。回答了第二个问题的压缩，丢掉的只是“此刻不在工作台上”，而不是“从此不存在”。

MemGPT 为理解这类分层记忆与控制流，提供了一个经典的系统视角：有限的上下文与外部存储相配合，由系统管理信息在两者之间的迁移。它借用了操作系统管理内存的思路：常用的放在快而小的地方，其余的放在慢而大的地方，需要时换进来。要看清的是，它没有让每次模型调用真正读到无限的历史；每一次调用看到的，仍然只是被搬上工作台的那一部分。来源：MemGPT

下面的实验把这件事做成了可以动手的样子。窗口只有 10 格，一开始装着目标和四条关键事实：预算不超过 7600 元、不得实际下单、10-05 前交付、clay 的精确报价。先点“继续工作”，看日志把窗口填满；然后在“压缩方式”里选一种，点“压缩并恢复”，看哪几条事实还在（绿色）、哪几条丢了（红色）。依次试“只留最近的日志”“一句自然语言摘要”“结构化交接”“按索引从磁盘取回原文”四种。留意右边“磁盘上的原始记录”：它自始至终都在，四种方式的区别，只在于压缩后的窗口里还有没有一条通往它的路。

给一次调用排预算

与其等窗口满了再手忙脚乱，不如每次调用前就给上下文排好预算，像做家庭开支计划一样，先分好各项的份额。

一个实用的方法，是把输入分成四块，再为输出留出空间：

区块放什么采购任务里的例子需要缩减时
核心约束目标、硬约束、动作边界含税 ≤ 7600 元，10-05 前交付，只建议不下单不缩减，每次都放
当前状态已完成、待办、版本、运行中的操作已按 quote-clay-v2 算出 7480；paper 待查保持最新，旧状态直接覆盖
证据片段这一步决策要用的原文clay 的报价原文按需检索，用完可以移出
近期交互最近几轮的调用与结果最后两次工具调用及其结果按协议单元整组裁剪或压缩
输出预留模型写回答（和思考）的空间最终 JSON，或下一次工具调用不能被挤占

具体每块给多少 token，要根据模型和任务实测，不能用一个固定的字符数通吃。原因之一是 tokenizer（把文字切成 token 的分词器）因模型而异：同一段中文，在不同模型里切出的 token 数可能不一样。

排的顺序也有讲究。先把输出预留扣出来，再放核心约束和当前状态，这两块几乎不可商量；剩下的空间分给证据片段和近期交互。放不下时，从近期交互里最旧的一组开始，整组裁剪或换成带索引的摘要；证据片段则按“这一步用不用得上”来取舍。这样即使窗口吃紧，最先被牺牲的也是最容易找回的东西。

排预算时还有一条硬规则：工具调用和它对应的结果，要作为一个完整的协议单元来处理。随意截掉一条 assistant 的工具调用、只留下对应的工具结果，会造成语义上的错误，甚至在接口层面出错。若 provider 还要求回传 reasoning 字段（第 6 讲讲过 DeepSeek 的例子），压缩适配层也必须遵守这个协议。

用“保留最近 N 条”当作压缩策略

“只保留最近 20 条消息”写起来只要一行，但它默认了一个错误前提：越新的越重要。长任务里恰恰相反，最关键的约束往往出现在最早的几条消息里。按条数截断还很容易把一对调用和结果从中间拆开。先按区块分好类，再决定每一块怎样缩减。

更长的窗口，也替你做不了决定

模型的窗口越来越长，会不会让这些问题自然消失？更长的窗口确实能缓解“搬运”的频率：以前二十轮就要压缩一次，现在也许一百轮才需要（数字仅为示意）。

但窗口再长，也不能替你决定：哪些信息可靠，哪些已经过期，哪些事实互相冲突。一份报价出现了 v2 和 v3 两个版本，窗口能把两份都装下，却不会告诉模型该信哪一份。这个决定仍然属于 context engineering（上下文工程），也就是设计每次调用放进什么、按什么顺序、以什么形式放。标称窗口和真正用得上的上下文之间的差距，第 11 讲会专门讨论。

一句话

上下文是工作台，不是仓库。每次调用前要决定搬什么上来；压缩时要同时想好保留什么，以及丢掉的东西怎样找回。

小结

  • 长任务里，历史不断增长会带来超长失败、变慢、变贵，以及更隐蔽的“早期硬约束被忽略”。
  • 保存全部聊天不等于模型能看到：日志是仓库，上下文是工作台，一次调用只读得到工作台上的内容。
  • 信息要分成上下文、事件日志、工作状态、长期记忆四层；一段摘要身兼四职，哪一职都做不可靠。
  • 裁剪、压缩、检索、子任务隔离、检查点各治一种病；压缩是有损的，设计时要同时回答“保留什么”和“缺了怎样找回”。
  • 排上下文预算时，核心约束不参与裁剪，输出要留足空间，工具调用和结果要按协议单元整组处理。
  • 更长的窗口减少了搬运次数，但判断可靠、过期与冲突仍然是 context engineering 的工作。
