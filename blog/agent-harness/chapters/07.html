假设采购练习扩展成一项连续工作：先确定预算，再收集几十家供应商，比较历史报价，等待新的交付日期，最后提交一份建议。每一次工具结果都加入历史，很快就会出现几类问题：请求超过上下文窗口、调用变慢、费用增加，或者虽然没有超长，模型仍忽略了早期的硬约束。

“保存了所有聊天”无法直接解决它。会话日志可以有几百 MB，但一次模型调用只能看到这次输入中的内容。日志是仓库，上下文是工作台。资料在仓库里，并不意味着已经摆在工作台上；工作台上堆得越满，也不意味着每件东西都更容易找到。

建议先把系统中的信息分为四层。上下文是这一次调用实际可见的 token；事件日志记录发生过什么；工作状态说明当前目标、已完成内容、待办、版本和运行中的操作；长期记忆保存未来任务可能复用的事实或经验。四层可以共用某种存储技术，但概念上要分开。否则你会用一段聊天摘要同时承担审计日志、任务计划、用户画像和故障恢复，最后哪一项都不可靠。

处理溢出至少有五种不同手段。裁剪移除可恢复的大块旧结果；压缩把历史变成更短摘要；检索在需要时重新取回原文；子任务隔离让局部工作使用独立上下文；检查点保存继续执行必需的状态。它们各自解决不同问题。把一万行日志归档，只把失败摘要留在上下文里，是结果裁剪；把“我们做过什么”写成五百字，是压缩；下一轮根据错误名取回对应堆栈，是检索。来源：Effective context engineering for AI agents

其中最危险的误解是认为压缩能无损地把任意长历史塞进固定摘要。假如原文包含二十个报价的完整字段，摘要只保留三家候选，那么以后突然要比较第十七家的保修条款，摘要很可能答不出来。若原始记录仍存在且有稳定索引，系统可以补查；若原文已经丢失，遗漏就可能不可恢复。

因此，压缩设计应同时问两个问题：这次摘要保留什么，未来发现缺失时如何找回。MemGPT 提供了理解这类分层记忆与控制流的经典系统视角：有限上下文与外部存储相配合，由系统管理信息迁移。它没有让每次模型调用真正读到无限历史。来源：MemGPT

一个实用的预算方法，是把输入分成核心约束、当前状态、证据片段与近期交互，并为输出留空间。具体 token 配额要根据模型和任务实测，不能用固定字符数通吃所有 tokenizer。工具调用与对应结果应作为完整协议单元处理；随意截断一条 assistant tool call，只保留 tool result，会造成语义甚至接口层面的错误。若 provider 还要求回传 reasoning 字段，压缩适配层也必须遵守该协议。

更长窗口能缓解搬运频率，但不能替你决定什么可靠、什么过期、哪些事实冲突。这个决定仍然属于 context engineering。
