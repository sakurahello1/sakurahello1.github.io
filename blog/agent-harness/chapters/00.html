流畅的回答，不等于做过的事

先看一个贯穿全课的练习。你要买一台笔记本：含税预算 7600 元，必须在 2026-10-05 前到货，候选供应商有三家，分别叫 clay、ink、paper。这些供应商和报价都是虚构的，没有任何东西会被真的买下来。

把这个问题直接丢给一个聊天模型，几秒钟后你可能会得到一段像模像样的回答：推荐某一家，给出一个价格、一个交期，甚至补一句“已为你核对完毕”。

问题在于，最新的报价存放在本地的报价文件里，交期需要查询，含税总价需要计算。模型收到问题以后，只能根据它已有的知识和你这次输入的文字来组织答案。这些东西它一样也看不到。语言再流畅，也补不出它从未看到过的事实。就算它写了“已为你核对完毕”，那也只是一句话，背后并没有发生过任何一次核对。

我们把这种“只调用一次模型、不给它任何工具”的用法叫裸模型。这一讲的标题问“系统怎样知道真做了”，答案的方向很朴素：不相信模型怎么说，去查做过的事留下了什么证据。为此需要两样东西：一个让模型能够真的去查的循环，和一个在最后按证据判定完成的检查。

右边那一列，就是这门课要从零搭起来的东西。下面把它拆开来看。

多出来的那一段：一个循环，外加一道验收

打个比方。一位聪明但刚入职的同事被关在一间没有电脑的会议室里，只能靠递纸条和外界沟通。他写“请帮我查一下 clay 的报价”，你去查，把结果抄在纸条上递回去；他看了结果，再决定下一张纸条写什么。最后他写下结论，你拿着结论去和原始记录逐项核对。

在这个比方里，同事就是模型，替他跑腿、抄结果、最后核对的你，就是 harness。

最小 agent 做的事，就是给模型加上这样一个循环：获取观察，提出下一项动作，执行动作，再根据结果继续。循环一旦存在，模型的输出就有了两种不同的用途：有些内容是给用户看的，比如一句进度说明、一段解释；有些内容是交给程序执行的，比如“调用 lookup_vendor，参数是 clay”。把后一类输出安全、准确地落实到环境中的那层运行设施，就是这里所说的 harness。

还有一种输出比较特殊：最终答案。它不让程序去做任何事，却在宣称“事情做完了”。这句宣称既不能只显示给用户了事，也不能直接当真，所以它有第三个去处：交给验收器检查。

harness 这个词没有一个统一到每个细节的行业定义，但它通常覆盖下面这些事。用采购任务来看，每一项都很具体：

职责在采购任务里是什么样子
上下文组装把目标、工具列表、此前每一次查询的结果，按顺序拼成这一次要发给模型的消息
模型调用发出请求，收回回复，记下用掉了多少 token
工具路由看到“调用 lookup_vendor”，找到对应的函数去执行；不认识的工具名一律拒绝

这些职责可以装在一个程序里，也可以分给几个部件。Anthropic 介绍过一种有代表性的架构，把 session、harness、sandbox 分开：session（会话）保存发生过的事件，harness 驱动执行，sandbox（沙箱）提供代码和文件环境。这是一种有帮助的责任划分，而不是所有实现都必须照搬的规范。来源：Managed Agents

这一节只需要记住一件事

模型只产生文字。一段文字是被显示、被执行还是被当作“完成”的依据，由 harness 决定；而“完成”这个判断，最终要落在验收器对证据的检查上。

五个角色，各管一段

循环里其实不止两方。把采购 agent 拆细一点，可以得到五个角色：

  1. 模型：决定下一步做什么，比如“先查 paper 的交期”。它只提出请求。
  2. harness：检查这个请求是不是允许的工具、参数是否合法、当前预算够不够，然后才去执行。
  3. 工具：一段普通的程序，比如 lookup_vendor，负责读取带版本号的报价文件。
  4. 环境：工具读写的真实对象，这里就是那份报价记录本身。
  5. 验收器（verifier）：一段确定性的检查代码，检查最后的推荐是否满足预算与交付约束。

这张图里最值得注意的是最后一步。模型能够提出“看起来完成了”，但完成判定仍然要回到证据上。验收器不关心模型的解释写得多好，只看答案里的字段和原始数据是否一一对得上。在我们的采购任务里，它检查五件事：

教学任务的正确答案事先知道，所以这里可以直接写死。真实系统里的验收器检查的是约束本身：总价是否不超过预算，交期是否早于期限，引用的报价是否存在且仍然有效。形式不同，原则一样：判定完成的，是一段不依赖模型自述的检查。

为什么不干脆让模型自己检查一遍？那等于让答卷人自己批卷：它依据的还是同一份上下文，写错的地方未必看得出来。验收器的价值在于它和模型互不依赖：它不读模型的解释，只拿答案去和原始数据对照。验证者为什么要独立、独立到什么程度，是第 16 讲的主题。

ink 为什么落选？它最便宜，含税 7040 元，但交期是 10-12，晚于期限。paper 交期来得及，但含税 7810 元，超出预算。只有 clay 两头都满足。模型如果只看价格就推荐 ink，答案会是可解析的 JSON、字段齐全、语气笃定，却仍然过不了验收器：供应商、总价、来源、交期四项都对不上，其中真正致命的是交期晚了一周。

出了错，先找到坏在哪一层

汽车打不着火，说一句“车坏了”并不是诊断。修车师傅会一样一样排查：电瓶、油路、点火。只有知道坏在哪一处，才知道该换什么。

agent 出错也是这样。为什么要把责任拆成上面五个角色？因为出错时，修复的位置完全不同。

症状坏在哪一层该修什么
模型查错了供应商决策改善工具描述，以及模型做选择时看到的上下文
工具读到了缓存里的旧价格数据数据的更新策略
同一个订单提交了两遍执行与恢复幂等与恢复流程
测试还没跑完就向用户报告成功完成判定完成状态机

表里有两个词需要解释。幂等的意思是：同一个请求执行一次和执行多次，效果相同。下单接口如果是幂等的，网络抖动时重试一次也不会多出一张订单。状态机指的是用一组明确的状态和它们之间的转换规则，来描述“现在进行到哪一步”，最后一节会专门画出来。

别把一切都叫“幻觉”

把所有失败统称为“模型幻觉”，听上去像是一个解释，其实让工程诊断失去了抓手：你不会因此去查缓存，不会去补幂等，也不会去修那个提前报喜的完成判定。先问“坏在哪一层”，再决定修什么。

从一个有界循环开始

看到上面那张职责表，你可能以为要先搭一个庞大的框架。其实不需要。一个实用的 harness 可以从很小的东西开始：

  • 一个有界循环：给模型调用次数设上限，到了就停，不会无限转下去；
  • 一张固定的工具注册表：只允许查询教学数据，表里没有的工具一律拒绝；
  • 一份记录：每次的输入、动作和结果都记下来；
  • 一个确定性的检查：最后用上一节的 verify 判定答案。

每一部分都买到了一样东西，也都有代价。调用上限保证运行一定会结束，但定得太低，本来能完成的任务会停在半路；定得太高，一次跑偏的运行会白白烧钱。

拿采购任务算一笔账。本讲实验的那段录像里，模型第一轮就同时查了三家，第二轮算了两家的含税总价，第三轮交出答案，5 次的上限只用了 3 次。再设想一个每轮只肯调用一个工具的模型：查三家要 3 次，算两家的总价要 2 次，交答案还要 1 次，一共 6 次。第 5 次调用用完时，它还没来得及交答案，这次运行就会以 incomplete 结束，尽管它每一步都没做错。上限该定多少，要看任务真正需要几步，而不是拍一个整数。

另外两样也一样。注册表让模型无法调用不存在的东西，代价是每加一个工具都要有人写清它的契约，这正是第 3 讲的内容。记录让事后排查成为可能，代价是存储和隐私上的负担。

等这个小循环跑顺了，再逐步增加持久日志、并发调度、权限确认和断点恢复。顺序反过来，你会在一个自己都看不清的系统里调试。

停下来的时候，说清停在哪

快递单上有“派送中”“联系不上收件人”“已签收”几种状态。假如一家快递公司让司机下班时把手里所有包裹都标成“已签收”，这个系统就失去了意义：你没法知道哪一件真到了。

agent 的每一次运行也会以某种方式停下来，而停下来的原因不止一种。值得为它们分别起名字：

  • running：还在工作；
  • waiting_for_user：缺少必要的信息或授权，需要用户介入；
  • incomplete：预算耗尽，但目标还没达成；
  • failed：当前这次执行失败了；
  • completed：完成条件已经满足。

同一句话，两种结局

两次运行的最后一条消息都是“采购分析已完成”。第一次，模型查了三家、算了含税总价，答案通过了验收器的五项检查。第二次，模型反复查询 clay 和 ink，5 次调用的预算用完时还没碰过 paper，最后那句话只是它的自述。

对用户来说，这两次运行应该呈现成完全不同的结果：前一个是 completed，后一个是 incomplete，并且要附上“还差 paper 没有核对”。

不要把所有退出路径都包装成“任务完成”。可靠系统的一项重要能力，是准确说明自己停在了哪里。一个会诚实地说“我做到一半”的 agent，比一个永远说“做完了”的 agent 有用得多，因为只有前者的“做完了”值得相信。

小结

  • 模型的输出只是文字；“已经完成”必须由一段按证据工作的检查来判定，而不是由模型自己宣布。
  • 最小 agent 就是模型加上一个有界循环：模型提出动作，harness 校验并执行，观察写回上下文，最终答案交给验收器。
  • harness 负责把“要执行的那部分输出”安全、准确地落到环境里，通常包括上下文组装、模型调用、工具路由、权限、预算、日志与恢复。
  • 把责任分给模型、harness、工具、环境、验收器五个角色，出错时才能定位到该修的那一层，而不是笼统地归咎于“幻觉”。
  • 每条退出路径都要有自己的状态：waiting_for_user、incomplete、failed 各有含义，只有验收通过才是 completed。
