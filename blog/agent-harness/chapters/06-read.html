Python + OpenAI SDK：最小可运行ReAct

现在把前面的概念压缩进一个小例子。目标很克制：模型查询虚构供应商报价，再向用户解释。工具只能读取固定字典，既不能购买，也不能执行任意代码。这样我们可以把注意力放在协议闭环，而不把安全边界藏在一个复杂框架后面。

以下示例沿用 DeepSeek 当前官方文档中的 OpenAI 兼容接口和模型名称。SDK 是官方 openai 包，API 服务由 base_url 决定；使用 OpenAI SDK 不意味着请求会发给 OpenAI。密钥从本地环境变量读取，不能写进仓库、前端静态资源或日志。示例未声称经过付费在线端到端测试。来源：DeepSeek 首次调用、官方 OpenAI Python SDK

读这段代码时，重点看三个位置。第一处是 dispatch：只有写在注册边界里的能力才能执行，工具名不会被传给 eval。第二处是 tool_call_id：结果必须对应模型请求的那一次调用，否则历史关系会断裂。第三处是循环预算：当模型持续请求工具时，系统有明确的停止机制，不会无限消耗余额。

完整程序已经要求最终JSON并校验供应商、含税价、日期与证据ID。它不靠关键词包含判断：‘不要选clay’也包含clay，不能当作正确推荐。当前验证器只覆盖固定fixture；扩展题目时应同时扩展验收合同，而不是让模型迎合一个写死的答案。

这个小程序没有生产级持久会话或副作用恢复；Python采用非流式SDK，让协议容易阅读，浏览器实现流式组装。完整代码同时设置单次60秒与整项120秒deadline，Ctrl+C取消，但本地取消不保证provider停止计费。自动重试关闭，以便调用次数清楚，也避免不确定动作重复。扩展写工具仍需授权、幂等与事后核验。

练习可以把clay交期改到截止日之后，再设计结构化‘无可行方案’结果及相应验证器。不能只改fixture还沿用固定正确答案，也不能因为用户说推荐就硬选一家。这个反例把我们带入下一部分：任务进行很久、数据变化时，系统还能记住哪些约束，知道读的是哪个版本吗？

保存聊天记录很容易，让另一次模型调用在正确状态下继续工作却困难得多。模型看到的上下文、磁盘里的记录、当前正在运行的任务、以后可能复用的经验，具有不同的用途与生命周期。这一部分把它们拆开，讨论压缩、位置、检索、存储和技能如何协作。
