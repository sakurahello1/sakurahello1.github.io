“饱和”至少有三种意思

先看三个学生。第一个每次考试都是 98 分，你没法从分数看出他这学期有没有进步，因为卷子太简单了。第二个在写论文，相关文献已经查全，再去图书馆只会借回同样的书。第三个报了太多兴趣班，每天光在路上就花掉三小时，真正坐下来学习的时间反而少了。三个人都“卡住了”，原因完全不同，开出的药方也完全不同。

在 agent 系统里，“能力饱和”至少有三种含义：

  • 基准饱和：题目已经太容易，分数接近上限，新增能力无法体现在指标上。
  • 信息饱和：相关资料已经齐全，继续搜索只会重复已有证据。
  • 系统饱和：协调和整合耗尽预算，使实际解题资源下降。

这三者需要不同处理，不能统一归结为“模型已经到极限”。

预算是一只水箱

可以把总预算想成一只固定容量的水箱。直接推理、工具使用、分支通信、结果整合和最终验证，都要从中取水。水箱不会因为接水的龙头变多而变大。

增加分支可能扩大搜索面，也会多出几样新开销：给每个分支写的任务说明，消息在分支之间来回时的重复内容，结论互相冲突时的处理，以及最后的汇总。若总量固定，这些开销先被扣掉，剩下的才轮到真正解题，再平分给每个 worker，每个 worker 实际得到的深度就可能下降。

图中的数字是虚构的，但方向值得记住：分支越多，固定开销越大，平摊到每个分支的深度越浅。一个任务必须连续分析很长的状态链，分成四份之后，每个人都只看了一小段，却还要花精力解释上下文，最终可能比完整执行更差。

这并不是说分支永远亏。如果任务真能拆成几块互不依赖的资料（第 23 讲讲过怎样判断），每个分支 33 格也许就够把自己那一块查透，拆分换来的是更广的覆盖和更短的等待。水箱比喻要提醒的只是：开销是先扣的，收益要靠任务结构去挣。

协调税不只收 token

人类团队里有一个熟悉的现象：人一多，会就多。机器不抱怨开会，会议依然占用计算和关键路径。关键路径是从开始到交付之间、必须依次走完的那条最长的等待链，它决定了用户要等多久。

协调税不只有 token。它还包括：

  • 时间：等待最慢的 worker、解决互相依赖、重新跑过期的测试；
  • 信息：压缩报告时遗漏前提；
  • 状态：每个分支观察到的环境版本不一致。

约 45% 附近的“能力饱和”，怎样读

前述 v3 论文报告了约 45% 基线表现附近的能力饱和现象，也讨论了不同架构中的轨迹级错误传播。来源：论文 v3，结果与局限部分

先把这句话拆开。基线表现指单体 agent 自己在某个任务上的成绩。论文对这一现象的描述大意是：单体本来就能做到约 45% 以上的任务，再加 agent，收益会递减，甚至转为负，因为剩下可改进的空间变小了，协调成本却不会跟着变小。用上一节的水箱来想：还能挣到的收益变少了，先扣的开销还是那么多。

轨迹级错误传播说的是另一件事：某一步出了错，这个错误会沿着后续步骤一路传下去。在多 agent 系统里，一个分支的错误结论会进入汇总，再进入最终答案。论文比较了这种传播在不同架构中的程度；大致的对照是，各分支各自执行、没有人逐一核查的独立式更容易让错误一路放大，有协调者整合结果的集中式能拦住其中一部分。这和第 16 讲讲的验证要独立于被验证的对象，是同一类道理。

这里不把 45% 当作部署阈值。不同任务的成功定义、题目难度和工具条件会改变分数含义；相同的 45%，可能表示做对一半独立题，也可能表示完整长流程的成功比例。前者每道题各自计分，后者只要中间一步出错整条流程就算失败，两个 45% 背后的能力完全不同。它不是一个脱离任务仍然成立的物理常数。

把 45% 写进路由规则

“单体成功率超过 45% 就不开分支”这样的规则看起来有论文撑腰，其实把一个在特定基准、特定成功定义下拟合出的现象，当成了到处成立的开关。你的任务怎么计分、题目怎么分布、工具条件如何，都会让这个数移动。可以把它当作一个提示：单体已经不错时，更要认真检查多 agent 的收益是否真实；不要把它当作阈值。

怎样知道系统正在饱和

如何知道系统正在饱和？不要只观察最终分数，还要看轨迹里的几个信号：新分支是否带来不同的有效证据，通信占比是否上升，重复操作是否增加，纠错是否真的改变了结果。这些都可以从运行记录里算出来：

信号怎样从轨迹里算饱和时的样子
新证据率各分支带回的证据编号去重后，新增了多少加了分支，新编号几乎不增加
通信占比说明、消息、汇总的 token 占总 token 的比例比例随分支数一路上升
重复操作同一工具、同一参数、资源版本也没变的调用次数多个分支反复读同样的网页
纠错命中复查之后答案真的改变、并且改对的次数复查了很多次，答案从不改变

用采购任务算一次新证据率

示意：让两个分支各自去核对三家报价。分支甲带回 quote-clay-v2、quote-ink-v3、quote-paper-v1，分支乙带回的也是这三个编号。去重之后还是三个，分支乙的新证据率是零：它花掉的预算只换来一次重复。再扩到四个分支，只要资料来源还是这三份报价，去重后仍然是三个。如果你想要的是一次独立复查，就应当明确交给验收器去做，而不是靠多开分支碰运气；想改变结论，就得换一种证据，比如去核对交期。

只看合计，两个方案一样；分开看，四个分支在难题上多做对 10 道，在易题上少做对 10 道。这时该问的就不是“哪个好”，而是“哪类任务该走哪条路”。

可以按依赖深度、工具调用强度、输入长度与验收难度分层，查看收益是否集中在某一类任务。不过分层过多、样本太少也会制造偶然模式：分成十几层、每层只有几道题，总有某一层碰巧显得“多 agent 大胜”。所以探索性观察应在新的保留集（事先留出、分析时没看过的一批题）上检验，而不是直接写入路由规则。

按需开分支：路由器也要被评估

上面的分层自然引出一个想法：动态分配预算。简单任务先走单体；出现明确的独立子问题、需要第二种证据或候选搜索不足时，再生成分支。这是一个值得尝试的候选方向。

但路由器自身也要评估。它会误判任务难度，也会增加额外调用。一个复杂的自适应系统若只比固定单体略好，却更难维护、更难复现，未必是最佳选择：出了问题时，你得先搞清楚这次走了哪条路、为什么走这条路，排查成本也是成本。

架构的目标是用可解释的代价提高可验证结果，而不是让结构图显得复杂。

小结

  • “饱和”至少有三种：基准饱和看题目，信息饱和看证据是否重复，系统饱和看预算流向；统一归为“模型到极限”会误诊。
  • 总预算固定时，任务说明、消息、汇总先从水箱里扣掉，剩下的才平分给各分支；分支越多，每个分支的深度越浅。
  • 协调税除了 token，还收时间（等最慢者、重跑过期测试）、信息（压缩丢前提）和状态（版本不一致）；协议能降低税率，不能免税。
  • v3 论文报告的约 45% 附近的能力饱和，依赖具体基准的成功定义和条件，不是部署阈值；轨迹级错误传播提醒我们，没人核查的分支会把错误一路带进答案。
  • 判断饱和要看新证据率、通信占比、重复操作和纠错命中；按难度分层要防偶然模式，动态路由本身也要被评估。
