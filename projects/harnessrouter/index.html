HarnessRouter

— px

为统一的 agent 接口补上一个可复核的评测维度：同一个模型放进不同的 harness，做同一批公开任务，谁完成得多、花得少，失败又是因为什么。

一句话版本

同一个模型，放进不同的 agent 运行框架（harness），做完同一道题所需的时间和调用量可能差很多。我给上游项目加了一套公开任务评测：除了看答案对不对，也记录耗时、用量和失败原因，把“偷看答案”“评分器出错”这类情况单独列出来。后来换到编码任务，发现评测环境本身就会漏答案，于是断网、清掉 git 历史再重跑：同一个模型、同样的思考强度，五个 harness 做对的题数只差几道，花费却差到 1.9 倍。所以报告成绩时，应该把模型、harness 和 benchmark 当成一个三元组一起写。下一步是固定模型和任务，每次只改变一个运行机制，分清省下的资源到底来自哪里。

01 · ContextHarnessRouter 是什么

HarnessRouter 是一个开源的 agent 基础设施：应用如果想分别接入 Codex、Claude Code、pi 这些后端，就得一个个处理会话、流式事件、文件、取消和失败语义。项目用 Unified Harness Protocol（UHP）把这些交互统一起来，并提供兼容 OpenAI Responses 的任务接口，让产品用同一套调用方式选择不同的 harness。Community Edition 以 Apache-2.0 开源，可以用 Docker 自部署。

这些工程设计属于上游项目。我是它的贡献者，下面讲的是我提出并实现的那一部分。

02 · Problem能跑起来，还不足以决定选谁

项目原本有两类检查：支持矩阵回答某个 harness 能不能在系统里跑起来，conformance 测试回答它是否遵守协议。但它们都没回答一个更实际的问题：同样的工作交给不同的 harness 和模型，完成率、耗时和资源消耗差多少？

我在 issue #205 里指出，当时官网上的对比数字来自单个没有公开任务与脚本的案例，缺少一个可以复跑的公共任务维度。

03 · Design在矩阵旁边加一个维度

我的方案是在支持矩阵旁边新增一个评测维度，以 harness × model × task pack 为比较单位，并复用项目已有的 API、会话、产物和运行记录。问题从“支持哪些后端”变成“这些组合做同样的工作做得怎样”，也不再把整体表现只归因于底座模型。

选任务集时，我最初考虑了多文档推理、表格产物、长程开发、跨系统工具使用等方向（DABstep hard、SpreadsheetBench 2、RoadmapBench、TheAgentCompany 等）。随后发现 DABstep 的 450 道正式题没有公开答案，只有 10 道开发题能在本地评分，于是自己更正：第一列改用答案公开、评分确定的 SpreadsheetBench Verified，DABstep 只留作管线的冒烟测试。

04 · Method第一列：SpreadsheetBench Verified

首轮取数据集前 50 题，对 pi、opencode、dsh、cline 各运行一次，共 200 次；模型都请求 deepseek-v4.1-flash，经同一个自定义连接，用自部署的 Community Edition。每道题的流程是：

记录什么

是否完成、reward、评分原因、总耗时与中位耗时、工具调用及其失败、fresh 和 cached input tokens、output tokens、实际使用的连接、服务端返回的模型、产物与错误记录。工具失败率只用能读到 trace 的工具结果做分母，不把缺失的记录当成成功；三类 token 分开报告，不直接换算成账单。

五条计分规则

  1. 连接必须一致实际连接与声明不符的运行列为 finding，不计分。
  2. 模型必须一致服务端模型不符也不计分；允许合法别名。缺失 served model 时照常计分，但明确标注“不可验证”。
  3. 不许偷看答案联网或到工作区外查找题目答案，列为 finding，保留证据、不计分。
  4. token 同一口径fresh、cached、output 三类分开，按同一规则统计。
  5. 只用确定性评分只用任务集自带的 grader，不用 LLM judge。

失败也要分清原因

正确答案本身都过不了 grader 的两道题，从所有组剔除。正常超时会记录取消，并对已有产物评分，产物没通过仍算失败。agent 还没开始动作就遇到的鉴权、余额、限流或服务错误，归为 runner error 并重跑，连续三次被供应商拒绝就停止。历史上代理超时后的 20 次任务，从会话记录里恢复评分，避免把客户端断线误判为任务失败。

05 · Results首轮结果，以及它不能说明什么

findings 共 4 次：pi 1 次、dsh 2 次到工作区外查找，cline 1 次联网。pi 与 cline 的 fresh input、cached input、output 分别相差约 2.5、2.6、2.2 倍，总耗时约 1.9 倍。

这些数字的边界要一起写清楚：它们是不同计分集合的汇总，不是逐题配对的均值，也不是账单倍数，不足以证明普遍的排名。四组的 Community Edition 版本和运行日期不完全相同；web 开关对 pi 和 opencode 是硬开关，对 cline 和 dsh 只是模型可能忽略的指令；cline 和 dsh 的 50 次运行都缺少 served model 记录。首轮没有做多轮随机重复和置信区间。这里的“可复现”首先指规则和汇总可以复核：实现支持断点续跑，表格能从 JSON 记录重新生成，finding 会话都留有 trace。

06 · NextPi Lab：一次只改变一个机制

第一列回答了“差多少”，但没回答“为什么”。不同的 harness 同时改变了许多机制，很难归因。issue #280 提出 Pi Lab：把机制做成开关，固定其余条件，比较原版 pi 与只多打开一个机制的实验组。首批机制来自 NVIDIA 的 SoL-Pi，论文里四项全开时，花费比原版 Pi 少了约三分之一，得分也掉了几分。

issue 一直没有回复，9 月 28 日我直接提交了 PR #318：一个独立的 pi-lab backend，四项机制各有一个开关。Pi、SoL-Pi 的源码和完整的 npm lockfile 都固定版本并做哈希校验；开关只从 harness 定义里读，工作区里的配置文件改不动它；原版 pi 完全不受影响，可以直接当对照组。控制台里能看到开关、缓存读写价格比和可选的 reducer 模型，每轮都会记录哪些机制是开着的。PR 在等待评审。

最初的方案是用扩展加载这些机制，后来改成独立的 backend，让原版 pi 保持为干净的对照，也避免工作区配置覆盖实验开关。首轮的表格任务太短（中位 48 秒），机制几乎不会触发，所以接下来换成更长的任务。

07 · Round 2第二轮：GDPval 办公任务

从 GDPval 里取 20 道要交付 Excel、Word 或 PDF 的任务，在自部署的 HarnessRouter 上交给五个 harness：pi、Pi Lab、Codex、Claude Code 和 dsh（DeepSeek 自家的 harness）。模型都是 deepseek-v4.1-flash，走同一个第三方中转，每题跑一次。评分用官方 rubric，由 GPT 独立打两遍，两遍的一致率 97.8%（κ 0.93）。另外我把其中四个 harness 的交付物打乱顺序做人工盲评，只比外观，允许并列。

名次 1 最好。dsh 有 3 题没有交出文件，原因是回复被这个中转的 32k 单次上限截断，或者流在中途断开后没有重试；换到另一个不截断的分组重跑这 3 题后，dsh 的平均分为 81.5%。dsh 没有参加盲评。

Pi Lab 对 pi 是 10 胜 8 负 2 平，费用低约 7%，但这都在一次运行的噪声范围内。更说明问题的是机制实际触发了多少：20 个会话里，ObservationPack 触发 7 次，Action Fusion 4 次，真正压缩上下文 1 次，Reducer 一次都没有。也就是说，这些机制在办公任务上大多闲着，Pi Lab 那点领先不能记在它们头上。外观名次和 rubric 分数几乎不相关（Spearman −0.18）；同一个模型的交付物质量起伏很大，有时连文件类型都交错，差异更多来自每一次运行，而不是 harness。

08 · Leakage评测环境本身会漏答案

编码任务（DeepSWE、SWE-bench Pro）用的是 Harbor：每道题一个容器，harness 装进容器里跑，结束后用隐藏测试判分。第一次跑 SWE-bench Pro，31 次运行全部通过。这不合常理，我去翻了 trace，发现模型是在拿官方修复：

漏洞模型做了什么怎么堵
镜像里留着上游 git 历史git log --all -S 搜关键字，找到修复提交，git show <fix> | git apply构建镜像时删掉 remote 和其他 ref，清空 reflog 再 gc，只留题目的基准提交；评分改成直接打测试补丁，不再依赖 git
容器能上网clone 上游仓库、拉 PR 分支、pip download 或 npm pack 新版本、从 GitHub API 取修复在宿主机的 DOCKER-USER 链上设白名单：容器只能访问模型 API 的 443 端口。每次开跑前先确认 GitHub、PyPI、npm 都连不上
文件系统在整个文件系统里 grep 题目原文，用 git fsck 找悬空的提交前两条堵上之后，这里已经找不到东西

五个 harness 全都这样做过，不是哪一家的问题。模型在推理里写得很明白：它知道后面会有隐藏测试，而上游的修复能过这些测试。这是 #231 第三条规则“不许偷看答案”在更开放的环境里的延伸：光靠事后翻 trace 不够，得在环境里把路堵上。在这之前跑出的 DeepSWE 结果和两轮 SWE-bench Pro 全部作废。

09 · Round 3SWE-bench Pro：隔离之后

从 SWE-bench Pro 公开集里选了 22 题（Python 8、Go 8、JS/TS 6），五个 harness 各跑一次，一共 110 次，全部是有效结果。模型用 DeepSeek 官方 API 上的 deepseek-v4.1-flash，五家的思考强度都是 high，单次输出上限统一为 64K，每题限时 1 小时。harness 版本固定：Codex 0.157.1、Claude Code 2.1.283、pi 0.85.1、Pi Lab（PR #318 分支）、dsh 0.1.2rc1，Codex 和 pi 的模型配置照搬 HarnessRouter 里的设置。这一轮全部在闲时跑，110 次一共约 38 元。

harness通过每次输入缓存命中每次输出每次花费
dsh15 / 226.2M99%66k0.45 元

通过率拉不开。22 题里有 15 题五家的对错完全一样（9 题全对，6 题全错），真正分出高下的只有 7 题。12 到 15 题的差距落在一次运行的噪声里。dsh 多出来的是两道只有它做出来的 Go 题，它也是最舍得花 token 的一家。

花费差得稳定。模型相同，思考强度也相同（DeepSeek 会把 medium 当成 high 处理），每次运行的花费却从 0.24 元到 0.45 元不等。缓存命中率都在 98% 以上，而命中价只有未命中的 1/50，所以在 DeepSeek 上账单主要由输出决定。Claude Code 的输入和输出都是最少的。

Pi Lab 为什么没省钱。它的输入比 pi 少约 9%，输出却差不多。SoL-Pi 省的主要是输入和缓存写入，放到输出主导的价格结构上就看不出来；换成缓存命中价约为 1/10 的模型，这部分才会值钱。

Pi Lab 输在哪。别家大多做对、Pi Lab 没做对的两题，卡在同一件事上：模型在整个文件系统里 grep 题目原文找答案，扫到 /proc、/sys 就卡住了，而 pi 这一系的 bash 工具没有默认超时，一条命令耗掉了整整一个小时。Claude Code 和 Codex 的命令都有默认超时。“工具默认超时”会是 Pi Lab 的下一个开关，也正好是一次只改一个机制的例子。

边界。每题只跑一次、只有 22 题，不足以排名。这一轮不经过 HarnessRouter 的 benchmark runner，而是在 Harbor 的任务容器里直接运行各个 harness。dsh 是预发布版本。所有结论只针对 deepseek-v4.1-flash 这一个模型。

10 · Takeaways三轮下来的结论

三轮一共 410 次运行，任务、评分方式各不相同，下面几条是它们共同指向的东西。需要先说明：它们都只基于 deepseek-v4.1-flash 这一个模型、每题一次运行，是观察，不是定论。

  1. harness 几乎不改变模型能做什么SWE-bench Pro 的 22 题里，有 15 题五家的对错完全相同，通过数只在 12 到 15 之间；首轮表格任务的完成率也都落在 77% 到 85%。一道题做不做得出来，主要看模型。
  2. 好的 harness 防的是卡死和打转拉开差距的往往不是聪明程度，而是护栏。Pi Lab 输掉的两题，都是一条 grep 在没有超时的 bash 里卡了一小时；dsh 在 GDPval 上没交出的 3 个文件，是长回复被截断、或者流断开后没有重试。命令超时、失败重试、输出截断这些细节，决定了模型卡住以后还能不能回来。
  3. 综合成本差距很大同一个模型、同样的思考强度，SWE-bench Pro 上每次运行从 0.24 元到 0.45 元，差 1.9 倍；首轮表格任务里，pi 和 cline 的 token 用量差 2.2 到 2.6 倍，总耗时差 1.9 倍。花多少钱，很大程度上由 harness 决定。
  4. 同一组合换一道题也差很多同一个 harness，便宜的题一次 0.14 元，难题要 0.78 元，差 5 倍多；做不出来的题反而最费钱，模型会在里面反复尝试。GDPval 上同一组合的交付物有时很出色，有时连文件类型都交错。只看一两道题、一次运行，说明不了一个 harness。

所以，报告成绩时应该写全三元组：模型 × harness × benchmark。“某个模型在某个 benchmark 上得了多少分”这句话本身是不完整的：同一个模型换一个 harness，成本可能差一倍，遇到会卡死的情况，分数也跟着变。DeepSeek 在 V4.1 Flash 的模型卡里分别报了它在 Claude Code、Codex、Pi 等 harness 下的 DeepSWE 分数，就是这个方向。除了三元组，还应该一起写清运行了几次、花了多少钱、评测环境有没有隔离（断网、清掉 git 历史），不然分数可能是抄来的。
