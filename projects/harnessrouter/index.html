一句话版本

同一个模型，放进不同的 agent 运行框架（harness），做完同一道题所需的时间和调用量可能差很多。我给上游项目加了一套公开任务评测：除了看答案对不对，也记录耗时、用量和失败原因，把“偷看答案”“评分器出错”这类情况单独列出来。下一步想固定模型和任务，每次只改变一个运行机制，分清省下的资源到底来自哪里。

01 · ContextHarnessRouter 是什么

HarnessRouter 是一个开源的 agent 基础设施：应用如果想分别接入 Codex、Claude Code、pi 这些后端，就得一个个处理会话、流式事件、文件、取消和失败语义。项目用 Unified Harness Protocol（UHP）把这些交互统一起来，并提供兼容 OpenAI Responses 的任务接口，让产品用同一套调用方式选择不同的 harness。Community Edition 以 Apache-2.0 开源，可以用 Docker 自部署。

这些工程设计属于上游项目。我是它的贡献者，下面讲的是我提出并实现的那一部分。

02 · Problem能跑起来，还不足以决定选谁

项目原本有两类检查：支持矩阵回答某个 harness 能不能在系统里跑起来，conformance 测试回答它是否遵守协议。但它们都没回答一个更实际的问题：同样的工作交给不同的 harness 和模型，完成率、耗时和资源消耗差多少？

我在 issue #205 里指出，当时官网上的对比数字来自单个没有公开任务与脚本的案例，缺少一个可以复跑的公共任务维度。

03 · Design在矩阵旁边加一个维度

我的方案是在支持矩阵旁边新增一个评测维度，以 harness × model × task pack 为比较单位，并复用项目已有的 API、会话、产物和运行记录。问题从“支持哪些后端”变成“这些组合做同样的工作做得怎样”，也不再把整体表现只归因于底座模型。

选任务集时，我最初考虑了多文档推理、表格产物、长程开发、跨系统工具使用等方向（DABstep hard、SpreadsheetBench 2、RoadmapBench、TheAgentCompany 等）。随后发现 DABstep 的 450 道正式题没有公开答案，只有 10 道开发题能在本地评分，于是自己更正：第一列改用答案公开、评分确定的 SpreadsheetBench Verified，DABstep 只留作管线的冒烟测试。

04 · Method第一列：SpreadsheetBench Verified

首轮取数据集前 50 题，对 pi、opencode、dsh、cline 各运行一次，共 200 次；模型都请求 deepseek-v4.1-flash，经同一个自定义连接，用自部署的 Community Edition。每道题的流程是：

记录什么

是否完成、reward、评分原因、总耗时与中位耗时、工具调用及其失败、fresh 和 cached input tokens、output tokens、实际使用的连接、服务端返回的模型、产物与错误记录。工具失败率只用能读到 trace 的工具结果做分母，不把缺失的记录当成成功；三类 token 分开报告，不直接换算成账单。

五条计分规则

  1. 连接必须一致实际连接与声明不符的运行列为 finding，不计分。
  2. 模型必须一致服务端模型不符也不计分；允许合法别名。缺失 served model 时照常计分，但明确标注“不可验证”。
  3. 不许偷看答案联网或到工作区外查找题目答案，列为 finding，保留证据、不计分。
  4. token 同一口径fresh、cached、output 三类分开，按同一规则统计。
  5. 只用确定性评分只用任务集自带的 grader，不用 LLM judge。

失败也要分清原因

正确答案本身都过不了 grader 的两道题，从所有组剔除。正常超时会记录取消，并对已有产物评分，产物没通过仍算失败。agent 还没开始动作就遇到的鉴权、余额、限流或服务错误，归为 runner error 并重跑，连续三次被供应商拒绝就停止。历史上代理超时后的 20 次任务，从会话记录里恢复评分，避免把客户端断线误判为任务失败。

05 · Results首轮结果，以及它不能说明什么

findings 共 4 次：pi 1 次、dsh 2 次到工作区外查找，cline 1 次联网。pi 与 cline 的 fresh input、cached input、output 分别相差约 2.5、2.6、2.2 倍，总耗时约 1.9 倍。

这些数字的边界要一起写清楚：它们是不同计分集合的汇总，不是逐题配对的均值，也不是账单倍数，不足以证明普遍的排名。四组的 Community Edition 版本和运行日期不完全相同；web 开关对 pi 和 opencode 是硬开关，对 cline 和 dsh 只是模型可能忽略的指令；cline 和 dsh 的 50 次运行都缺少 served model 记录。首轮没有做多轮随机重复和置信区间。这里的“可复现”首先指规则和汇总可以复核：实现支持断点续跑，表格能从 JSON 记录重新生成，finding 会话都留有 trace。

06 · NextPi Lab：一次只改变一个机制

第一列回答了“差多少”，但没回答“为什么”。不同的 harness 同时改变了许多机制，很难归因。issue #280 提出 Pi Lab：把机制做成开关，固定其余条件，比较原版 pi 与只多打开一个机制的实验组。首批机制来自 SoL-Pi。

最初的方案是用扩展加载这些机制，后来改成独立的 pi-lab backend，让原版 pi 保持为干净的对照，也避免工作区配置覆盖实验开关。短的表格任务可能看不出长程机制的收益，延长任务或缩小上下文窗口是下一步的实验思路，目前还不是已经取得的结果。
